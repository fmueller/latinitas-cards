# LatinitasCards v0.8.0

## Summary

Planned release. Hardens CLI usability, extension boundaries, pre-v1 migrations, and
operational safety so the full workflow is practical without requiring knowledge of Anki
internals or corpus implementation details.

## Goals

- Make common workflows discoverable while retaining deterministic expert controls.
- Provide best-effort migration from earlier generated material before v1 schemas freeze.
- Stabilize extension contracts for corpus adapters, analyzers, recipes, and outputs.
- Improve diagnostics, accessibility, performance, and recovery behavior before v0.9.

## Potential Features

### Guided CLI Workflows

Add guided project initialization, deck-profile confirmation, corpus import, recipe/theme
selection, preview, update planning, conflict review, and apply flows. Interactive commands
produce ordinary project files that can be inspected and rerun non-interactively. CLI
controls and documentation remain English.

### Best-Effort Pre-v1 Migration

Detect older profiles, manifests, generated-note layouts, and legacy Latinitas output.
Preview migration effects, preserve stable identities where evidence permits, and require
explicit choices where identity cannot be inferred safely. Pre-v1 compatibility remains a
best effort rather than a guarantee.

### Extension Interfaces

Document and test boundaries for corpus adapters, annotation producers, card recipes,
ranking factors, themes, dictionary links, and output transports. Extensions emit the same
versioned models, provenance, validation errors, and confidence states as built-in
components and cannot bypass ownership or plan/apply rules.

### Diagnostics And Recovery

Provide project health checks, environment/resource diagnostics, dry-run explanations,
backup guidance, interrupted-apply recovery, and actionable reports for Anki, corpus,
profile, optional model, and network failures. Core offline failures remain distinguishable
from missing optional resources.

### Performance And Accessibility Hardening

Profile large decks and corpora, bound memory use, cache reusable indexes safely, and keep
progress machine-readable. Validate theme contrast and non-color cues, readable card HTML,
keyboard-friendly CLI review, and German/English text handling.

#### Bounded-Memory Dense USFX Markup Retention

Bound end-to-end working memory for `corpus normalize --adapter usfx`, including passage
construction, validation, canonical serialization, and publication. Streaming XML alone is
insufficient when one passage retains many required metadata entries. Retention must not
materialize an unbounded collection of per-entry Python/Pydantic objects or a second full
serialized passage in memory. Compact representations and disk-backed/spooled processing
are implementation options, not a prescribed design. Define separately the memory needed
for text, XML depth, indexing, and bounded buffers; do not call a smaller per-entry constant
a bound independent of metadata cardinality. Temporary disk and output size may grow with
retained content and must have documented resource and cleanup behavior.

This is future performance hardening, not a new v0.3.0 acceptance or release gate. The
T-110 review reported a completed probe with 200,053 bytes of valid XML, 50,000 empty `w`
elements and one text character: 50,000 required entries were retained, with 51,961,856
bytes additional peak RSS. It demonstrated amplification, not a crash, OOM, or denial of
service; v0.3.0 defines input-size/depth limits but no total memory budget. Reproduce the
observation on the accepted implementation before drawing further conclusions.

Acceptance:

- Before implementation, commit a reproducible benchmark protocol and numerical pass/fail
  budgets for absolute peak process RSS, baseline-adjusted RSS growth, elapsed time, and
  temporary disk use on a named reference environment. Record Python/dependency versions,
  fresh-process baseline, repeated-run variation, fixture sizes, and measurement units.
  Define the working-memory envelope and allowed text/depth/index terms explicitly; at
  fixed text/depth, increasing retained metadata must remain within a fixed memory budget,
  not merely below the input-size limit. Report whole-process peaks through final write,
  including validation/serialization, rather than only parser allocations.
- Exercise geometric metadata counts including 5,000, 50,000, and 500,000 entries where
  inputs fit supported limits. Cover the empty-element probe, realistic nonempty `w`
  attributes and text, nested `wj`, notes/headings with flattened descendants, and unknown
  metadata under `--allow-unknown`. Include both one dense passage and many passages,
  long text with sparse metadata, and the bundled Clementine corpus as a realistic control.
  Distinguish fixed-text cardinality tests from tests whose meaningful payload also grows.
- Document supported boundaries and test both sides of the existing 64 MiB input and
  depth-64 limits, plus declared spool/disk boundaries. Do not silently introduce element
  caps, truncate metadata, or reject previously valid dense inputs to meet the budget.
  Any proposed compatibility restriction requires an explicit spec decision first.
- Preserve every required metadata entry, ordering, attributes, canonical text and spans,
  notes/headings attachment, identity, hashes, accepted aliases, and deterministic output.
  Check independently specified counts and literal values/spans as well as canonical-byte
  comparisons; validate emitted corpora and keep existing legacy goldens unchanged.
- Exercise late malformed/unknown XML, validation failure, exhausted temporary storage,
  and interrupted processing. Preserve existing diagnostics, exit codes, and failure/no-write
  semantics: never publish partial output or replace an existing destination on failure.
  Specify cleanup/recovery for temporary artifacts, including abrupt interruption, and
  verify it without weakening source immutability or existing atomic publication behavior.

## Caution

- Guided commands must not hide the effective configuration they create.
- Extension flexibility can destabilize schemas unless all boundaries remain versioned.
- Migration must prefer an explicit unresolved case over a guessed identity match.
- Caches are disposable optimizations and never canonical state.

## Recommendation About LLM Support

Optional LLM and agent integrations use documented extension boundaries and diagnostics.
They remain disabled unless requested and cannot weaken offline behavior, privacy controls,
or deterministic validation.

## Explicitly Excluded

- A GUI as a substitute for the CLI.
- Guaranteed migration from every unreleased historical prototype.
- Unrestricted third-party extensions modifying Anki or source data directly.
- Silent configuration, schema, or identity migration.
