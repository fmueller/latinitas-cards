# LatinitasCards v0.5.5

## Summary

Planned, inactive release after v0.5.0 and before v0.6.0. Adds sentence-function and
construction exercises from original Latin corpus passages, using v0.5.0's shared library
and LLM verification, automatic acceptance, CLI orchestration, reports and Anki status.
Support both finding corpus examples for source-deck vocabulary and creating exercises
from selected readings. Translation remains primary; contextual grammar explains how the
text works rather than requiring the learner to proofread generated claims.

This release discovers structure in supplied passages. v0.5.0 already owns isolated forms
and short, controlled combinations whose structure is specified by supported patterns.
The boundary is not the number of words on a card. Do not build a second acceptance engine
or move v0.5.0's curated grammar/mnemonic intake into this release.

## Planning Status And Dependencies

The entry points, selection behavior and presentation record user decisions. Items marked
**proposed technical contract** are recommendations requiring their named design checkpoint,
not approved wire formats or a claim of implemented coverage. Both specs remain inactive;
v0.4.0 is unchanged. This document neither activates a spec nor authorizes implementation.

Depend on v0.4.0's normalized corpora, citation/span preservation, corpus exercise identity
and file-based handoff, then v0.5.0's versioned evidence/acceptance and provider pipeline.
Add explicit adapters/schema upgrades where needed: existing strict morphology-only models
are not assumed to accept syntax roles, construction spans or automatic acceptance records.
Existing accepted corpus exercises remain usable without enabling a model.

## Goals

- Practice Latin-to-German translation using actual text, with form and construction
  recognition as supporting exercises; retain explicit German/English generated content.
- Find useful passages for known deck entries and support passage-first study without a deck.
- Discover supported constructions automatically, subject to profile/CLI filters and budgets.
- Explain unsupported material and lower accepted-card yield instead of silently omitting it.
- Extend automatic checking without claiming exhaustive or error-free Latin syntax analysis.

## Potential Features

### Deck-Driven Corpus Examples

Given a confirmed source deck/profile and selected normalized corpora, discover occurrences
of selected vocabulary and propose contextual exercises. Match inflected forms using
supported analysis with explicit lexical/sense evidence, not surface-string equality alone.
Deck knowledge helps prioritize appropriate passages; it does not prove a passage's syntax
or that every occurrence has the deck entry's sense. Preserve alternatives and explain
unresolved homographs, sense conflicts and missing matches.

Use original wording with source edition/work/native citation and enough sentence/passage
context to support the question. Do not invent an example and label it as Vulgate or another
source. If a passage is shortened, retain its source span and expose the full context on
the answer/report; do not silently turn fragments into altered quotations.

Acceptance: link a deck entry to an inflected occurrence, distinguish a homograph/wrong-sense
control, retain exact source text and citation, and report no suitable match without
fabricating a passage. The source deck is read-only; a corpus link never changes deck identity.

### Reading-Driven Exercises

Given selected works/passages or reading ranges, discover eligible grammar targets without
requiring a source deck. An optional deck supplies vocabulary priorities and difficulty
signals, not a prerequisite for source identity or grammatical acceptance. Both entry points
use the same proposal, evidence, selection and export contracts. Reaching the same semantic
exercise through both paths must not create duplicate notes or reset existing schedules.

Translation cards show the Latin before its analysis. Recognition cards identify a target
without revealing the tested function; answers explain its contribution to meaning and
include a reference translation only when that translation is sufficiently supported.
Reference wording is guidance, not exact-string grading. A construction explanation or
translation is its own checked assertion, not automatically approved by accepted morphology.

Acceptance: a selected passage produces supported exercises without a deck; adding deck
priorities affects selection rather than source identity. Both entry points can converge
on one exercise. Ambiguous or incomplete context retains defensible alternatives or withholds
the question; missing translation support cannot silently produce an asserted translation.

### Supported Construction Library And Automatic Discovery

Implement and test a bounded library covering basic subject/predicate/object/attribute and
prepositional functions, plus AcI, ablative absolute, participium coniunctum and selected
subordinate-clause types. The exact clause inventory, annotation conventions and supported
boundaries require the P55-1 design checkpoint. The list describes committed feature
families, not a promise that every occurrence in arbitrary Latin can be resolved.

Within that library, discover candidates from the supplied deck/corpora automatically.
Profiles and CLI filters restrict construction types, vocabulary, passages, difficulty
and card count. Do not require selection of each candidate. Without extra filters, choose
a finite varied set, respecting previous selections and suppression as applicable. Report
selection factors and limits; do not silently replace v0.4.0's ranking rule or use raw model
confidence as a new ranking factor.

A user filter narrows the supported set; it does not authorize an unsupported analysis.
Report detected unsupported constructions and explicit failures where detectable. Do not
claim every unsupported construction was discovered or classify all unknown text as
unsupported. No fixed corpus/course whitelist: process any supported input, report the
demonstrated evaluation scope, and withhold unresolved candidates individually.

Acceptance: profile and CLI restrictions exclude the requested categories deterministically,
default budgets prevent unbounded output, and near-duplicates do not exhaust the selection.
For each supported family, include a valid case, an ambiguity/conflicting-evidence case and
a documented unsupported boundary. Test classical and biblical material separately and
publish actual coverage rather than infer it from a successful import.

### Contextual Verification And Material-Yield Reports

Extend v0.5.0's evidence and blind counter-check pipeline with passage context, target and
construction spans, sense choices, dependency/role alternatives and conventions. A dependency
parse alone does not prove a pedagogical sentence function. A blind check must not receive
the first model's labels or explanations disguised as source facts. Upstream accepted
morphology may be supplied with its provenance; proposed syntax remains the task to solve.

Automatically accept only complete supported assertions under the applicable policy with
no unresolved objections. The same model may be used for separate proposal/check runs;
second-model support is configurable, not mandatory. Do not equate agreement or high model
confidence with human review or measured correctness. Shared invalidation/reuse rules bind
the actual passage, relevant annotations, source/deck links, check policy and model/prompt
configuration. Changed passage context invalidates its dependent analyses.

Use the shared optional review queue and report taxonomy: not generated, not processed/deferred,
withheld, processing failed, accepted but not selected, and accepted/selected. Summarize by
material and exercise type, with source-linked examples and reasons. Distinguish a lack of
suitable passages or supported constructions from model outages, linguistic conflicts,
processing limits and output-card selection budgets. Do not invent candidate counts for
unprocessed input. No need to approve every withheld item before using supported output.

Acceptance: a new passage can yield automatically accepted cards without per-claim human
approval. Unresolved model disagreement, insufficient context and a model outage produce
different report outcomes. Passage edits invalidate dependent checks while unrelated
validated work can be reused. Reuse the shared evaluation protocol with independent syntax
judgments; permit negative or not-evaluable results and narrow the affected acceptance path.
Exhaust processing limits before the whole reading is analyzed, distinguish deferred work
from accepted-but-unselected exercises, and resume without repeating validated checks.

### Syntax Presentation And Anki Handoff

Add optional independent semantic classes for sentence functions and construction spans,
building on v0.5.0 morphology themes. Support configurable course conventions, light/dark
appearance and non-color cues. Explanatory colors/labels default to the answer; the front
may neutrally mark the target without leaking its tested role. Preserve original text and
handle nested/overlapping constructions without corrupting passage spans or HTML.

Reuse the small answer-side acceptance status and collapsible `Warum diese Antwort?`
section. Explain the construction-specific basis and show source context/citation; keep
detailed stage results in the report. Note tags summarize acceptance conservatively; precise
per-card status stays inspectable. Fully checked automatic cards are not relabeled as human
reviewed. Theme changes do not affect linguistic acceptance, identities or schedules.

**Proposed technical contract:** define versioned syntax/span annotations, exercise semantic
keys, layout/field ownership and explicit note-type/template migration at P55-1. Reuse
existing corpus layouts where compatible; do not silently repurpose frozen slots or promise
that a new recipe needs no schema change. File export and managed updates remain canonical;
omitting an old card from new output does not delete or safely retire its existing Anki card.
Direct Anki provisioning/application remains v0.6.0 scope.

Acceptance: inspect supported exercises in Linux Anki Desktop in German and English,
light/dark modes, and collapsed/expanded evidence states. Check neutral fronts, nested
markings, keyboard accessibility, import/update identity and scheduling, user fields/tags,
and explicit handling of previously accepted exercises that become ineligible.

## Open Technical Design Checkpoints

- P55-1 must specify subordinate-clause coverage and negative boundaries, label conventions,
  data/schema adapters, source-link ambiguity handling, selection defaults/precedence and
  migration. These choices are proposed design work, not silently delegated product policy.
- Reuse v0.5.0's evaluation design but add independently judged construction cases and
  release criteria. A morphology benchmark does not establish syntax accuracy. Capture
  required corpora/licences and available native/model environments before release checks.
- Implementation decomposition and activation are separate work. Unresolved P55-1 design
  gates block dependent tasks; this planning package does not promise selector eligibility.

## Caution

- Original Latin can admit multiple analyses; a construction name is not a unique translation.
- Smaller accepted-card yield can reflect honest uncertainty, not a defective corpus.
- Shared model errors, prompt injection and unsupported parser conventions remain risks.
- A selected passage is not permission to send unrelated deck content to a hosted provider.
- Corpus and translation licensing/provenance remain separate obligations.

## Recommendation About LLM Support

Use v0.5.0's optional, explicitly configured local/hosted pipeline and provider limits, not
a separate syntax-specific service. Include the necessary source context while enforcing
declared data boundaries; no silent endpoint fallback or authority derived from source text.
Keep library/rule/human-backed operation usable without an LLM where supported, without
claiming equivalent automatic discovery coverage. Self-reported confidence may be retained
as an estimate, never the sole acceptance threshold.

## Explicitly Excluded

- Exhaustive or infallible automatic interpretation of arbitrary historical Latin.
- Accepting unsupported construction types merely because a filter or LLM requests them.
- Mandatory human approval of every automatically accepted contextual exercise.
- Invented or silently rewritten quotations presented as source-corpus examples.
- Exact-string grading of free translations or default Latin production drills.
- A second verification engine, mandatory second model, GUI, or required hosted provider.
- Direct Anki integration/provisioning (v0.6.0) or portable project bundles (v0.7.0).
