# LatinitasCards v0.2.0

## Summary

Planned release. Builds on v0.1.0's coherent-learning-object note model, stable note and
card/template identities, confirmed deck profile, and deck-first CSV workflow. Adds
destination-aware managed updates, evidence-led source extraction, Latin form analysis
with calibrated review gates, a configurable semantic presentation layer, and PyPI
publishing. These are target contracts, not claims that the current CSV exporter
implements managed application.

## Goals

- Update previously generated material without duplicate notes or lost review history.
- Protect shared personal fields, destination-added tags, and each card's scheduling;
  expose conflicts before applying changes.
- Expand source-text extraction from reviewed skipped/ambiguous cases without confusing
  successful extraction with supported linguistic analysis.
- Explain how principal parts relate through stems and formation markers, with only
  linguistically supported detail; generate high-precision form-parsing exercises after that.
- Introduce configurable, restrained presentation without coupling colors to linguistic data.
- Publish versioned releases on PyPI so users can install the CLI without a Git checkout.

## Potential Features

### Managed Update Plans

Compare regenerated knowledge, the last successfully applied managed baseline, and a
current snapshot of the explicitly selected destination. Classify each logical note as
create, update, unchanged, conflict, or retire, with separate per-card effects: retain,
add when eligible, retire, or reactivate an eligible existing retired card. Include reasons
and blocked/unsupported operations rather than silently treating an incomplete snapshot
as an empty destination. Plans must be
deterministic, machine-readable, and inspectable before application.

The destination is the identified target collection/export, Latinitas-owned note type, and
managed note set, not merely a deck name or the source input. Record snapshot fingerprint,
baseline version, effective profile, proposed values, field/tag differences, card effects,
transport capabilities, and conflicts. A CSV snapshot without card state cannot establish
scheduling preservation or authorize structural changes. Missing or duplicate identities,
unknown schemas, and absent baselines require reconciliation; never adopt existing notes
by visible text alone or label missing baseline data as safe to overwrite.

For managed fields use a three-way comparison: change only when the destination still
matches the applied baseline; convergent destination/proposed values need no write.
Divergence from both baseline and proposal is a conflict, including destination-only edits
that regeneration would undo. Resolve explicitly by keeping destination, accepting the
proposal, or reviewing a replacement; record the decision and resulting managed baseline.
User-owned personal fields are excluded from writes and baseline ownership, not presented
as conflicts that the user could authorize the generator to overwrite.

Acceptance: sanitized fixtures distinguish create, unchanged, safe update, convergent
edit, divergent edit, missing baseline, wrong destination, duplicate identity, and stale
snapshot. A failed/partial apply never advances the whole baseline as if successful;
retry first reconciles observed destination state with recorded applied operations.

### Note And Card Lifecycle Contract

Use the v0.1.0 target: one Latinitas-generated note per coherent learning object, normally
one Latin lexeme plus relevant sense, with zero or more conditional retrieval cards.
Strongly related facts that meaningfully cue one another share a note; merely related
material need not. A contextual sentence exercise may be a separate object. An arbitrary
source note can contain multiple objects and must not be assumed to be one unit; ambiguous
splits need confirmation and stable object identities. Separate source entries are not
automatically merged because their visible lemma matches. This release adds no contextual
recipe merely to illustrate that boundary.

Retain v0.1.0's immutable source/object-to-`LatinitasID` mapping and provenance. The note
identity is not a recipe, profile, or question identity. Card identity combines the stable
parent-note identity with the semantic retrieval-task key and its stable template binding.
Software version, profile name, enabled card set, wording, explanations, segmentation,
CSS, colors, and mutable form strings must not re-key the note or surviving cards. Local
Anki note/card IDs and template ordinals are destination bindings, not portable identity;
do not silently reorder/reuse a template slot for a different retrieval task.

Personal Notes and tags belong to the shared note and are visible/shared across its cards.
Cards remain Anki siblings with independent scheduling and review histories. Respect the
user's sibling-burying settings; Latinitas neither implements FSRS nor creates note-level
scheduling. Source fields, source note types/templates, and source deck structure stay
unchanged; enrichment targets dedicated Latinitas-owned note types only.

Profiles select knowledge and eligible card types, not note identity. Adding supported
knowledge or enabling an eligible card enriches the same note; existing cards retain their
identities and schedules, and only added cards start as new Anki cards. Follow v0.1.0's explicit
per-card required-role rules: absent, ambiguous, withheld, or inapplicable data must not
produce empty or misleading new cards. A noun must not acquire verb cards. Parser failure,
incomplete source input, or uncertain object reconciliation is a blocked/review outcome,
not evidence that existing cards should be retired.

When an approved profile/data change makes an existing card ineligible, plan card-level
retirement rather than clearing required fields and letting import delete/recreate it.
Retain the last safe content and its provenance while suspension is pending or required;
never present stale retained data as a newly approved claim. If safe retention cannot be
represented by the existing schema, block application. Explicitly retiring an entire
object tags its note `latinitas::retired` and suspends its cards. Retiring only one retrieval
task suspends that card, leaves siblings active, and records card-level retirement in the
managed manifest; the note-level tag must not imply all siblings are retired. Neither
case deletes notes, cards, templates, personal data, or review logs. Re-enabling a retired
card requires an explicit reactivation plan effect and approval, reusing its existing
note/card/template identities and review history rather than adding a new card. Record
pre-retirement suspension state and tool-applied suspension provenance. Reactivation may
reverse tool-owned suspension only; cards already suspended by the user remain suspended.
Unknown or conflicting suspension ownership requires review and blocks unsuspension;
profile re-enablement alone never authorizes it.

Acceptance: an object with completion and recognition tasks stays one note with multiple
distinct sibling cards across wording/profile/theme changes. Multiple objects, including
two senses in one source note, retain separate identities. Enabling one eligible card
adds only that card; disabling one does not retire siblings. Missing-form and unsupported
cases create no invalid cards and trigger no implicit deletion. Verify each surviving
card's schedule/review history independently, including user-suspended cards.
Reactivation fixtures cover an eligible tool-retired card, a user-suspended card later
retired by the tool, uncertain suspension ownership, and re-enablement without approval.
Only approved reversal of tool-owned suspension may unsuspend; all cases retain existing
identities and histories, create no replacement cards, and leave siblings unchanged.

### Destination Tag Ownership

Native plain CSV Update replaces destination tags with the exported set, even if managed
fields are unchanged. v0.1.0 documents that limitation; source parent-tag inheritance is
already resolved and is not destination-tag preservation. v0.2.0 must distinguish:

- source-inherited tags, traced to the current source note;
- configured generated tags and lifecycle tags, with their managed provenance; and
- user-added destination tags, which Latinitas does not own or remove.

Persist source/configured contributions separately in the applied baseline even when the
same tag has both origins. Compare them with current destination tags and the proposal.
Preserve destination-only additions. Removing one generated contribution must not remove
a tag still contributed by another origin. Removing a previously managed tag requires an
inspectable removal decision; destination deletion of a still-required generated tag is
a conflict rather than an automatic re-add. Tags do not affect note/card identity.

Anki stores a tag set, not per-tag authorship. A user intending to keep a tag already
present as a managed tag leaves no observable addition. Never claim to infer that intent:
show proposed removals and allow an explicit keep-as-user-owned decision, recorded in the
baseline. Unknown ownership on first adoption requires review. A destination-added tag in
the managed namespace is not automatically owned by Latinitas. Reserved lifecycle-tag
collisions require resolution and never authorize suspension by themselves.

Acceptance: test source additions/removals, configured changes, overlapping origins,
manual destination additions, user-deleted generated tags, keep-as-user-owned overrides,
unknown baseline ownership, lifecycle collisions, and unchanged/no-op regeneration.
Compare exact final tag sets, not just inclusion of generated tags; shared siblings see
the same preserved tags. Deterministic deduplication must not erase origin information.

### Safe Update Application

Apply only the approved operations to the bound destination snapshot. Approval includes
field conflicts, tag changes, card additions/retirements/reactivations, and any structural
migration; generation or profile confirmation alone is not apply permission. Revalidate the relevant
destination preconditions immediately before application; changed state requires a new
plan/approval. Keep a recoverable backup and an application report. Update only managed
fields and approved managed tag contributions; preserve user fields and destination tags.
Never treat artifact creation as proof of successful import or advance the applied
baseline without observing the destination result.

File-based output remains canonical, with explicit transport capability gates:

- Destination-aware CSV can emit reviewed managed content and a reconciled full tag set
  for the existing compatible note type. It must omit Personal Notes from importable
  writes. It cannot itself check a later GUI import, preserve tags added after the
  snapshot, suspend cards, or migrate templates/scheduling. Require a fresh snapshot and
  no intervening destination edits through import, followed by reconciliation; if this
  cannot be established, withhold the preservation claim and require replanning. Plain
  source-only CSV remains the limited v0.1.0 path, not a managed preservation guarantee.
- A file-based transport claiming structural changes or retirement must demonstrate
  preservation of the actual destination card identities, schedules, and review logs.
  APKG support must follow Anki GUID, note-type, template, and modification-time semantics;
  copying local numeric IDs into a package is not proof of safe matching. Until verified,
  report such operations as unsupported and refuse their application, not approximate
  suspension by a tag or an empty card. A separate content-only plan may be approved.
- Reading/writing a running collection and general automated note-type/template
  provisioning remain v0.6.0 work. v0.1.0 supplies reference templates and the verified
  import checklist; v0.2.0 verifies compatibility with that contract rather than silently
  provisioning or rewriting arbitrary note types.

Acceptance: actual supported import/update paths must show no duplicate notes or cards,
unchanged user fields/tags, and full card/review-log comparisons for content-only changes
and no-op reapplication. For card additions, approved suspension, or reactivation, enumerate
only the expected rows/columns that may change; surviving card schedules/review logs stay intact.
Check sibling relationships and configured burying without reproducing Anki's scheduler.
Exercise stale-plan rejection, backup/recovery and retry. Unit tests or a generated CSV
alone do not establish destination safety. Record tested transport/client/version and
limitations; broad compatibility testing remains v0.9.0.

### Pre-Release Migration Boundary

Depend on v0.1.0's explicit boundary between experimental per-exercise notes and the new
learning-object notes; do not rewrite historical IDs/manifests as if they had always used
the new model. Ordinary regeneration is not structural migration. Detect incompatible
schema/identity/template layouts and stop with the available choices before import.

The default for disposable pre-release experiments may be an explicitly chosen fresh
start in a separate destination, after backup, leaving the original data untouched and
stating that new cards do not inherit scheduling. Do not automatically delete or retire
the old notes. A scheduling-preserving consolidation, if supported, needs a separate
approved plan mapping every old note/card/template to its target learning object and
retrieval task. Reconcile differing Personal Notes without dropping text or provenance,
union user tags, and block ambiguous senses, duplicate task histories, or incompatible
templates rather than arbitrarily choosing a surviving history. Preserve per-card review
logs and scheduling, not merely a note-level summary. CSV-only regeneration is not this
migration. Unsupported consolidation must fail clearly; do not introduce a general
migration engine solely for unreleased disposable data.

Acceptance: old-layout fixtures are rejected by normal apply; fresh-start output leaves
original notes/cards/user data unchanged and discloses new scheduling. Any supported
consolidation must prove its complete old-to-new mapping, user-data reconciliation,
surviving card histories, retry safety, and rollback before being advertised. Pre-1.0
schema freedom does not waive these protections.

### Evidence-Led Source Extraction

Source-text extraction identifies candidate forms, separators, alternatives, explicit
omissions, and embedded hints from a confirmed field layout. It is separate from
linguistic analysis, which decides what a form means and which claims can be studied.
Successful extraction never establishes a grammatical role or calibrated certainty.

Use v0.1.0's reviewed skipped/ambiguous-entry evidence to select additional layouts and
normalization rules. Publish the supported-layout matrix and representative sanitized
fixtures before broadening it: include formatting/separator variations, alternative
forms, missing roles, and hints mixed with forms. Keep original text/provenance alongside
normalized candidates, record applied rules, and show representative profile-confirmation
examples. Alternatives stay alternatives until an explicit rule/review selects them;
omissions stay absent rather than shifting later forms into earlier slots. Mixed hints
are retained as evidence, not silently converted to grammatical facts. Unknown formats
and conflicting hints remain unsupported/ambiguous with actionable reasons.

Acceptance: reviewed examples assert exact candidates, role positions, alternatives,
omissions, and reasons for withholding. Include counterexamples that look similar but
must not parse, and distinguish extraction failure from linguistic uncertainty in skip
summaries/review output. Coverage reports give reviewed/generated/skipped/ambiguous counts
for the declared sample, not an unmeasured claim of universal support. Broader input
support follows evidence; demonstrated bugs in the v0.1.0 promised layout remain v0.1.0
work. No private deck or private output is required for these fixtures.

### Calibrated Form Parsing

Generate Latin-first parsing cards that map an encountered form to lemma, person, number,
tense, mood, voice, case, gender, or other applicable features. Confidence is tracked per
claim, not as one score for the whole analysis. CLTK/Stanza, deterministic rules, lexical
data, and optional LLM disambiguation are evidence sources; none is accepted as calibrated
without evaluation on reviewed material from the relevant Latin domain.

The default policy is precision-first for facts placed on study cards. High-confidence
claims may be applied automatically under project policy; ambiguous claims enter a review
queue with alternatives and provenance. Acceptance into generated knowledge is not
permission to apply a destination update; managed-plan approval still governs writes.

For the existing principal-part completion and recognition recipes, prioritize the
relationship among named principal parts over simply listing tense/person features. On
answer reveal, show a focused German explanation of the tested form and a compact
comparison with related stems. Keep the complete four-role comparison and further
explanation on the answer side, initially collapsed under `Stammformen vergleichen`.
Show absent or withheld roles explicitly without fabricating a complete paradigm.
The confirmed deck profile names the fourth role explicitly: PPP (*Partizip Perfekt
Passiv*) and supine are distinct grammatical roles, not interchangeable labels. Do not
infer case/gender or PPP status from an uncontextualized `-um`; omissions, exceptional
patterns, and deponents need explicit handling or an unsupported/review outcome.

Represent segmentation and its explanation as reviewable linguistic claims independent
of display styling. Where evidence supports it, show stem, formation marker, and ending
(e.g. `amā- | -v- | -ī`, explaining `-v-`); where only a coarser analysis is justified,
show stem plus ending (e.g. `amāv- | -ī`). Irregular relationships such as
`ferre → tulī → lātum` may be compared without fabricated character-level derivations.
Uncertain splits or explanations must be withheld or sent to review with alternatives and
provenance, never promoted merely because an analyzer or LLM supplied them. The existing
claim-level calibration requirement applies to each segmentation and explanation, not
just to the form's label. An unreviewed example is not evidence of calibrated accuracy.

Acceptance: tests cover detailed, coarse, irregular, ambiguous, omitted, PPP, supine,
and deponent cases; unsupported facts are not rendered as assertions. Both existing
recipes retain their Latin-first prompts and stable exercise keys. Reviewable output
exposes evidence and the reason for withholding a split; automatic claims require
domain-relevant reviewed evaluation and project-policy thresholds. Form-parsing cards
remain a distinct later step, using the same precision-first gate rather than treating
principal-part comparison as proof of full token analysis.

### Morphology Themes

Generated content uses semantic classes for roles such as lemma, stem, formation marker,
and ending, with room for the existing noun/verb roles. The owning configuration is the
versioned, human-readable deck/project profile and its reported effective overrides,
not a separate hidden settings store. Extend its schema explicitly; incompatible profile
versions must fail clearly rather than silently reinterpret older profiles. A named
color profile maps semantic roles to presentation only: ship a muted default and a
monochrome option, each with light/dark variants. Most content remains ordinary text;
use restrained accents and meaningful labels, separators, and typography so the anatomy
remains comprehensible without color. No palette value, style class, or chosen profile
may change linguistic claims or stable note/card identity.

Render ordinary generated answer HTML from escaped source strings and controlled markup;
do not pass through arbitrary HTML from source deck fields. Prefer native
`<details><summary>Stammformen vergleichen</summary>…</details>` for the additional
comparison rather than custom JavaScript, subject to actual Anki client verification.
The core answer and compact comparison must remain visible after reveal even if expansion
is unsupported. If native disclosure is unusable in a supported client, use a tested
static, fully readable answer-side fallback without hiding information behind broken
controls; do not silently add an untested script dependency.

Acceptance: preview and exported/imported notes preserve the same semantic claims when
switching muted/monochrome profiles or light/dark variants; labels and separators remain
useful with color absent. Verify answer reveal, touch expansion, and readable light/dark
appearance on AnkiMobile (iPhone/iPad, primary), and reveal/disclosure on Anki Desktop
(secondary). A browser preview or static HTML snapshot alone is not native-client
evidence. Record client/version, device, observed behavior, and fallback decision before
claiming client compatibility; native-client manual verification is a future release gate,
not a test already performed.

### PyPI Publishing

Publish the v0.2.0 release and subsequent approved releases as source distributions and
wheels on PyPI. Provide an automated release workflow using PyPI Trusted Publishing,
restricted to approved release tags and a protected publishing environment; routine CI
must not publish packages. Build and validate distributions from the release commit,
and publish only after release checks pass and the maintainer approves publication.

Verify installation from the built wheel and source distribution in clean environments,
including the `latinitas-cards --help` entry point. Default installation must not require
CLTK/Stanza resources or optional annotation extras. Document installation, upgrades,
supported Python versions, and optional extras; after publication, verify installation
of the exact released version from PyPI. Package metadata and bundled licensing notices
must be complete, and package availability and Trusted Publisher configuration must be
confirmed before claiming the release is published.

## Caution

- CSV, APKG, and direct collection updates have different matching behavior; a shared plan
  must not conceal transport-specific limitations.
- The installed CLTK/Stanza path does not provide calibrated token-level probabilities.
- LLM self-reported confidence is not calibration.
- Changing note-type or template identity can detach scheduling from its intended exercise.
- A shared learning-object note does not imply shared scheduling; retiring one card must
  not retire its siblings or erase shared personal data.
- If a v0.1 profile or note template cannot carry the new settings or disclosure without
  changing scheduled template identity, resolve that migration explicitly before applying
  generated changes; pre-1.0 schema freedom is not permission to lose review history.

## Delivery Order And Open Evidence

1. Consume the v0.1 learning-object identity, stable template bindings, conditional-card
   rules, shared-field ownership, reference setup/import checklist, and explicit
   pre-release fresh-start/migration boundary. Do not implement v0.2 against the historical
   per-exercise-note default or infer that every source note is one learning object.
2. Review v0.1 skip/ambiguity evidence, establish extraction fixtures and explicit
   PPP/supine/deponent boundaries, and define claim-level evidence and coarse/unsupported
   fallbacks before generating explanations. New supported layouts need reviewed examples;
   extraction success alone is not analysis calibration.
3. Add explanations and comparison to the existing recipe answers, then extend the
   versioned profile with named presentation options and render safe answer-side markup.
   Test linguistic output independently of color and preserve note/card identities.
4. Exercise destination-aware plans, tag-ownership reconciliation, and approved updates
   against changed content/styles and eligible card sets. Verify user data, card-level
   scheduling, stale-plan rejection, and retirement capability on actual target transports
   rather than assuming CSV/APKG parity. Publish unsupported operations before apply.
5. Run AnkiMobile and Desktop acceptance on a sanitized representative deck before
   marking disclosure and contrast compatible. Client behavior, calibration thresholds,
   and the safe template/profile migration path require evidence; until then, retain the
   static disclosure fallback and do not claim full release readiness.

T-026 safe HTML, T-027 Personal Notes protection, and T-028 parent-tag inheritance remain
closed regression baselines. Native GUI fresh/update/no-op imports, full-table scheduling
checks, and existing recipe visuals passed the retest in its tested environment. That
evidence neither resolves manual destination tags nor validates the new multi-card
lifecycle or v0.2 disclosure/theme behavior. Old harness, permission, and process failures
are not new product requirements.

Before implementation, settle the minimum destination snapshot format and supported
file-application transport for each operation, including whether retirement can be applied
safely in v0.2. Record this decision before implementing managed plan/application contracts:

- Specify the snapshot's destination binding, schema/template identity, managed values,
  tag provenance, and available card/suspension/review-state evidence, plus completeness
  and freshness checks. Missing evidence blocks the operations that depend on it.
- Publish an operation-by-transport matrix for content/tag updates, card addition,
  retirement, reactivation and migration. Name the supported native verification path
  for each claimed capability; label unproved capabilities unsupported before apply.
- Define how observed import results establish or advance the successfully applied
  baseline, and how partial application is reconciled. v0.1's prior-export eligibility
  checkpoint is not that baseline and cannot be promoted merely because a file exists.
- If no file transport safely supports retirement/reactivation, retain inspectable plans
  and reject those apply operations; allow separately approved compatible content-only
  plans. Do not bring live integration or general provisioning forward from v0.6.0.

Unsupported structural migration remains blocked, with the explicit fresh-start option
for disposable data. Exact new extraction layouts, calibration
thresholds, and any migration support require reviewed evidence rather than speculation.
Exact palette values and the native-client fallback choice depend on readability and
client testing, not another new recipe or unreviewed grammatical inference.

## Recommendation About LLM Support

Keep LLM use optional and network-explicit. It may propose alternatives, disambiguate in
context, or explain an analysis. Auto-application depends on measured recipe/analyzer
performance and project policy, not provider confidence claims.

## Explicitly Excluded

- Corpus-first generation.
- Syntactic sentence-role analysis and coloring.
- German-to-Latin production or any new principal-part recipe beyond completion and
  recognition; corpus/syntax explanations are not part of these cards.
- Direct updates to a running Anki instance.
- General automated note-type/template provisioning (v0.6.0).
- Broad deck/domain/platform compatibility certification (v0.9.0).
- Automatic deletion of retired notes or cards, and silent per-exercise-note consolidation.
- Network-required core operation.
- Backwards-compatibility guarantees for pre-1.0 profiles and manifests.
