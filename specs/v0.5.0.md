# LatinitasCards v0.5.0

## Summary

Planned, inactive release. Makes deck-based forms and short, controlled word groups useful
for Latin-to-German translation practice without requiring approval of every generated
claim. Reuse source-deck evidence, check it with Latin analysis libraries and rules, and
use an optional LLM proposal and blind counter-check pipeline for supported enrichment.
Automatically accepted cards remain distinguishable from human-reviewed cards. Unresolved
candidates go to an optional review queue, not the learning deck.

This release also retains curated grammar rules and mnemonics with explicit human approval.
It owns the shared verification pipeline and morphology presentation. Discovery and analysis
of sentence functions and constructions in original corpus passages belong to
[v0.5.5](v0.5.5.md). A controlled mini-clause is not excluded merely because it contains
several words: its structure is supplied by a supported pattern rather than discovered in
arbitrary prose.

## Planning Status And Release Boundary

The behavior below records the agreed product scope. Sections marked **proposed technical
contract** are implementation recommendations, not previously settled wire formats or user
choices. Their named design checkpoints must be resolved before dependent implementation
tasks are ready. This document does not activate a spec or authorize implementation.

v0.4.0 remains unchanged. Its accepted-annotation gate, confidence-neutral ranking and
German characterization goldens remain binding for that release. v0.5.0 explicitly changes
the later acceptance model and adds opt-in orchestration; it does not reinterpret historical
review decisions or the v0.3.0 sidecar-write policy as automatic linguistic approval.

## Goals

- Prioritize Latin-to-German translation; retain explicit German/English output languages
  and English CLI controls. Form recognition supports translation, not the other way round.
- Reuse plausible deck data rather than ask a model to invent already available forms.
- Support automatic acceptance after defined evidence checks without per-card human work.
- Offer one CLI entry point, inspectable stages, bounded selection, and explainable outcomes.
- Represent uncertainty and alternate analyses instead of teaching guesses as facts.
- Accept any supported source material, without a fixed author, corpus or course whitelist.
- Support morphology conventions without naming or hard-coding one course.
- Treat mnemonics as curated content that can generate repeatable cards.

## Potential Features

### Grammar Exercise Library

Expand beyond v0.2.1's bounded deck-based phrase and form-recognition exercises. Add recipe
families for verb production/recognition, stems, noun nominative/genitive pairs, declension
recognition, case and number, and adjective agreement. Include both standalone forms and
short preposition–noun, noun–genitive, adjective–noun and verb–noun combinations, including
mini-clauses with supported conjugated verbs. Patterns must model government, agreement,
sense and valency, not concatenate arbitrary words. Unsupported paradigms or combinations
remain reported outcomes. Extend existing phrase inputs and recipes rather than create a
second phrase engine. Basic roles already specified by a controlled pattern stay in scope;
automatic discovery of those roles in corpus prose moves to v0.5.5.

Translation is the primary exercise; form recognition is a selectable supporting recipe.
Latin-form production and fill-in-the-form clozes are opt-in. Do not multiply each example
into every recipe or reveal a tested form's analysis on a translation front. Reference
translations are guidance, not unique strings for automatic grading. Each card has one
primary learning objective. Preserve legitimate alternatives, including isolated forms
with multiple readings; withhold exercises whose intended distinction the prompt cannot
support.

Profiles and CLI filters choose vocabulary, patterns, recipes and limits. Without extra
filters, select a bounded, varied set rather than export every possible combination.
Explain selection and duplicate suppression in the report. The finite default budget and
selection rule must be specified and tested at the selection design checkpoint; they are
not inferred from an LLM's preferences.

Acceptance: demonstrate translation and recognition using contrasting noun cases, verb
forms and adjective agreement. A wrong government or agreement pattern must fail; an
ambiguous prompt must retain alternatives or be withheld. Default output contains no
Latin-form clozes. Explicit opt-in enables supported clozes without changing other recipes.

### Shared Evidence And Automatic Acceptance

Source-deck fields are inputs, not blanket proof of every derived explanation. Bind each
used form and meaning to the confirmed field mapping, check plausibility using applicable
rules/library results, and record the outcome. Missing corroboration may trigger LLM
verification; contradictions must be resolved with recorded evidence or remain withheld.
Do not manufacture a missing source form or repair source identity by accepting an analysis.

Support library/rule-backed acceptance and optional LLM-supported acceptance. For the latter,
generate a structured proposal, then solve the task in a separate model invocation that
sees the source evidence and task but not the first answer, its rationale or confidence.
Compare the two results, explicitly examine alternatives and objections, and accept only
when the defined checks pass, the answer fits the evidence, and no material objection is
unresolved. The same model is permitted; a separately configured second model is optional.
Neither agreement nor self-reported confidence is proof of correctness or a measured error
probability. Unresolved semantic disagreements cannot be resolved by majority vote alone.

Assess the full rendered assertion, not only isolated labels. A supported form does not
automatically approve a translation, segmentation or explanatory sentence. An exportable
card requires every asserted linguistic claim to be human-accepted or automatically
accepted under the applicable policy. Unsupported, stale, unresolved or failed checks
withhold affected cards, not unrelated supported cards. The optional review queue never
becomes mandatory homework or an implicit approve-all operation.

**Proposed technical contract:** version automatic decisions separately from human review.
Record evidence, producer/analyzer versions, prompt/checker versions, effective acceptance
policy, stage results, alternatives and objections. Bind decisions and reusable results to
the relevant source content, extraction, task, language and configuration. Changes that
affect correctness invalidate reuse; a stale success cannot authorize a new answer. Existing
human decisions remain human decisions. Define explicit schema upgrades or adapters before
using automatic decisions with the strict deck/corpus claim readers; do not overload a
`reviewer` string or the current annotation-write `auto` action to disguise automation.

Acceptance: a plausible deck entry with agreeing checks can become an exportable card
without human acceptance. Contradictory evidence, a matching pair of answers with an open
objection, an unsupported explanation, malformed model output and stale checks must not.
Capture the blind check's actual input to prove the first answer was not supplied. Human
and automatic acceptance remain separately inspectable after export and regeneration.

Track invalidation against previous export receipts: list affected semantic card/note
identities and the reason when source/checker changes or policy withdrawal makes installed
content ineligible. Omitting a row from a later CSV neither removes the old assertion nor
updates its old acceptance badge in Anki. Provide an explicit manual-resolution handoff or
a supported retained-field managed plan; unsupported lifecycle operations remain blocked.
Do not claim automatic suspension/retirement through CSV or bring direct integration
forward from v0.6.0. Reporting affected cards does not itself write to Anki.

Acceptance: import an automatically accepted card, invalidate its evidence or disable its
policy, and regenerate. The affected installed identity appears in the handoff with the
required manual action; new exports do not assert its old acceptance. Verify the chosen
supported resolution path without deleting history or silently changing scheduling.

### CLI Orchestration And Provider Boundaries

Provide one CLI entry point configured by a profile to ingest inputs, analyze, propose,
counter-check, decide, select and produce export files plus a report. Each stage remains
separately inspectable and usable. CLI orchestration may invoke optional provider adapters;
this supersedes the earlier v0.5.0 proposal to keep all provider calls outside the CLI.
Keep provider-independent validation and deterministic rendering outside those adapters.
LLM-off operation remains available for supported library/rule-backed or human-reviewed
inputs; it need not provide the same enrichment coverage as LLM-enabled operation.

Support explicitly configured local and hosted endpoints, separately for proposal and
counter-check. No mandatory hosted service, silent provider/model fallback, or automatic
network use in an offline command. Show the effective endpoints, data scope and configured
call/token limits before a network run; require explicit permission for hosted processing.
Do not log credentials. Treat source text and model outputs as untrusted data, never as
instructions granting tool, file or destination authority. Local-only processing requires
the entire processing path to be local; a loopback endpoint in an orb is not the user's
computer.

**Proposed technical contract:** persist stage results for validated reuse and resume with
finite request timeouts, retry/call limits and cancellation. Reuse valid completed work;
do not resubmit successful calls merely to resume. Interrupted or failed calls remain
failures/unknown outcomes until reconciled, not accepted checks. This is pipeline-local
recovery, not v0.7.0's portable project bundles and generation locks. Export remains the
existing file workflow; producing files never authorizes applying them to Anki.

Acceptance: interruption and resumption do not duplicate accepted artifacts or repeat
valid completed stages. A changed input or checker invalidates affected reuse. Endpoint
failure, missing configuration, exhausted limits and cancellation produce explicit report
outcomes and no silent fallback. Inspect hosted requests for declared data boundaries and
verify that LLM-off validation/export makes no provider calls.

### Outcome Reports And Anki Acceptance Metadata

Provide readable and versioned machine-readable reports with source-entry/passage links,
stage outcomes and representative examples. Distinguish at least:

- not generated: no supported recipe, form or suitable example;
- not processed/deferred: processing limits ended before work was attempted or completed;
- withheld: unresolved ambiguity, contradiction, missing support or stale assessment;
- processing failed: unavailable analyzer/model, malformed response or interrupted work;
- accepted but not selected: output-card budget or duplicate/diversity constraints;
- accepted and selected for export.

Keep stage counts and candidate/card counts distinct so one failed claim affecting several
cards is not misreported. Explain why a given material yields fewer cards without requiring
the user to inspect every candidate. Never count a provider outage as linguistic rejection.
Distinguish processing call/token limits from output-card selection budgets. Show attempted
versus deferred source work without inventing a count of undiscovered candidate exercises.
Acceptance: exhaust processing limits partway through input and resume; reports distinguish
deferred work from failed checks and accepted-but-unselected cards, preserving valid results.

On each answer, show a small human/automatic acceptance status and a collapsible evidence
section (German label: `Warum diese Antwort?`). Include the supporting basis and a concise
check summary; detailed traces stay in the report. No requirement to expose private reasoning
traces: structured findings and concise justifications suffice. The front stays focused on
the exercise. Optional confidence values are labeled as model estimates, not measured truth.

**Proposed technical contract:** add filterable, namespaced note tags for acceptance origin
and supporting source categories. Tags summarize the note, never pretend to be per-card
metadata; preserve per-card distinctions in managed data and the answer. Define conservative
mixed-note summaries, source/user tag ownership and migration before changing layouts. Reuse
stable identities and scheduling; no silent replacement of installed Anki templates.

Acceptance: report fixtures distinguish all outcome classes, mixed human/automatic siblings
retain their own status, and note tags do not label the whole note human-reviewed when only
one card is. Inspect German and English answers in light/dark Anki Desktop, with evidence
collapsed and expanded, and verify keyboard access. Preserve user-owned fields and tags.

### Curated Grammar And Mnemonics

Treat a mnemonic (a memory aid or *Eselsbrücke*) separately from the grammatical rule it
helps recall. A short *Merksatz* may itself state a rule; do not treat memorable wording as
a complete or universally applicable analysis. Define a human-readable, versioned format
for stable author-controlled item keys, precise rules, original mnemonic wording and
language, optional examples, caveats or exceptions, tags, and course/lecture provenance.
Record whether wording is quoted from course material or proposed by an agent, and retain
the source reference. Preserve German wordplay in its original language; an English
alternative is a separately reviewed variant, not an automatic translation.

The primary intake path is an agent extracting candidate rule–mnemonic pairs from lecture
notes into a draft file. Prefer course-supplied memory aids; when none is available, an
LLM may optionally suggest one as a clearly marked candidate. The curated intake validates
the draft, previews each item and its rendered cards, records explicit
per-item approval or rejection, and exports selected approved cards through the existing
deterministic file workflow. New items require human approval of both the rule–mnemonic
pair and the actual rendered cards before export; unchanged approvals need not be repeated.
Changes to the approved rule, mnemonic, caveats, or rendered card content require renewed
approval before export. Agent suggestions and unreviewed extracts never become
authoritative course material merely by appearing in the draft.

The automatic acceptance path for forms and controlled phrases does not bypass these human
approvals, including approval of the rendered curated cards. Both workflows share provenance
and export safety, not an interchangeable acceptance rule.

Offer selectable card recipes for applying a rule to a Latin example or grammatical
situation and for recalling/explaining a rule from its mnemonic. Application is the
default emphasis; mnemonic recall is opt-in so every item does not automatically multiply
cards. Other forward, reverse, or cloze recipes may be added where they have a distinct
learning objective. Preview must show the prompt, answer, mnemonic, explanation, caveats,
and provenance relevant to the chosen recipe. Selection and effective recipe choices are
saved for deterministic reruns.

Reuse the stable generated-note identity, note-field ownership, and CSV export contracts:
the source item key remains stable across wording corrections, while recipe and semantic
exercise keys distinguish card directions. Preserve the learner's personal notes on
updates. Reuse the v0.1.1 authored-note intake conventions where applicable, but do not
silently duplicate a free-form `qa` note as a curated mnemonic card. Previously imported
cards withdrawn after review require the shared ineligibility handoff: use supported managed
field updates where applicable and explicit manual resolution for unsupported lifecycle
effects. Omission from a later CSV does not delete or retire cards in Anki.

### Reviewed Syntax Roles

Moved to v0.5.5: corpus-based discovery and interpretation of sentence functions and
constructions, including both deck-driven example discovery and selected-passage exercises.
This does not remove v0.2.1's bounded controlled phrases or their pattern-specified roles.

### Semantic Color Layers

Extend morphology presentation in v0.5.0; v0.5.5 adds independent sentence-function and
construction classes. Theme profiles map semantics to colors plus non-color cues and
support light/dark modes and course-specific conventions. Explanatory markings default to
the answer; a front may neutrally highlight the target, but must not reveal its tested
analysis. Changing a theme never changes linguistic data, linguistic acceptance or note
identity. P50-1 must separately define presentation-change invalidation for curated
rendered-card approvals; linguistic acceptance cannot bypass those approvals.

### Domain-Specific Confidence Calibration

Evaluate acceptance behavior against independently judged samples, separately by claim type,
recipe and material characteristics. Include classical and biblical examples and varied
supported inputs, rather than restrict processing to a named corpus or course. Report
accepted errors, precision, coverage, withheld cases and failures; zero accepted items means
precision is not evaluable, not perfect. Agreement/self-confidence is not the reference
judgment. Keep development samples separate from held-out evaluation and retain known
counterexamples.

This revises the earlier calibration-only proposal: the defined evidence and blind-check
policy may authorize LLM-supported acceptance without a human decision on each claim.
Do not present uncalibrated numeric confidence as an observed success rate. Evaluation may
show insufficient reliability or coverage; narrow or disable the affected automatic path
and document that result instead of lowering standards silently or fabricating a score.
Material outside demonstrated evaluation coverage remains processable, with that limitation
reported and unresolved candidates withheld individually.

**Proposed technical contract:** before dependent implementation, specify a versioned check
matrix per claim class, comparison semantics for legitimate alternate translations/analyses,
an independently judged evaluation protocol, and explicit release pass/fail criteria.
Numeric thresholds and minimum sample sizes require evidence from the evaluation design
checkpoint; none were selected in the interview. Version and invalidate affected decisions
when an acceptance policy changes. Human-reviewed and auto-accepted remain distinct states.

## Open Technical Design Checkpoints

- P50-1 must resolve exact command/profile names, schemas and upgrades, semantic comparison
  rules, configured request limits, finite selection defaults and tag ownership. Existing
  strict formats are not assumed to accept new fields. These are proposals until reviewed.
- The evaluation owner must supply independently judged examples and measured release
  criteria. Automated fixture success alone cannot establish linguistic reliability.
- Native acceptance needs Linux Anki Desktop; real library/model checks need available
  resources and authorized endpoints. Unavailable evidence blocks the corresponding release
  claim, not an excuse to substitute mocked output. New consumer tasks remain unready while
  their design prerequisites are unresolved; no activation or release is authorized here.

## Caution

- Grammar conventions and terminology vary; profiles must name roles and sources.
- Incorrect study-card facts are more harmful than incomplete coverage.
- Course material may carry usage restrictions; provenance and permission to process or
  export it must be considered before agent extraction or sharing with a provider.
- A locally configured model endpoint alone does not guarantee local-only handling when
  the agent running extraction may itself transmit lecture notes elsewhere.
- Models and libraries can agree on the same error; counter-checks are not independent
  evidence merely because they use different prompts or models.
- Corpus/deck text and model output must not override pipeline policy or invoke tools.
- Arbitrary supported input does not imply equal accepted-card yield or demonstrated accuracy.
- Colors must not become the only carrier of meaning.

## Recommendation About LLM Support

Use the shared optional provider pipeline for analyses, form-appropriate translations and
explanations, with explicit local/hosted endpoints and a blind counter-check. Never use
self-reported model confidence alone as an automation threshold. Allow pipeline-managed
provider calls from the CLI without making ordinary validation/rendering network-dependent.
For lecture-note extraction, retain OpenAI-compatible local/hosted agent support and explicit
per-run hosted-processing permission; no hosted service is required. Curated mnemonic drafts
remain candidates requiring human approval even if the same model generated accepted form
analyses. No model output grants source/destination write authority.

## Explicitly Excluded

- Corpus-driven sentence-function/construction discovery and syntax coloring (v0.5.5).
- Fully automatic authoritative syntax analysis for arbitrary Latin or a zero-error claim.
- Automatic acceptance of generated mnemonics.
- Mandatory per-card human approval of otherwise automatically accepted forms/phrases.
- Self-reported confidence as the sole acceptance rule or a universal measured probability.
- Silent hosted processing, unbounded retry loops or provider fallback.
- Portable project bundles and general generation locks (v0.7.0).
- A GUI grammar editor.
- Exhaustive coverage of Latin grammar.
- Required direct Anki integration.
