# LatinitasCards v0.4.0

## Summary

Planned release. Generates study cards directly from normalized Latin corpora, without an
existing Anki deck. Four context and translation recipes draw only on reviewed sidecar
annotations. A ranked, sticky selection keeps the card count manageable, and its candidate
report keeps unselected candidates inspectable. A TEI adapter imports the Perseus/EpiDoc
CTS subset, and German and English are both supported generated-content languages. A
corpus-generation profile ties corpora, recipes, budgets and target language together;
it is not a project layout or bundle, which remain v0.7.0 scope.

v0.4.0 adds one Anki note type for corpus exercises. It changes existing deck-first
output only where a profile selects English: German output, note identities, layouts and
CSV columns of existing recipes stay byte-identical, and characterization goldens committed
before any refactor prove it. Corpus exercises reach Anki through the existing file
workflow: initial CSV export, manual note-type setup and import, explicit adoption, then
managed retained-slot and content-field updates. Structural creation and retirement
through CSV remain unsupported, as in v0.2.1.

Fixed Contracts is binding: agents do not amend this spec during the implementation loop
but file a blocked follow-up task for the maintainer. Where task notes disagree with this
spec, this spec takes precedence. v0.3.0 contracts (corpus records, identity and hashing,
annotation sidecars, claim sidecar v2, policy, CLI envelope, writer rules) apply unchanged
unless this spec names an additive change.

## Goals

- Generate useful cards directly from structured Latin corpora, each card backed by
  reviewed annotations with provenance.
- Support reading and translation practice with reference translations and
  self-assessment, never exact-string grading.
- Select a bounded, explainable set of exercises with a transparent, deterministic
  ranking that keeps earlier selections stable across reruns.
- Import scholarly TEI editions of classical Latin with their own citation systems.
- Produce German or English generated content on corpus and deck-first cards from an
  explicit language tag, while the CLI stays English.

## Potential Features

All five sections below are committed v0.4.0 release scope. Exact grammars, names, codes
and tables are in Fixed Contracts, and every Acceptance paragraph holds under them.

### Corpus-First Profiles And Exercise Identity

A `latinitas-corpus-profile` file names the corpora by `corpus_id` and sets the target
language, recipes with budgets, assigned reading, target lemmas, ranking weights, sentence
limits, morphology appearance and terminology, and the Anki note type and deck names. It
holds no file paths: commands take corpus paths explicitly and reject a corpus whose header
`corpus_id` the profile does not name. The profile is not a deck profile, not a policy file
and not a project bundle; it never enters claim fingerprints.

Each corpus exercise is one coherent learning object and one Anki note with one card. Its
note identity uses the v0.3.0-frozen `passage_id` as `source_identity`, the constant
`source_scope` `corpus-passage-v1`, and an `object_key` digesting the recipe, the context
unit, the exercise target and the target language. Targets are identified by folded
surface text and occurrence, never by review state, so accepting, withholding or adding
annotations never changes an exercise's identity. Two profiles over the same corpus and
language produce the same notes, and a target-language change produces new notes.
Wording, glosses, translations, lemmas, scores, review state, known lemmas, profile ID,
theme and terminology are not identity inputs.

A source correction keeps the passage ID, but it can change what a sentence index or an
occurrence points to. Each selection entry therefore records a context digest outside
identity. When the current context differs, the exercise becomes ineligible
(`context_changed`) until the learner either confirms the new context or deselects it.

Acceptance: `corpus-cards profile validate` accepts the documented example and rejects
unknown fields, floats, a language other than `de`/`en`, an unknown recipe, budgets or
limits outside their bounds and duplicate corpus IDs (exit 3). A reading range naming an
unknown work or ref exits 3 at `select` and `preview`. Independently specified identity
vectors in `tests/unit/identity_vectors_test.py` lock corpus exercise IDs for each recipe
and both languages. They are never regenerated from the production helper. Tests prove:

- The same exercise from two profiles has one ID, and `de` and `en` variants differ.
- A gloss, translation or theme change keeps the ID.
- With two tokens of one form, accepting the second token's facts before the first
  keeps both IDs unchanged.
- A correction that splits sentence 0 into two sentences leaves the selected exercise
  at index 2 ineligible (`context_changed`) instead of silently showing the old
  sentence 1. `--confirm-context` makes it eligible again.

Deck, phrase, form-parsing and authored identity vectors are unchanged.

### Context And Translation Recipes

Four recipes, each with one primary learning objective:

- `corpus_lexical_recognition`: a sentence with one highlighted word; the answer gives the
  reviewed contextual gloss, the lemma and, where reviewed, its grammatical features.
- `corpus_guided_analysis`: a sentence with one highlighted word; the answer gives that
  word's reviewed analysis, then the reviewed sentence translation.
- `corpus_phrase_translation`: a reviewed phrase of two to eight words inside one sentence,
  shown in its sentence; the answer gives the reference translation.
- `corpus_sentence_translation`: a whole sentence, or a whole passage of several sentences
  with one passage-level translation; the answer gives the reference translation and a
  self-assessment prompt.

Every card front is Latin-first. Reference translations carry a fixed guidance label
(string key `reference_guidance`) stating that other translations can be correct, and
translation cards ask the learner to compare meaning, not wording. The default context is
one sentence, and every answer keeps the full passage text and its citation.

A card is eligible only when every fact it asserts comes from a current annotation with
an `accepted` claim decision. Missing, stale, withheld, open, conflicting or unsupported
facts withhold the card with a reason. Lemmas and features come from `morphology`
annotations with tagset `latinitas-morph/1`, and glosses and translations from
`translation` annotations in the target language. There is no built-in dictionary and no
lexicon file: every fact is per occurrence. Enclitics (`-que`, `-ne`, `-ve`) stay in
their host token under `latin-tok/1`, so a fact on `virumque` describes the whole token.

Reference translations enter only as reviewed `translation` annotations through the
v0.3.0 patch, plan, approve and apply flow. LLM drafts carry `producer.kind: llm` and a
named model. `annotations import-translations` turns an aligned parallel corpus into such
a patch. The parallel corpus is a normalized corpus in the target language whose
`native_ref`s match the Latin corpus, for example a plain-text file normalized with the
same `--citation-template` labels. The command writes only a patch, never a sidecar or
claim decision.

Acceptance: fixture corpora with reviewed annotations render each recipe in German and
English, and previews show complete prompts, answers, citations, the full passage and
review state. Withholding is tested with its documented reason for each of:

- missing, stale, withheld, open, unsupported and conflicting facts;
- a gloss in the wrong language;
- a non-`latinitas-morph/1` tagset;
- a feature value outside the controlled vocabulary;
- a guided-analysis target without features;
- a phrase span equal to or crossing its sentence (reason `invalid_span`).

Every translation card shows the `reference_guidance` string, and no code compares
translation strings for grading. `import-translations` produces a patch that plans,
approves and applies through the v0.3.0 commands with full provenance. It reports
unmatched refs on both sides. A parallel corpus whose header language does not match
`--language`, or is Latin, is rejected. Applying the patch alone makes no card eligible
until `claims record` accepts the translations. No test imports CLTK, Stanza or an LLM
client.

### Ranked Card Budgets

`corpus-cards select` enumerates eligible candidates for the profile's recipes, scores
them with the fixed rule `latin-rank/1`, and updates a `latinitas-corpus-selection` file.
Factors are integers and their weights come from the profile: assigned reading, target
lemmas, a new-word bonus for the tested word, sentence length, unknown-word count against
an optional known-lemma input, and review coverage (the share of word tokens with
accepted morphology). For the two single-word recipes, the target and new-word factors
describe the highlighted word, so profile targets and known lemmas steer which word in a
sentence is tested. Near-duplicate
suppression and per-lemma caps keep exercises diverse. Annotation `confidence` is never a
ranking factor; it remains provenance only until calibration arrives in v0.5.0.

Selection is sticky. Reruns keep previously selected exercises, including ones that have
become ineligible, and only fill free budget. Explicit `corpus-cards deselect` with a
reason moves an exercise out. Deselected exercises are never re-selected automatically,
and `--restore` undoes a deselect. Every run writes a `latinitas-corpus-candidates` report
listing every candidate, selected or not, with its score, factor contributions and
outcome. A learner never needs to review every candidate.

The optional known-lemma input reads the lexical entry field of a confirmed deck profile's
source. It affects only the new-word and unknown-word factors, the `max_unknown` filter and
an informational deck link (matching deck source identities) in the candidate report and
preview. It never changes identity, eligibility, card fields or deck files.

Acceptance: a hand-computed fixture pins every factor, weight, score, tie-break, outcome
and the precedence of exclusion reasons. Budgets per recipe, per work and per run are each
exercised at and just above their limit. The per-run test starts from more sticky
selections than `per_run`, so the two readings of the run budget differ. A rerun with new
accepted annotations keeps every earlier selection and adds only up to the free budget.
A newly ineligible selection stays selected, is reported, and still occupies its recipe
and work budget slots. Deselect then rerun never re-selects; `--restore` does.

Near-duplicate and per-lemma tests use asymmetric inputs where wrong multiset arithmetic
gives a different selection. Changing `confidence` values changes no score. The
known-lemma input changes new-word and unknown-word values and the report's deck links,
and nothing else; with it absent, every word counts as unknown and new. In a sentence
containing a target lemma, the lexical exercise highlights the target word even when that
word neither comes first nor has the lowest `latinitas_id`. Two corpora with identical passage orders produce the same
selection whatever the `--corpus` argument order. `select` gives byte-identical selection
and report files in two subprocess runs with different working directory, `TZ`, locale
and `PYTHONHASHSEED`.

### TEI XML Adapter

`corpus normalize --adapter tei` imports one TEI P5 file in the Perseus/EpiDoc CTS style
into one corpus with one work. Citations come from nested
`div[@type="textpart"][@subtype][@n]` elements and, for verse, `l[@n]`, and the `@subtype`
values become citation units. The `@subtype` path is authoritative: `refsDecl` labels that
disagree with it only warn, because real Perseus files often mislabel them. The header
supplies edition, publisher, licence and work title, and a `--descriptor` file overrides
them with a warning. Notes, headings, apparatus readings and editorial alternatives
inside `choice` leave canonical `text` but stay in the passage record. Recognised inline
and editorial markup keeps its text and is recorded as spans. An unknown element fails
with names and counts unless `--allow-unknown` keeps it in `source_extra`. XML is
untrusted and uses the v0.3.0 hardening (no DTD, entities or external entities; 64 MiB;
depth 64), shared with the USFX adapter rather than copied.

Milestone-based citation, drama (`sp`, `speaker`, `stage`), multiple editions per file,
translation divisions, other TEI customizations and network download are out of scope. A
translation division is skipped with a warning; it is not a parallel corpus. Adding the
adapter goes through an explicit adapter registry for `corpus normalize`, and USFX and
plain-text outputs stay byte-identical.

Acceptance: synthetic fixtures reproduce the real Perseus skeletons and round-trip to
committed golden corpora that pass `corpus validate`:

- Prose: book/chapter/section textparts with `section/p`, a standalone `reg` and `sic`
  as in Cicero and Caesar, `ex` inside `expan`, `emph` and `desc`.
- Verse: book/line with `l` both directly in the textpart and inside `lg`, a `note`
  between lines containing an `l` with `@n` and a `del` (as in the Metamorphoses), and
  one line consisting only of `del`.

Fixtures also cover:

- citations: non-numeric `@n` (`pr`, `3a`, `62b`) and components needing
  percent-encoding; a duplicate citation (exit 3, `duplicate_source_ref`); inconsistent
  unit paths (exit 3); a `cRefPattern` label mismatch, such as the Aeneid's `line, Book`
  (warning only);
- markup: `note`, `head`, `app`/`lem`/`rdg`, `choice` with `sic`/`corr`, `abbr`/`expan`
  and `orig`/`reg`, `del`, `add`, `supplied`, `gap` (warning), and `lb`/`pb`/`milestone`;
- an unknown element (failure, then `--allow-unknown`) and a drama `sp` (unknown element);
- structure: a translation division (skipped with a warning), a non-Latin edition, a
  missing edition division and the wrong namespace;
- unsafe inputs: DTD, entity, depth-65 and over-64-MiB files (exit 3).

Header metadata maps to the documented fields, including the Perseus
`biblStruct/monogr/title` and filename-`idno` fallbacks, and a descriptor override warns.
Segmentation, annotations and recipes work on a TEI corpus as on USFX and plain text.
Existing USFX, plain-text and legacy goldens and the full-Vulgate oracle stay
byte-identical.

### German And English Output

The target language is an explicit BCP 47 tag whose primary subtag is `de` or `en`. It is
the deck profile's `language_tag` and the corpus profile's `target_language`, and German
remains the default for new profiles. English covers terminology in `user` mode, fixed
generated-card strings on principal-part, phrase, form-parsing and corpus cards, reviewed
form translations and phrase references. Latin terminology mode and Latin-first prompts
are unchanged, and the CLI control language stays English. The vocabulary is keyed by
language, so later languages are extensions, not rewrites. Rejection of other languages is
limited to the cases in Fixed Contracts **Languages**; existing valid deck profiles keep
working.

Deck-first note identities, card keys, slots, layouts and CSV columns do not change with
language. Deck claim fingerprints bind the whole deck profile except `morphology`,
`language_tag` included, so switching an existing deck profile to English makes every
reviewed claim of that profile stale, not only translations. All of them need new
reviewed decisions before cards become eligible again. This is the existing v0.2.1
fingerprint contract, kept unchanged. Applying the switch to imported notes is a managed
retained-slot payload update with renewed approval.

Acceptance: every terminology feature, value and role label renders in Latin, German and
English, and every fixed card string renders in German and English. Tests prove the
English tables have an entry for every German key. German goldens for principal-part, phrase and form-parsing preview
and CSV output stay byte-identical, including a profile whose `language_tag` is neither
`de` nor `en` with Latin terminology. An English profile renders English fixed strings and
terminology with unchanged note IDs, card keys and columns. A German reviewed form
translation or phrase reference never appears on an English card. Switching a fixture
deck profile from `de` to `en` makes its claims stale, as the test asserts. A `fr` tag is
rejected for terminology `user` mode, form translations, phrase references and corpus
profiles with the documented diagnostic.

## Fixed Contracts

**Terms.** A corpus profile is a `latinitas-corpus-profile` file. A candidate is an
exercise the profile's recipes could produce from current corpora and annotations, eligible
or not. A unit is the exercise's context: a sentence of a passage's current `latin-seg/1`
segmentation, or a whole passage. A target is what the exercise tests inside its unit. An
exercise is selected when listed in the selection file's `selected` list. A fact is an
annotation value a card asserts. Accepted means a current claim decision with status
`accepted` on a current (not stale, orphaned, superseded or retracted) annotation, per
v0.3.0. Word tokens are `latin-tok/1` tokens of kind `word`. `fold` is `latin-fold/1`.

**Corpus profile.** `latinitas-corpus-profile` version 1, strict, canonical JSON, no
floats or unknown fields:

- `profile_id` (`^[a-z0-9][a-z0-9-]{1,62}$`); `corpora`: non-empty sorted unique list of
  `corpus_id`s; `target_language`: BCP 47, primary subtag `de` or `en`, default `de`;
  `note_type` and `deck`: non-empty strings.
- `recipes`: non-empty list of `{recipe, budget}`, `budget` an integer 1 to 1000, each
  recipe at most once. Recipe names are the four above.
- `budgets`: `{per_run, per_work}`, integers 1 to 1000, defaults 50 and 200.
- `reading`: optional list of `{corpus_id, work, from, to}` (strings; `corpus_id` must be
  listed in `corpora`). At use, `from` and `to` must be `native_ref`s of passages in that
  work with `from` not after `to` in passage `order`; otherwise `select` and `preview`
  exit 3 (`invalid_reading`). A range is inclusive by `order` within its work.
  `reading_only` (boolean, default false) excludes candidates outside every range.
- `targets`: optional sorted unique list of lemmas, compared after `fold`.
- `limits`: `{min_tokens, max_tokens, ideal_tokens, max_unknown}`, integers with
  `1 <= min_tokens <= ideal_tokens <= max_tokens <= 200`; defaults `min_tokens` 3,
  `ideal_tokens` 12, `max_tokens` 30 and `max_unknown` null (no limit; otherwise 0 to
  200). These count word tokens of the unit. Without a known-lemma input every word is
  unknown, so a small `max_unknown` can filter every candidate.
- `weights`: integers -100 to 100 per factor: `reading` 40, `target` 30, `novelty` 20,
  `length` 10, `unknown` 20 and `coverage` 10 by default. `length` and `unknown` values are
  non-positive, so positive weights penalize.
- `morphology`: the deck profile's `MorphologySettings` shape (theme, appearance,
  comparison, terminology), with the same defaults and validation.

`corpus-cards profile validate FILE` is read-only and checks only the file. The profile
digest is the structured digest of the profile. A command given a corpus whose
`corpus_id` the profile does not list, or missing a listed corpus, exits 3
(`profile_mismatch`).

**`latinitas-morph/1`.** A `morphology` annotation value with `tagset:
"latinitas-morph/1"` has:

- `lemma`: a non-empty NFC string;
- `pos`: one of `noun`, `verb`, `adjective`, `pronoun`, `adverb`, `preposition`,
  `conjunction`, `particle`, `numeral` or `interjection`;
- optional `features`: a map from `case`, `number`, `gender`, `person`, `tense`, `mood`,
  `voice`, `degree` and `verbform` to controlled values.

The controlled values are those in `terminology.py`, except that `mood` takes only the
finite values `indicativus`, `coniunctivus` and `imperativus`. Two features are added:
`degree` (`positivus`, `comparativus`, `superlativus`) and `verbform` for non-finite forms
(`infinitivus`, `participium`, `gerundium`, `gerundivum`, `supinum`). Each value maps to
`la`, `de` and `en`. A non-finite `mood` value is unsupported, so each form has one
encoding.

v0.3.0 annotation validation is unchanged. `corpus-cards` validates this shape only when
it consumes a value. An invalid value or another tagset makes the fact unsupported
(reason `unsupported_morphology`). The anchor must cover exactly one word token of the
current segmentation.

**Fact rules.**

- A spanned fact must carry the `segmentation_id` of the passage's current segmentation
  record, and its span must equal the stated token or sentence span. A span-less
  translation needs only a current `passage_hash`; the current segmentation is still
  needed to form units.
- Translation facts must be in the profile's target language (primary subtag match).
- After the language filter, two or more accepted facts that serve the same requirement
  and disagree in value withhold every card needing it (reason `conflicting_facts`). This
  covers facts on the same anchor and, for a one-sentence passage, a sentence-span
  translation versus a span-less one. Identical accepted values count once.
- Sentences with `continued` or `continues` set are fragments of a sentence spanning
  passages. Guided analysis and sentence translation never use them as units (outcome
  `filtered:fragment`). Lexical recognition and phrase translation may, showing the
  fragment as the unit.

**Recipes.**

| Recipe | Unit | Target | Required accepted facts |
| --- | --- | --- | --- |
| `corpus_lexical_recognition` | sentence | one word token | morphology and a translation anchored to exactly that token |
| `corpus_guided_analysis` | sentence | one word token | morphology with at least one feature on that token, and a translation of the unit |
| `corpus_phrase_translation` | sentence | 2-8 consecutive word tokens, a proper sub-span of the sentence, from the first word token's start to the last word token's end | a translation anchored to exactly that span |
| `corpus_sentence_translation` | sentence or passage | none | a translation of the unit |

A translation of a sentence unit is anchored to exactly the sentence span. For a passage
whose segmentation has exactly one sentence, a span-less translation is also that
sentence's translation. A passage unit exists only for a span-less translation on a passage
of two or more sentences with at most `max_tokens` word tokens.

Candidates are generated per occurrence:

- Lexical recognition and guided analysis: one candidate per word token that has at least
  one current morphology annotation, accepted or not, so they appear in the report.
- Phrase translation: one candidate per current spanned translation annotation whose
  span is not exactly a sentence span. One that is not a qualifying span is ineligible
  (reason `invalid_span`) and has no identity beyond its `annotation_id` in the report.
- Sentence translation: one candidate per unit with a current translation.

Eligibility then applies the table.

**Exercise identity.**

- `source_identity = passage_id`; `source_scope = "corpus-passage-v1"`;
  `object_key = "corpus-exercise-v1-" + hex(sha256(canonical JSON))` of `{recipe,
  target_language, unit, target}`, where `target_language` is the lowercased primary
  subtag.
- `unit` is `{"kind": "sentence", "index": i}` (zero-based sentence index in the passage's
  current segmentation) or `{"kind": "passage"}`.
- `target` for lexical recognition and guided analysis is `{"form": F, "occurrence": k}`.
  `F` is the `fold` of the token's surface text. `k` is the zero-based count of earlier
  word tokens in the unit whose folded surface is also `F`, counted over all word tokens
  regardless of annotations. Phrase translation uses `{"form": F, "occurrence": k}` with
  `F` the space-joined folded surfaces of the span's word tokens, and `k` counted over
  all earlier windows of the same number of word tokens in the unit with the same `F`;
punctuation tokens are ignored in windows. Sentence
  translation uses null.
- `LatinitasID = derive_latinitas_id(source_identity, object_key, source_scope=...)`;
  the card semantic key is `<recipe>:context`.
- `context_digest` is the structured digest of `{unit_text, target_text}`: the `fold` of
  the unit's text and of the target span's text (null for no target). It is stored per
  selected entry, never in identity.
- At each `select`, `preview`, `export`, `inspect` and `plan`, a selected exercise whose
  key no longer arises is ineligible with reason `target_missing`. If it arises with a
  different `context_digest`, it is ineligible with reason `context_changed`.
  `select --confirm-context LATINITAS_ID` stores the current digest after explicit
  review. Identity is never transferred to a different key.

**`latin-rank/1`.** Factor values for an eligible candidate, all integers:

- `reading`: 1 if the passage lies in a reading range, else 0.
- `target`: for lexical recognition and guided analysis, 1 if the target token's folded
  accepted lemma is in `targets`, else 0; for the other recipes, the number of distinct
  folded target lemmas among the unit's accepted lemmas, capped at 3.
- `novelty`: for lexical recognition and guided analysis, 1 if the target token's folded
  accepted lemma is not a known lemma, else 0; 0 for the other recipes.
- `length`: `-abs(w - ideal_tokens)`, where `w` is the unit's word-token count.
- `unknown`: `-u`, where `u` counts the unit's word tokens, other than a single-word
  target, whose accepted folded lemma is not a known lemma, plus such tokens without an
  accepted lemma. With no known-lemma input, `u` is `w` minus the single-word target,
  if any.
- `coverage`: `(100 * word tokens with accepted morphology) // w`.

`score = sum(weight * value)`. Ineligible candidates get no factor values or score.

Order:

1. Filters run before ranking, in this order: `filtered:fragment`, `filtered:length`
   (`w` outside `min_tokens..max_tokens`), `filtered:unknown` (`u > max_unknown`) and
   `filtered:reading` (`reading_only`). Filters never remove an existing selection.
2. Ranking order is score descending, then `(corpus_id, passage order)`, then unit index
   (passage units after sentence units), then the target's first word-token index in the
   unit (null last), then `latinitas_id`.
3. Existing selections are placed first, as outcome `kept`. Then each remaining eligible
   candidate in ranking order is checked against these exclusions in this order and
   takes the first that applies:
   - `deselected`;
   - `budget:recipe`;
   - `budget:work`;
   - `budget:run`;
   - `near_duplicate`;
   - `per_lemma`.

   If none applies, the candidate is `selected`. Recipe and work budgets count kept
   and newly selected exercises. `budget:run` counts only exercises newly selected in
   this run.

`near_duplicate` compares a candidate with each kept or selected exercise of the same
recipe using folded word-token multisets. `A` and `B` are the unit's tokens, or the span's
tokens for phrase translation. The test is `5 * |A ∩ B| >= 4 * |A ∪ B|` with multiset
intersection and union. Lexical recognition and guided analysis therefore get at most one
exercise per sentence and recipe, by design. A `target_missing` selection has no multiset
and is never compared.

`per_lemma` applies to lexical recognition only. It excludes a candidate whose folded
accepted lemma already has a kept or selected lexical-recognition exercise. Lemmas that
differ only in macrons share one folded lemma, so reviewers distinguish homographs by
lemma spelling, for example `liber (1)` and `liber (2)`.

Known lemmas are the folded lemmas from the known-lemma input. Before an accepted lemma is
compared with known lemmas or `targets`, a trailing homograph suffix ` (n)` (a space and
digits in parentheses) is removed; the suffix still separates `per_lemma` buckets.

**Selection and report.**

- `latinitas-corpus-selection` version 1:
  - top level: `profile_id`, `target_language`, and `runs` (an integer, incremented by
    each run of `select`, `deselect` or `--confirm-context` that changes the file);
  - `selected: [{latinitas_id, object_key, recipe, passage_id, unit, target,
    context_digest, run}]`, sorted by `latinitas_id`;
  - `deselected`: the full selected entry plus `reason`, with `run` set to the
    deselecting run, sorted by `latinitas_id`.

  `run` is the value of `runs` after the changing run. The file holds no clock values,
  paths or scores. `--restore` moves an entry back to `selected` with its stored context
  digest and `run` set to the restoring run.
- A selection whose `profile_id` or `target_language` differs from the profile exits 4
  (`binding_drift`). `select` never drops a selected exercise; it reports each one's
  status (`eligible`, or ineligible with reason).
- `latinitas-corpus-candidates` version 1 records:
  - the profile digest, corpus header digests, sidecar and claims file digests (null when
    absent), and the known-lemma source and profile digests (or null);
  - the rule `latin-rank/1` and the selection's `runs` after this run;
  - every candidate: `object_key`, `latinitas_id`, recipe, `passage_id`, unit, target,
    eligibility with reasons, factor values, weighted contributions, score, and outcome
    (`kept`, `selected`, a filter or an exclusion code).

  Candidates are sorted in ranking order, with ineligible candidates last by
  `latinitas_id`, then `invalid_span` entries by `annotation_id`. Every selected entry
  appears, including one with `target_missing`, as outcome `kept` with its reason.
- Outcome and withholding reasons form one closed vocabulary, defined in the selection
  and candidates schemas and in the documentation. They are report values, not CLI
  diagnostics:
  - filters and exclusions: `filtered:fragment`, `filtered:length`, `filtered:unknown`,
    `filtered:reading`, `deselected`, `budget:recipe`, `budget:work`, `budget:run`,
    `near_duplicate`, `per_lemma`;
  - fact states: `missing_fact`, `stale_fact`, `open_fact`, `withheld_fact`,
    `conflicting_facts`, `unsupported_morphology`, `wrong_language`,
    `no_features`, `invalid_span`;
  - selection states: `target_missing`, `context_changed`.
- `select` always writes the report. It replaces the selection only when the selection's
  bytes change, so a rerun with unchanged inputs is a byte-identical no-op. Both writers
  follow v0.3.0 writer rules: `<file>.lock` nonblocking (`busy`, exit 4), alias rejection
  against every input and lock, a same-directory temp file, `fsync` and `os.replace`. The
  selection is replaced last; a failure before that leaves the old selection, and an
  orphan report is never read as state.

**Known-lemma input.** `--known-lemmas PROFILE` with `--known-lemmas-source SOURCE` loads
any supported confirmed deck profile and its source read-only. For each record it takes
the lexical entry field, strips HTML with the existing source-text helper, takes the first
whitespace-delimited word, strips leading and trailing non-word characters, and folds it.
Records it cannot read are reported and skipped. The candidate report and preview list
the matching deck source identities for the target lemma as provenance only; no card field
holds them.

**Parallel translations.** `annotations import-translations CORPUS --parallel PARALLEL
--language TAG --producer-kind human|agent|llm --producer-name N --producer-version V
--output PATCH [--timestamp T]` builds the patch as follows:

- `PARALLEL` is a normalized corpus whose header `language` primary subtag equals that of
  `--language` and is not `la`; otherwise the command exits 3 (`unsupported_language`).
- For each Latin passage whose `native_ref` occurs in `PARALLEL`, it emits one `add`
  operation with a span-less `translation` annotation `{language: TAG, text}`. The text is
  the canonical text of the parallel passage, and the operation carries the given
  producer and the Latin passage's `passage_hash`.
- Latin passages without a match warn (`unmatched_translation`), as do parallel refs
  without a Latin passage (`unmatched_parallel`).
- Output is a `latinitas-annotation-patch`. An existing identical output is a no-op, and
  a different one exits 3 (`exists`). Timestamp rules follow v0.3.0.

**Note type `corpus-v1`.** A separate note type (default name `Latinitas Corpus Context
v1`), registered as managed layout `corpus-v1` in `managed_layouts.known_layouts()`.
Its fields, in order:

- `LatinitasID`;
- `Latin`: the unit as HTML, with the target wrapped in `<span class="corpus-target">`;
- `Citation`: `citation.display` plus `corpus_id`;
- `Passage`: the full passage text;
- `Language`: the target tag;
- `Source ID` (`passage_id`), `Source Scope`, `Source Kind` (`corpus`) and
  `Source Location` (`object_key`);
- `Note Schema` (`corpus-v1`), `Generator` (`corpus-v1`) and `Profile` (the exporting
  `profile_id`);
- four slot triples, ordinals 0 to 3: `CorpusLexicalEnabled/Prompt/Answer`,
  `CorpusAnalysisEnabled/...`, `CorpusPhraseEnabled/...` and
  `CorpusSentenceEnabled/...`;
- `Personal Notes`: user-owned and never exported.

Tags use the existing transport directive. Exactly one slot is enabled per note, and only
when its exercise is eligible. All text is escaped through the existing helpers and checked
by `validate_managed_controls`.

`ManagedLayout` gains a per-layout set of updatable content fields, used by planning,
approval and application alike (today `managed_plans.py` and `destination_state.py` each
hard-code `CONTENT_FIELDS`). For `corpus-v1` it holds `Latin`, `Citation` and `Passage`.
Existing layouts keep exactly today's set and plans. `Profile` records the first
exporting profile: plan proposals copy it from the anchored destination note, and
`inspect --check` ignores it, so two profiles sharing a note never contend. A corrected
and re-reviewed passage's `Passage` update must plan, approve and apply end to end.

`corpus-v1` has its own templates, guarded on each card's `Enabled` field, and its own
stylesheet `CORPUS_CARD_CSS` with `CORPUS_STYLE_VERSION = 1`. The stylesheet uses the
reference appearance class contract (`light`, `dark`, `auto` and the night-mode classes).
`REFERENCE_CARD_CSS` and `REFERENCE_STYLE_VERSION` stay unchanged, so principal-part
preview output and phrase package style checks stay byte-identical.

**Languages.**

- Generated-card text comes from one table keyed by `(string_key, language)`, with
  entries for `de` and `en`. Terminology tables map each canonical value to `la`, `de`
  and `en`.
- A primary subtag of `en` selects the English table. Any other subtag renders the
  German table, exactly as today, so existing deck profiles with other tags keep their
  output.
- Rejection applies only where a target language is asserted: a deck profile with
  `user` terminology, a form-translation or phrase-reference claim, or a corpus profile
  whose primary subtag is not `de` or `en`. These fail with the existing profile or claim
  validation error, which names the supported tags.
- `phrase_recipes.Reference.language`, form-translation claims and corpus translations
  accept `de` and `en`; the German claim fingerprints stay unchanged.
- German strings move into the table unchanged, and German output stays byte-identical
  to the goldens.

**TEI subset (`tei/1`, profile `epidoc-cts/1`).**

- Input: one TEI P5 file in namespace `http://www.tei-c.org/ns/1.0`. The root `TEI` holds
  `teiHeader` and `text/body`. Parsing uses the shared hardened expat reader with
  namespace processing. Elements in other namespaces are unknown, and processing
  instructions are ignored.
- Edition: there must be exactly one `body/div[@type="edition"]`, with `xml:lang` `lat` or
  `la`. A missing edition exits 3 (`invalid_structure`), and another language exits 3
  (`unsupported_language`). Other `body/div` types are skipped with a `skipped_division`
  warning naming the types.
- Passages:
  - A passage `l` is an `l[@n]` not inside `note`, `rdg`, `sic`, `abbr`, `orig` or `del`.
    A passage is a passage `l`, or a deepest `div[@type="textpart"]` that contains no
    passage `l`.
  - A textpart containing a passage `l` is not itself a passage. Its `head` elements
    attach to the next line. A `note`, `del`, `rdg`, `milestone`, `pb` or `lb` between
    lines, including inside or between `lg` groups, attaches to the preceding line, or to the next line if none precedes. Any
    other non-whitespace text outside its lines exits 3 (`invalid_structure`).
  - `lg` groups lines transparently.
  - An `l` without `@n`, or any `l` inside `note`, `rdg`, `sic`, `abbr`, `orig` or `del`,
    is flattened text, never a passage.
  - A passage whose canonical text is empty (for example a line consisting only of
    `del`) is omitted with a `skipped_empty_passage` warning naming its ref.
- Citation:
  - Every passage's path of `@subtype` values (plus `line` for an `l`) must be the same
    across the file, and every ancestor textpart needs `@subtype` and `@n`; otherwise the
    command exits 3 (`invalid_structure`).
  - `native_ref` joins the encoded `@n` components, using the v0.3.0 encoding.
  - The citation scheme is `tei-cts`, with parts from the `@subtype` values; the display
    joins the raw values with `.`.
  - A duplicate `native_ref` exits 3 (`duplicate_source_ref`).
  - When `encodingDesc/refsDecl[@n="CTS"]/cRefPattern/@n` values exist and, read deepest
    first, differ case-insensitively from the unit path, the command warns
    `citation_mismatch` and keeps the `@subtype` path.
- Work: `work` is `--work ID` (`^[A-Za-z0-9._-]{1,64}$`), else the textgroup and work
  part of a CTS URN in the edition `@n` (`urn:cts:latinLit:phi0448.phi001...` becomes
  `phi0448.phi001`), else the first two dot components of
  `publicationStmt/idno[@type="filename"]` when they match
  `^[a-z]+[0-9]+\.[a-z]+[0-9]+$`, else `corpus_id`. `work.title` is the first
  `titleStmt/title`.
- Header to descriptor fields, each null when absent:
  - `edition`: `editionStmt/edition`, else the first `sourceDesc//title`;
  - `publisher`: `publicationStmt/publisher`;
  - `url`: `publicationStmt/idno[@type="URI"]`;
  - `license`: `publicationStmt/availability/licence`, its `@target`, else its text.

  The corpus `title` comes from `titleStmt/title`. A `--descriptor` value overrides the
  header and warns `descriptor_override` for each differing field.
- Text and markup:
  - Canonical text concatenates text nodes per v0.3.0 `text_canon: 1`.
  - `note`, `bibl` and `desc` become `notes` of kind `note`, and `head` becomes `headings`,
    attached to the next passage.
  - `app` keeps `lem`; each `rdg` becomes a `notes` entry of kind `variant`. Inside
    `choice`, the `corr`, `expan` or `reg` text is kept, and `sic`, `abbr` or `orig`
    become `notes` of kind `variant`. `del` text leaves `text` as kind `variant`.
  - Outside `choice`, `reg`, `corr`, `expan`, `sic`, `abbr` and `orig` keep their text
    and record spans.
  - These keep their text and record `source_markup` spans with attributes: `p`, `ab`,
    `add`, `supplied`, `unclear`, `hi`, `emph`, `ex`, `q`, `quote`, `foreign`, `name`,
    `persName`, `placeName`, `geogName`, `num`, `date`, `w`, `seg`, `label`, `title`,
    `cit`.
  - `lb`, `pb`, `cb` and `milestone` record empty spans. `gap` records an empty span and
    warns `gap_in_text`.
  - Any other element fails with names and counts (exit 3, `unknown_element`), unless
    `--allow-unknown` keeps it in `source_extra`.
- Schema change: the v1 corpus header `adapter` gains `tei/1`, and passage `notes.kind`
  gains `note` and `variant`. Corpus `version` stays 1, and USFX and plain-text outputs
  are byte-identical. v0.3.0 releases reject TEI corpora as invalid; this is documented
  and accepted.
- `--manifest`, approval flags and `--citation-template` with `--adapter tei` exit 2. TEI
  citations are source-native, so no manifest is needed.

**Commands.** A new contract group `corpus-cards` joins the v0.3.0 CLI contract
(envelope, exit codes, diagnostic registry, matrix and schemas), and its commands never
prompt. Its matrix rows go in `CONTRACT_EXIT_CASES`, and the group is added to the walk
tuple in `tests/unit/cli_contract_matrix_test.py`. Corpus sidecar and claims paths use
the v0.3.0 defaults (`<corpus-stem>.annotations.jsonl` and `<corpus>.claims.json`). An
absent sidecar or claims file means no annotations or decisions.

- `corpus-cards profile validate PROFILE`
- `corpus-cards select PROFILE --corpus FILE... --selection FILE --report FILE
  [--known-lemmas PROFILE --known-lemmas-source SOURCE] [--confirm-context ID]...`
- `corpus-cards deselect SELECTION --exercise LATINITAS_ID... --reason TEXT [--restore]`
  writes only the selection. An ID in neither list exits 3 (`unknown_exercise`).
  Deselecting a deselected ID, or restoring a selected one, is a no-op.
- `corpus-cards preview PROFILE --corpus FILE... --selection FILE [--limit N]
  [--known-lemmas PROFILE --known-lemmas-source SOURCE]` is
  read-only (default 20, maximum 1000). For each selected exercise it shows the rendered
  prompt and answer as plain text, citation, status, withholding reasons, and the facts
  behind it with claim status and producer.
- `corpus-cards export PROFILE --corpus FILE... --selection FILE --output CSV` is initial
  creation only. It writes the eligible selected exercises through `serialize_anki_csv`
  and `commit_csv_artifacts`. An existing output is never overwritten (`exists`, exit 3),
  and an export with no eligible exercise exits 1 (`nothing_to_export`).
- `corpus-cards inspect PROFILE --corpus FILE... --selection FILE [--check CSV]` is
  read-only. The check mode compares an exported CSV with the current rendering. It
  reports unreviewed or stale asserted content, drifted fields, and identity or slot
  mismatches (`card_drift`), exiting 1 on any.
- `corpus-cards plan PROFILE --corpus FILE... --selection FILE SNAPSHOT STATE --output
  REQUEST` writes a `managed plan` request, as `phrases plan` does:
  - Eligible selected exercises become `approved` proposals; ineligible ones that are
    anchored become `withheld` proposals carrying the anchored destination fields, which
    means no change. Ineligible exercises without an anchor are omitted and reported as
    not imported.
  - Anchored notes with `Source Kind` `corpus` whose `LatinitasID` is in this selection's
    `deselected` list become `retire` proposals. The CSV transport reports them as
    blocked structural effects needing manual resolution. No other note is ever proposed
    for retirement.
  - Eligible selected exercises that are members of the bound managed set (the
    coherent-object membership recorded in managed state, as for `phrases plan`) but missing
    from the destination become `create` operations, which the transport reports as
    unsupported. Other unanchored exercises are reported as not imported.

  A target-language switch therefore uses a new selection file for the new language; the
  old notes are retired only by deselecting them in the old selection.

**Diagnostics.** New registry codes with exit classes, documented in
`docs/agent-cli-contract.md` and registered in `cli_contract.py`:

| Code | Exit class |
| --- | --- |
| `profile_mismatch`, `invalid_reading`, `unsupported_language`, `unknown_exercise` | 3 |
| `card_drift`, `nothing_to_export` | 1 |
| `citation_mismatch`, `skipped_division`, `skipped_empty_passage`, `descriptor_override`, `gap_in_text`, `unmatched_translation`, `unmatched_parallel` | 0 (warnings) |

The TEI adapter reuses `unknown_element`, `invalid_structure`, `duplicate_source_ref`,
`unsafe_xml`, `input_too_large` and `depth_exceeded` with adapter-neutral messages.
Existing codes keep their exit classes. JSON Schemas for `latinitas-corpus-profile`,
`latinitas-corpus-selection` and `latinitas-corpus-candidates`, plus the updated corpus
record schema, are committed under `docs/schemas/` with the drift test.

## Native Acceptance

v0.4.0 changes Anki-facing output, so the maintainer gate requires native evidence on
actual Linux Anki Desktop, using an isolated synthetic profile as in v0.2.1. The evidence
covers:

- the `corpus-v1` note type, set up manually from its templates and `CORPUS_CARD_CSS`;
- a CSV with all four recipes in German and English, imported, then re-imported as an
  update with first-field matching and `Personal Notes` unmapped;
- the front and answer of each card in `light`, `dark` and `auto`, with a light, night,
  light toggle;
- one English principal-part, phrase and form-parsing card each.

Browser previews and backend fixtures do not substitute for this evidence. AnkiMobile is
outside the gate and remains unverified; that is not a compatibility claim.

## Caution

- A ranked budget can hide useful candidates; the candidate report must stay complete and
  its reasons specific.
- Reference translations are not uniquely correct and are presented as guidance.
- TEI is a family of practices; the subset fails closed outside its documented elements,
  and real Perseus files may still surface unlisted elements.
- Per-occurrence facts cost one review per occurrence; agents may draft but never accept.
- Sticky selections that become ineligible keep their budget slots until deselected, so
  reports must make that visible.
- Switching a deck profile's language makes every reviewed claim of that profile stale.
- Without a known-lemma input every word counts as unknown, so a tight `max_unknown`
  can filter every candidate.
- A target-language switch on a corpus profile creates new notes. Retiring the old ones
  through CSV is a blocked plan needing manual resolution, not an automatic deletion.
- Verse lines usually yield sentence fragments, so guided analysis and sentence
  translation rarely apply to verse in v0.4.0; joining sentences across passages is
  future work.
- Folding strips macrons, so macron-only homographs need distinct lemma spellings.
- Parallel translations may carry licences separate from the Latin text, and provenance
  must name them.

## Recommendation About LLM Support

An LLM may draft glosses, analyses or translations only as an imported patch with
`producer.kind: llm` and a named model, under the v0.3.0 provenance, policy and review
contract. Drafts never make a card eligible without an accepted claim decision. Ranking is
deterministic and offline, LLM grading is not part of this release, and core commands need
no provider or model endpoint.

## Explicitly Excluded

- TEI customizations beyond the documented subset, milestone-based citation, drama
  markup, translation divisions as parallel input, and network download of sources.
- A built-in dictionary, a lexicon file or automatic lemmatization.
- Sentences joined across passages as one unit.
- Automatic syntax-role colouring, syntax annotation and confidence calibration (v0.5.0).
- Output languages other than German and English.
- Project layouts, bundles and lock files (v0.7.0); enriched corpus export (v0.6.0).
- Direct Anki integration, structural creation or retirement through CSV, and automatic
  grading of translations.
- Identity, layout or CSV-column changes to existing deck-first recipes.
