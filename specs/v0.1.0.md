# LatinitasCards v0.1.0

## Objective

Deliver the first useful, repeatable deck-enrichment workflow: inspect an existing Anki
deck, confirm how its lexical fields are structured, and generate principal-part recall
cards that can be imported repeatedly without creating duplicates.

The release is deck-first. It establishes identities and data contracts that later
versions can reuse for form parsing, color-coded grammar cards, corpus-first generation,
and optional direct Anki integration. The Vulgate remains the first bundled corpus and a
useful example, but it is not the product boundary.

## Context And Current State

The repository was retrofitted after a broader CLI had already been built. The existing
commands can inspect and split CSV/APKG inputs, annotate forms through CLTK with optional
Ollama disambiguation, and generate clozes from USFX, text, or parallel CSV corpora. These
capabilities remain available, but they do not yet form a coherent, safely updateable card
generation contract.

In particular, current generated APKG notes do not have identities suitable for repeated
generation: their GUID seed includes a newly allocated local note ID. The generalized
`cloze` command and the older `preview`/`generate` path also use different selection
engines. Difficulty filtering, parallel translations, module extraction, and generalized
corpus generation are therefore not v0.1.0 release gates.

The first existing deck used to verify this release is an acceptance fixture, not a
product-specific assumption. Deck field names, note types, languages, and separators must
be described by a reusable profile rather than hard-coded.

This revision replaces the unreleased per-exercise note model. Completed tasks describe
the implementation and evidence at their completion, not implementation of this revised
contract. T-026 (safe HTML), T-027 (Personal Notes protection), and T-028 (source-parent
tags) remain completed. Direct Amp retesting established native GUI first/update/no-op
imports, full-table scheduling preservation, and visible rendering for that old model;
it did not establish multi-card semantics or exhaustive extraction coverage. The new
release gates below require fresh evidence for the changed model, not reopening resolved
harness, environment, or screenshot issues.

## Potential Features

### Assisted Deck Profiles

LatinitasCards must inspect an existing CSV, APKG, or COLPKG input and propose a profile
covering at least:

- note type selection;
- the source lexical-entry field;
- the field containing principal parts or multi-form data;
- an optional meaning/gloss field;
- separators and principal-part ordering; and
- target deck, note type, and tags for generated notes.

The user must confirm proposed mappings against representative examples before generation.
The confirmed profile is saved in a human-readable, versioned project file. Subsequent
runs use it deterministically, while explicit CLI options may override individual values
and the effective configuration is reported. CLI controls and diagnostics are English.

v0.1.0 supports German generated content. Domain models must use explicit language tags so
English output can be added later without redesign; other target languages are not a v1.0
requirement.

### Stable Generated Note Identity

Every generated learning object must have an immutable logical `LatinitasID`. It is
derived from an immutable source identity, a stable learning-object key, and a fixed
identity namespace for the note family. Recipe selection, generation profile, semantic
card role, mutable text, formatting, colors, software/schema version, and local Anki
note/card IDs must not participate in note identity. Card identities are separate.

For APKG/COLPKG input, the source note GUID is the preferred source identity. CSV input
must provide a stable source-ID column or preserve IDs assigned in the confirmed profile's
manifest. The generated CSV places `LatinitasID` in the first field so Anki can match notes
on repeated text imports. Future APKG output must derive the Anki note GUID from the same
logical identity; numeric note and card IDs are transport-local only.

For a CSV without a stable source-ID column, the sidecar manifest reconciles unchanged rows
across reordering. Edited, duplicate, or unmatched rows require explicit review before an
existing source identity is reused or a new one is assigned. Reconciliation must never
silently transfer an identity between rows.

One coherent learning object is one generated note with zero or more eligible cards.
This explicitly supersedes the old recipe/role-derived per-exercise note identity and
single-card default; existing experimental notes require the migration decision below.

Generated notes use a dedicated, stable note type and default to a configurable subdeck
such as `Latin::Latinitas`. They carry source provenance and stable tags. For APKG/COLPKG
sources, every generated note inherits all parent-note tags in addition to configured
generated tags, combined deterministically without duplicates. Tags remain outside
identity derivation. At minimum the note contract separates these concerns:

- immutable Latinitas identity;
- managed structured knowledge and per-card prompt/answer content;
- source identity and provenance;
- schema, generator, profile, and recipe metadata (not identity inputs); and
- a user-owned personal-notes field that later updates must never overwrite.

### Principal-Part Card Generation

v0.1.0 generates Latin-first principal-part exercises from confirmed lexical entries.
The initial recipes are:

1. principal-part completion, for example
   `dico — dicere — _____ — dictum` -> `dixi`; and
2. principal-part recognition, for example `dixi` -> lemma, complete principal parts,
   semantic role such as perfect principal part/stem, and the configured German gloss.

German-to-Latin production is not an initial recipe. The objective is to recognize forms
encountered while reading, connect them to a dictionary lemma, and learn the stems needed
for later parsing. Generation must retain the relationship to the source lexical entry and
must report entries that cannot be parsed confidently rather than guessing silently.

Recipe suggestions are previewed and confirmed during profile setup. The confirmed recipe
selection is saved and reused; LatinitasCards does not generate every compatible exercise
implicitly.

Principal-part parsing is a separate domain boundary from recipe rendering. It produces
named semantic roles or a structured unsupported/ambiguous result. The supported layout
matrix and normalization rules are explicit and tested; the parser does not infer a role
silently when more than one interpretation remains.

Extraction of source text is not linguistic validation. A confirmed supine role and a
confirmed perfect passive participle role remain distinct even when strings resemble
each other; an ending such as `-um` never licenses silent conversion. v0.1.0 fixes proven
defects within its documented layout contract, not broad alternatives, omitted-slot
inference, mixed hints, or calibrated morphological analysis (v0.2.0).

### Coherent Learning Objects And Identities

Latinitas generates structured knowledge. A note represents one coherent underlying
learning object, usually one Latin lexeme plus relevant sense. Strongly related facts
that can meaningfully cue each other belong together; merely related material does not.
Meaning, principal parts, and irregular-form recognition for `fero` belong together.
A particular sentence translation involving `fero` may be a separate future object.
Do not create an arbitrarily large note containing every exercise about a word.

A source note can contain more than one object. v0.1.0 must either confirm one coherent
lexeme/sense or require explicit reviewed object boundaries and stable keys; automatic
sense splitting and merging are not required. Unsupported multi-object rows are reported,
never silently merged. Distinct source identities remain distinct even for identical
visible words. Corrections to spelling or gloss do not change an established object key;
a true split/merge or sense reassignment requires review, never text-hash rematching.

CSV identity must include an immutable persisted source scope, not only a manifest-local
counter. Independent manifests currently both allocate `csv-source-000001`; synthetic
`amo` and `fero` sources consequently produced eight identical generated IDs in the old
model. Fix this before freezing object IDs. Independent sources must remain distinct;
moving, reordering, saving and reloading the same manifest must retain its scope and IDs.
Explicit CSV source-ID columns also need documented scope, including future authored
IDs; filenames, mutable content and profiles cannot provide that scope. Specify independent
versioned input/output identity vectors, not expected IDs computed by the production
helper. Existing unscoped IDs require an explicit compatibility/fresh-start decision,
never silent reinterpretation. This finding demonstrated colliding IDs, not a native
destination-overwrite test; the overwrite risk follows from first-field update matching.

Define source-scope bootstrap before implementing identity derivation. An uninitialized
read-only preview reports that scope confirmation is required; it does not mint apparently
stable IDs or write state. The first explicitly approved export allocates a unique scope
and commits it with the source assignments and output through the recoverable export
boundary. Later exports reuse the persisted scope, including for explicit CSV-ID columns.
Moving or copying that state preserves the same logical source; creating an independent
source requires an explicit new scope. Missing state is not permission to silently replace
an established scope: require recovery/review or an explicitly confirmed fresh start.
Determinism includes the persisted scope and assignments as inputs; independent bootstrap
operations must not collide merely because their source contents are identical. Test
bootstrap cancellation/failure, read-only preview, retry with existing state, and copies.

Adapt the existing source adapters, identity/manifest, profile, parsed knowledge,
generation, notes, and preview/export boundaries rather than creating a parallel stack.
Separate source note, learning object/generated note, generated knowledge, card type,
and generation profile. Profiles enable knowledge/card types but do not own identities.
Keep source GUID/ID and location/deck provenance, schema/generator versions, and effective
profile metadata traceable. Source fields, note-type templates, and deck structure remain
unchanged; generated notes use Latinitas-owned note types.

Acceptance: a synthetic `fero` object yields one note with several enabled cards, while
`sum` yields another. Regeneration, wording changes, and adding an already-supported
recipe/role enrich the same note. Repeat export is deterministic. Ambiguous object
boundaries stop affected generation with review diagnostics. Tests establish provenance
and source immutability. No new lexical, mnemonic, or morphology recipe is required now.

### Conditional Sibling Cards

The two initial recipes produce cards on their shared learning-object note. Each card
has a stable semantic key (recipe + confirmed role) mapped to a documented template slot.
Template names, order/ordinals, and keys must not be repurposed or renumbered on profile
changes. A new capability uses a new slot; no deletion/recreation of surviving cards to
change wording. The note-family namespace stays stable through compatible schema changes;
incompatible changes require an explicit migration decision rather than new IDs by default.

T-029 establishes the authoritative note schema and ownership categories. T-030 extends
that same contract with the exact supported semantic keys, slots, per-card fields and
eligibility rules before implementing conditional rendering. Exporter and templates must
consume it; T-033 publishes and checks the reference setup, not a second schema. Complete
T-032's normalized eligibility fix before T-030, rather than implementing it twice.

Eligibility requires a selected recipe, a supported verb entry, a present target role,
and all context/answer data required by that recipe. Completion needs meaningful remaining
context and an answer; recognition needs the target, lemma, and interpretable role/context.
Optional gloss absence must not invent a translation. Explicitly omitted roles do not
shift positional meanings. Nouns, ambiguous roles, or missing answers do not emit verb
cards. Front templates must be wholly guarded by a per-card eligibility field so static
labels do not generate blank cards. Zero-eligible objects are reported; zero cards is
valid in the domain, but CSV must omit zero-eligible new notes if native import would
create a blank card. Report that omission separately from parser failures.

Existing-card eligibility loss or recipe deselection is not a safe deletion command:
preview it and withhold affected updates pending review. Do not automatically empty
fronts, delete cards, or reset schedules. Until managed retirement in v0.2.0, users retain
the existing notes or explicitly suspend affected cards using a backed-up manual workflow.
Compare against a retained prior export/eligibility manifest, not an assumed live
collection state. Missing prior evidence requires explicit fresh-import confirmation or
a review-only outcome; it cannot establish that removing a card is safe. This bounded
regeneration check is not destination-aware conflict detection or proof of actual import.

Define a versioned prior-export checkpoint bound to source scope, note-family/schema and
template registry, recording each exported object ID, card-key/slot eligibility and the
export fingerprint. Retain the last safe exported evidence for withheld or absent objects;
a partial export or parser failure must not erase it or assert that their cards disappeared.
Missing, corrupt, mismatched or incompatible checkpoint state requires recovery/review or
explicit fresh-import confirmation, never an assumed empty prior card set. Withhold the
whole affected note row when a shared-field update could invalidate an existing card.

Preview never advances this checkpoint. Commit changes only with a successful export,
through the existing CSV/identity-state recovery boundary; do not independently advance
the checkpoint before the corresponding output is committed. Extend interruption tests
when this state is added, preserving prior scope, assignments and eligibility evidence
or recoverable backups. Record exported state only: generating a file does not establish
that it was imported. v0.2.0's last-successfully-applied destination baseline is separate.
Test missing/mismatched state, withheld-row retention, partial exports, failed commit/retry,
profile disablement, and adding a supported card without forgetting surviving cards.

All cards share note-level Personal Notes and tags, but retain independent Anki card IDs,
review histories, and scheduling states. Same note ID plus different template ordinals
must make them genuine siblings. Anki owns FSRS and burying; Latinitas neither implements
scheduling nor changes users' burying settings. Acceptance tests inspect structural
sibling relationships, eligibility boundaries, stable slots, and independent states;
they do not simulate or test the FSRS algorithm.

### Mapping Evidence And Confirmation

Rank source-field suggestions from representative content as well as names. A synthetic
fixture with lesson-number field `LatinumB_Lektion` and Latin-content field `Latein` must
prefer the content field without hard-coding these names. Show candidate examples and
the reason for the suggestion; ties, conflicting samples, or weak evidence require an
explicit field choice before saving a usable profile. Even strong suggestions require
confirmation. Preserve manual overrides, deterministic saved mappings, and explicit
role/order confirmation. Test renamed fields, misleading names, sparse values, and ties;
correct use of a previously confirmed mapping is not evidence of improved suggestions.

### Extraction Content Review

Review a stratified representative sample of generated, skipped, incomplete, unsupported,
and ambiguous entries within the currently documented layout matrix. Record population
counts, selection method, per-category sample counts, adjudicated causes, and unreviewed
remainder; never extrapolate a sample into a claim that all content is correct. Use only
synthetic or independently sanitized examples in committed evidence, not private exports.

Separate wrong mapping, extraction/normalization defect, genuinely missing data, unsupported
layout, and unresolved linguistic role. Fix reproduced extraction defects within the
current contract with discriminating regression cases, preserving display versus
comparison values and uncertainty. Broader alternatives, omissions, mixed hints, and new
linguistic rules become v0.2.0 inputs, not silent scope expansion. A review that finds no
additional in-contract defect must say so rather than invent implementation work.
Existing German terminology approval remains historical evidence; new text needs review.

One in-contract eligibility defect is already reproduced: `amo — amare — <b></b> — amatum`
produced eight notes with no skips, including an empty perfect completion answer and
recognition of an empty string. Preserve raw provenance separately, normalize semantic
display text once before eligibility, then escape at rendering. Regressions must cover
markup-only/comment-only values, encoded whitespace, required leading omissions, and
decode-once/double-entity cases. This is not permission to pass through source HTML or
reopen T-026; the safe rendering fix remains valid.

### Interrupt-Safe CSV And Manifest Export

A reproduced `KeyboardInterrupt` after existing CSV/manifest destinations moved to
backups left neither destination nor any backup: rollback caught only `OSError` and
finally cleanup removed backups. This catchable interruption is distinct from power-loss
or hard-crash pair atomicity. CSV and source-identity manifest recovery must preserve
authoritative prior identities as well as content; source files must remain untouched.

Propagate cancellation after recovery or retain discoverable recoverable backups if
restoration fails. Delete backups only after confirmed commit or confirmed recovery,
never merely because control reached cleanup. Inject interruptions around every
destructive move/replacement with both existing and absent destinations, partial commit,
and failed restoration; retain ordinary `OSError` rollback tests. Assert prior bytes and
identity assignments survive or are recoverable with clear diagnostics, not just that
an exception was raised. Keep this a focused export-transaction fix; no database,
transaction framework, or stronger hard-crash atomicity promise is required.

### Reference Note Type And Import Safety

**Mapping Tags can replace destination-only manual tags when Anki updates a note.
Source-parent inheritance does not preserve destination edits.** In the tested native
Anki 26.09.3 CSV-dialog workflow, a tag-only difference was skipped and retained manual
tags; changing the managed gloss too caused the mapped tags to replace them. This is a
bounded observation, not a guarantee that other import paths or versions preserve tags.
Warn in setup/import/reimport guidance before the user applies output. Do not rely on CSV
import to preserve or merge manual tags. Back up/export destination tags before importing;
users requiring automatic preservation must defer updates to the destination-aware
v0.2.0 workflow.
Personal Notes is a separate protected field, shared across this note's cards, and must
remain absent from generated CSV columns rather than merely exported as an empty value.

A small authoritative generated-schema contract established in T-029 and completed with
card slots in T-030 must distinguish regular managed note fields, user-owned Personal Notes,
and special transport metadata. T-033 consumes and documents it. Anki's Tags column is
transport metadata, not an ordinary note field. Derive export positions, tag-column
directives and reference template fields from that contract; independently test their
external order/mapping rather than deriving test expectations with the same helper.
Source adapters retain source-specific field/profile preparation and raw provenance;
transport serialization owns CSV metadata/escaping, not source inference. This addresses
schema drift risk, not a newly demonstrated current import failure. Do not introduce
a generic adapter framework or automate live note-type provisioning.

Provide a versioned reference field schema, stable template-slot registry, copyable front
and back templates, and CSS with synthetic examples for both initial recipes and missing
forms. This is a manual reference setup, not general automated provisioning (v0.6.0).
An eligibility guard must enclose the entire front, for example the schematic template:

```html
{{#CompletionPerfectEnabled}}{{CompletionPerfectPrompt}}{{/CompletionPerfectEnabled}}
```

Its matching back renders managed answer/context plus shared Personal Notes using the
existing safe-HTML contract. Concrete field names and all supported slots must be frozen
and tested with the final exporter before release; this schematic is not an importable
schema for today's single-card output.

The supported first/repeat-import checklist is:

1. Back up the collection; use a disposable profile to verify the reference schema first.
2. Create the dedicated Latinitas note type from the exact reference fields and templates;
   put `LatinitasID` first. Do not modify source note types or reuse legacy exercise types.
3. Choose the configured target deck; enable HTML; match on first field with Note Type
   scope; choose Update for existing notes. Verify mapping in the native import dialog.
4. Map managed fields and Tags deliberately; leave Personal Notes unmapped and verify that
   no generated column can overwrite it. Accept the manual-tag replacement warning first.
5. Check preview counts separately for source entries, objects/notes, eligible cards, and
   skipped/review cases. Do not confuse one CSV row with one card.
6. Inspect both card sides and sibling relationships; repeat an unchanged import and a
   controlled managed-field update. Compare full card/review-log tables for updates and
   full note/card/review-log tables for no-op imports, not a scheduling-column subset.
7. Enable desired Anki sibling-burying settings manually; verify independent cards and
   observe burying with synthetic siblings without claiming to validate Anki's scheduler.

### Pre-Release Note Model Migration

The old recipe/role-derived IDs and per-exercise notes cannot be consolidated by ordinary
CSV Update with a promise of preserved card histories. There is no established evidence
for such a CSV-only structural migration. Never silently convert existing collections,
delete old notes, reuse their IDs for a different object, or combine Personal Notes by
last-write-wins. Inventory legacy profile/schema, note/card mappings, personal fields,
tags, and histories before recommending an operation.

The supported v0.1.0 option is an explicitly approved fresh start for disposable
pre-release generated data: back up first, create the new dedicated note type in a
disposable collection, validate output, and document that schedules are new. Keep old
collections intact until the owner explicitly approves any cleanup. For valuable review
history or conflicting personal annotations, retain the old model/collection and defer
conversion; do not claim that exporting/importing CSV preserves that history. A future
history-preserving migration requires a separately approved, destination-aware plan with
per-card mapping, explicit annotation/tag reconciliation, backup/rollback, and verified
native scheduling/history preservation. It is not required solely for unreleased data.

Reject incompatible legacy profiles clearly or require explicit re-confirmation into the
new schema; never silently reinterpret them. Acceptance covers legacy detection, no-write
review outcomes, conflicting personal annotations, consent boundaries, and a synthetic
fresh-start rehearsal. Compatible regeneration in the new model is a separate operation
and must preserve existing card identities/history without resetting them.

### Revised Architecture Release Gate

Publication is blocked until the new learning-object model, conditional templates,
mapping confirmation, content review, reference import setup, migration safety, and
interrupt-safe CSV/manifest recovery are implemented and verified together. Independent
source-scope identity vectors, normalized eligibility regressions, and external schema/
transport assertions are mandatory gates, not optional sample-review findings.
Prior completed release-candidate and single-card GUI evidence does not approve this
new candidate. Use synthetic fixtures
for first/update/no-op native GUI imports, adding an enabled card to the same note,
missing-form and profile-disable review paths, source immutability, shared Personal Notes,
tag-loss warning, separate card scheduling, and sibling structure/burying settings.
Inspect real rendered fronts/backs (reject blank/black captures) and compare full tables
for unchanged surviving cards/review logs. Record tested Anki version/platform and limits;
broad compatibility remains v0.9.0. Run the required ruff/mypy/pytest chain and supported
Python CI before seeking explicit publication approval for the exact candidate commit.

### Preview And Deterministic CSV Export

Before writing output, LatinitasCards must show a representative preview and a summary of
generated, skipped, and ambiguous entries. It then writes deterministic, UTF-8 Anki-import
CSV with stable field ordering, import metadata or clear import instructions, the dedicated
note type, target deck/subdeck, and provenance tags.

Source HTML formatting must become safe, readable study content without displaying raw
formatting tags or executing active source content. Repeat import must protect user-owned
Personal Notes without relying on Anki remembering a previous Ignore mapping; generated
import data must not expose an empty personal field for accidental overwrite.

Preview and export operate on an internal structured result so domain behavior is not
coupled to terminal rendering. v0.1.0 does not make that result a stable public JSON CLI
contract; stable non-interactive agent output remains roadmap work.

Running the same version with the same input and effective profile must produce the same
logical notes and IDs. Changing wording, German glosses, HTML, tags, or presentation must
update the same logical note rather than create a duplicate. The source deck is never
modified by this workflow.

v0.1.0 does not promise automatic conflict detection against a live Anki collection. It
must nevertheless establish the identity and field-ownership contract required for later
managed updates. Existing experimental APKG mutation commands are not the output path for
this release workflow.

### Release Readiness

The release must include:

- a sanitized acceptance fixture representing a realistic existing deck layout;
- regression tests for assisted mapping, stable identity, both principal-part recipes,
  deterministic regeneration, ambiguous-entry reporting, and CSV import metadata;
- documentation for profile creation, preview, generation, first import, and repeat import;
- an explicit experimental-status note for legacy APKG mutation and corpus commands;
- refreshed third-party notices and dependency-license review;
- a changelog entry, a matching `v0.1.0` tag, and a GitHub release; and
- a clean `ruff`, strict `mypy`, and full `pytest` chain on supported Python versions.

No release claim may imply that direct Anki updates, generalized corpus generation, or
automatic grammatical parsing are complete.

Release-candidate readiness is verified before publication. Tagging the exact candidate
commit and creating the GitHub release are a separate, final step.

## Functional Contracts

### Profile Contract

- Profiles are human-readable and carry a `schema_version`.
- Pre-1.0 profiles have no backwards-compatibility guarantee, but incompatible schemas
  fail clearly and are never interpreted silently.
- The effective profile, including CLI overrides, is available in human-readable output
  and a machine-readable form suitable for future agent use.
- Profiles contain no credentials or provider secrets.

### Identity Contract

- A source note has one stable source identity; its coherent objects have reviewed keys.
- A generated object has one stable Latinitas note identity; its retrieval cards have
  separate stable semantic keys mapped to non-repurposed template slots.
- Distinct objects never share note identity; different cards of one object do share it.
- Software/profile/recipe-selection changes do not change the learning object's identity.
- Domain relationships use Latinitas/source identities. Local card IDs/ordinals are
  inspected for transport and preservation evidence, not used as logical identity seeds.

### Ownership Contract

- v0.1.0 writes a new generated CSV and never mutates the source deck.
- Generated fields and user-owned fields are distinct in the note schema.
- Personal Notes and tags belong to the note and are shared by its cards, not separately
  editable per retrieval exercise. Anki scheduling and review histories remain per-card.
- Native CSV Update can replace destination-only manual tags with the mapped exported set
  when a note is updated, subject to the tested import boundary described above;
  destination-aware preservation/conflict handling is v0.2.0, not a v0.1.0 guarantee.
- Later managed-update workflows may change managed fields only after a plan; personal
  fields remain untouched.
- Removal from a future generation plan will mean retire and suspend after explicit apply,
  never silent deletion. v0.1.0 records enough provenance for that future behavior.

## Non-Functional Requirements

- Core inspection, profile use, generation, preview, and export work offline.
- Network access is opt-in for future LLM interactions and source downloads.
- Outputs are deterministic for fixed inputs, profile, and software version.
- Errors identify the source entry and failed assumption without exposing private deck
  contents unnecessarily.
- Existing command behavior remains available unless separately deprecated; new work must
  not expand the monolithic `cli.py` architecture.
- Application changes require the repository's full ruff, mypy, and pytest validation
  chain.

## Existing Experimental Capabilities

The following shipped capabilities remain available but are not v0.1.0 release promises:

- APKG/COLPKG mutation and split-note cloning;
- CLTK/Stanza annotation and optional Ollama disambiguation;
- corpus cloze generation from USFX, plain text, and parallel CSV;
- difficulty filtering and parallel translation output; and
- the separate USFX `preview` and `generate` workflow.

CLTK/Stanza annotation ships as the optional `annotate` package extra, so the default install
excludes CLTK, Stanza, and PyTorch. The `annotate` extra resolves CPU-only PyTorch; a highly
experimental, conflicting `annotate-gpu` extra resolves CUDA PyTorch instead. Both use
CLTK 2, which writes UD `upos` tags and UD `Key=Value|...` morphological features and leaves
`xpos` empty.

Their current tests continue to run. Known correctness or safety defects may be fixed, but
completing their option coverage is deferred unless required to prevent regression in the
v0.1.0 workflow.

## Roadmap To v1.0

**v0.2 — managed updates and form parsing.** Compare generated content with a current deck
export; classify create/update/unchanged/conflict/retire actions; preserve personal fields
and scheduling; tag and suspend explicitly retired notes; add calibrated form parsing with
a review queue; and add semantic morphology classes plus configurable color themes.

**v0.2.1 — deck-based phrase and grammar practice.** Recombine reviewed vocabulary already
in an Anki deck using bounded, reviewed construction patterns: preposition–noun,
noun–genitive, verb–noun, and adjective agreement. Offer separate translation and form
recognition recipes across supported inflectional variants, preserve ambiguity, and
require approval of new combinations before deterministic export. This deck-first feature
does not depend on corpus normalization or unrestricted sentence generation.

**v0.3 — normalized corpus and agent contracts.** Normalize USFX into a versioned JSONL
model with corpus namespaces, stable source passage IDs, content hashes, complete citations,
and immutable-source sidecar annotations. Add non-interactive JSON/JSONL CLI output, stable
exit/error codes, deterministic plan/apply behavior, and policy-gated agent automation.

**v0.4 — corpus-first generation.** Generate context, guided-analysis, phrase-translation,
and free-translation recipes without requiring an existing deck. Default context to one
sentence while retaining the complete source segment and citation. Use transparent,
deterministic ranking budgets instead of requiring review of every candidate. Add TEI XML
as an adapter to the normalized corpus model and English generated content.

**v0.5+ — grammar and integration expansion.** Add reviewed syntactic roles, separate
morphology and sentence-function color layers, curated grammar/mnemonic recipes, additional
lexical and paradigm exercises, optional dictionary links, enriched-corpus exports, and
optional direct Anki integration. File outputs remain the canonical auditable workflow.

**v1.0 — stable core contract.** Deck-first and corpus-first workflows, generated-note
identity, update semantics, profiles, recipes, normalized corpora, provenance, and file
formats become compatibility promises with documented migrations. v1.0 does not require
every possible card type, corpus adapter, output language, or integration.

## Risks And Trade-Offs

- Existing decks vary widely; assisted mapping must expose examples and uncertainty rather
  than imply universal automatic inference.
- Principal-part order is convention-dependent. The profile must name semantic roles, not
  preserve only positional indices.
- A stable ID created from mutable text would duplicate notes after corrections; identity
  must remain separate from content hashes.
- CSV import depends on matching note type and first field. Documentation and fixtures must
  demonstrate the required Anki import settings.
- Pre-1.0 schema freedom accelerates design but may require users to recreate profiles.
- Existing direct APKG mutation manually manages Anki internals and is not evidence that
  safe managed updates are complete.

## Open Inputs

- Prior representative-deck and German terminology validation remains completed evidence
  for the old model. New mapping edge cases, extraction samples, and multi-card wording
  require their own bounded review; no new private deck transfer is required here.
- Synthetic fixtures establish structural behavior, not exhaustive real-world extraction
  accuracy. Record the available sample boundary and outstanding content/wording review.
- The exact supported template-slot set and resulting sibling count must be reviewed
  during T-030/T-033; avoid expanding the initial two recipes merely to fill templates.
- Owners with valuable legacy history must choose retention/deferred migration versus an
  explicitly approved disposable fresh start; planning does not grant cleanup consent.
- Exact command names and profile serialization are implementation decisions, provided the
  contracts above remain stable within v0.1.0.

## Explicitly Out Of Scope For v0.1.0
