# LatinitasCards v0.1.0

## Objective

Deliver the first useful, repeatable deck-enrichment workflow: inspect an existing Anki
deck, confirm how its lexical fields are structured, and generate principal-part recall
cards that can be imported repeatedly without creating duplicates.

The release is deck-first. It establishes identities and data contracts that later
versions can reuse for form parsing, color-coded grammar cards, corpus-first generation,
and optional direct Anki integration. The Vulgate remains the first bundled corpus and a
useful example, but it is not the product boundary.

## Context And Current State

The repository was retrofitted after a broader CLI had already been built. The existing
commands can inspect and split CSV/APKG inputs, annotate forms through CLTK with optional
Ollama disambiguation, and generate clozes from USFX, text, or parallel CSV corpora. These
capabilities remain available, but they do not yet form a coherent, safely updateable card
generation contract.

In particular, current generated APKG notes do not have identities suitable for repeated
generation: their GUID seed includes a newly allocated local note ID. The generalized
`cloze` command and the older `preview`/`generate` path also use different selection
engines. Difficulty filtering, parallel translations, module extraction, and generalized
corpus generation are therefore not v0.1.0 release gates.

The first existing deck used to verify this release is an acceptance fixture, not a
product-specific assumption. Deck field names, note types, languages, and separators must
be described by a reusable profile rather than hard-coded.

## Potential Features

### Assisted Deck Profiles

LatinitasCards must inspect an existing CSV, APKG, or COLPKG input and propose a profile
covering at least:

- note type selection;
- the source lexical-entry field;
- the field containing principal parts or multi-form data;
- an optional meaning/gloss field;
- separators and principal-part ordering; and
- target deck, note type, and tags for generated notes.

The user must confirm proposed mappings against representative examples before generation.
The confirmed profile is saved in a human-readable, versioned project file. Subsequent
runs use it deterministically, while explicit CLI options may override individual values
and the effective configuration is reported. CLI controls and diagnostics are English.

v0.1.0 supports German generated content. Domain models must use explicit language tags so
English output can be added later without redesign; other target languages are not a v1.0
requirement.

### Stable Generated Note Identity

Every generated exercise must have an immutable logical `LatinitasID`. It is derived from
an immutable source identity, the recipe identity, and a semantic exercise key such as a
principal-part role. Mutable text, formatting, colors, generated output, software version,
and local Anki note/card IDs must not participate in identity.

For APKG/COLPKG input, the source note GUID is the preferred source identity. CSV input
must provide a stable source-ID column or preserve IDs assigned in the confirmed profile's
manifest. The generated CSV places `LatinitasID` in the first field so Anki can match notes
on repeated text imports. Future APKG output must derive the Anki note GUID from the same
logical identity; numeric note and card IDs are transport-local only.

For a CSV without a stable source-ID column, the sidecar manifest reconciles unchanged rows
across reordering. Edited, duplicate, or unmatched rows require explicit review before an
existing source identity is reused or a new one is assigned. Reconciliation must never
silently transfer an identity between rows.

One generated exercise is one generated note/card by default. A later recipe may use a
multi-card note only when the exercises are intentionally inseparable and template
identity can remain stable.

Generated notes use a dedicated, stable note type and default to a configurable subdeck
such as `Latin::Latinitas`. They carry source provenance and stable tags. At minimum the
note contract separates these concerns:

- immutable Latinitas identity;
- managed prompt and answer content;
- source identity and provenance;
- recipe and generation metadata; and
- a user-owned personal-notes field that later updates must never overwrite.

### Principal-Part Card Generation

v0.1.0 generates Latin-first principal-part exercises from confirmed lexical entries.
The initial recipes are:

1. principal-part completion, for example
   `dico — dicere — _____ — dictum` -> `dixi`; and
2. principal-part recognition, for example `dixi` -> lemma, complete principal parts,
   semantic role such as perfect principal part/stem, and the configured German gloss.

German-to-Latin production is not an initial recipe. The objective is to recognize forms
encountered while reading, connect them to a dictionary lemma, and learn the stems needed
for later parsing. Generation must retain the relationship to the source lexical entry and
must report entries that cannot be parsed confidently rather than guessing silently.

Recipe suggestions are previewed and confirmed during profile setup. The confirmed recipe
selection is saved and reused; LatinitasCards does not generate every compatible exercise
implicitly.

Principal-part parsing is a separate domain boundary from recipe rendering. It produces
named semantic roles or a structured unsupported/ambiguous result. The supported layout
matrix and normalization rules are explicit and tested; the parser does not infer a role
silently when more than one interpretation remains.

### Preview And Deterministic CSV Export

Before writing output, LatinitasCards must show a representative preview and a summary of
generated, skipped, and ambiguous entries. It then writes deterministic, UTF-8 Anki-import
CSV with stable field ordering, import metadata or clear import instructions, the dedicated
note type, target deck/subdeck, and provenance tags.

Preview and export operate on an internal structured result so domain behavior is not
coupled to terminal rendering. v0.1.0 does not make that result a stable public JSON CLI
contract; stable non-interactive agent output remains roadmap work.

Running the same version with the same input and effective profile must produce the same
logical notes and IDs. Changing wording, German glosses, HTML, tags, or presentation must
update the same logical note rather than create a duplicate. The source deck is never
modified by this workflow.

v0.1.0 does not promise automatic conflict detection against a live Anki collection. It
must nevertheless establish the identity and field-ownership contract required for later
managed updates. Existing experimental APKG mutation commands are not the output path for
this release workflow.

### Release Readiness

The release must include:

- a sanitized acceptance fixture representing a realistic existing deck layout;
- regression tests for assisted mapping, stable identity, both principal-part recipes,
  deterministic regeneration, ambiguous-entry reporting, and CSV import metadata;
- documentation for profile creation, preview, generation, first import, and repeat import;
- an explicit experimental-status note for legacy APKG mutation and corpus commands;
- refreshed third-party notices and dependency-license review;
- a changelog entry, a matching `v0.1.0` tag, and a GitHub release; and
- a clean `ruff`, strict `mypy`, and full `pytest` chain on supported Python versions.

No release claim may imply that direct Anki updates, generalized corpus generation, or
automatic grammatical parsing are complete.

Release-candidate readiness is verified before publication. Tagging the exact candidate
commit and creating the GitHub release are a separate, final step.

## Functional Contracts

### Profile Contract

- Profiles are human-readable and carry a `schema_version`.
- Pre-1.0 profiles have no backwards-compatibility guarantee, but incompatible schemas
  fail clearly and are never interpreted silently.
- The effective profile, including CLI overrides, is available in human-readable output
  and a machine-readable form suitable for future agent use.
- Profiles contain no credentials or provider secrets.

### Identity Contract

- A source lexical entry has one stable source identity.
- A generated exercise has one stable Latinitas identity.
- The same identity is never issued to two semantically distinct exercises.
- A software upgrade does not change identity unless the learning exercise itself changes.
- Relationships use Latinitas/source identities, never local Anki card IDs.

### Ownership Contract

- v0.1.0 writes a new generated CSV and never mutates the source deck.
- Generated fields and user-owned fields are distinct in the note schema.
- Later managed-update workflows may change managed fields only after a plan; personal
  fields remain untouched.
- Removal from a future generation plan will mean retire and suspend after explicit apply,
  never silent deletion. v0.1.0 records enough provenance for that future behavior.

## Non-Functional Requirements

- Core inspection, profile use, generation, preview, and export work offline.
- Network access is opt-in for future LLM interactions and source downloads.
- Outputs are deterministic for fixed inputs, profile, and software version.
- Errors identify the source entry and failed assumption without exposing private deck
  contents unnecessarily.
- Existing command behavior remains available unless separately deprecated; new work must
  not expand the monolithic `cli.py` architecture.
- Application changes require the repository's full ruff, mypy, and pytest validation
  chain.

## Implemented Infrastructure

### Commit Policy Hooks

Local hooks are managed by lefthook and enforce linting, formatting, type checking,
Taskrail validation, commit-message policy, authorship policy, and pre-push tests. The
guard scripts have dedicated CI coverage.

### uv Toolchain

The project uses uv with the pinned mise toolchain, locked dependencies, Python 3.13 and
3.14 CI coverage, grouped Dependabot updates, and cached orb setup/resume scripts.

## Existing Experimental Capabilities

The following shipped capabilities remain available but are not v0.1.0 release promises:

- APKG/COLPKG mutation and split-note cloning;
- CLTK/Stanza annotation and optional Ollama disambiguation;
- corpus cloze generation from USFX, plain text, and parallel CSV;
- difficulty filtering and parallel translation output; and
- the separate USFX `preview` and `generate` workflow.

CLTK/Stanza annotation ships as the optional `annotate` package extra, so the default install
excludes CLTK, Stanza, and PyTorch. The `annotate` extra resolves CPU-only PyTorch; a highly
experimental, conflicting `annotate-gpu` extra resolves CUDA PyTorch instead. Both use
CLTK 2, which writes UD `upos` tags and UD `Key=Value|...` morphological features and leaves
`xpos` empty.

Their current tests continue to run. Known correctness or safety defects may be fixed, but
completing their option coverage is deferred unless required to prevent regression in the
v0.1.0 workflow.

## Roadmap To v1.0

**v0.2 — managed updates and form parsing.** Compare generated content with a current deck
export; classify create/update/unchanged/conflict/retire actions; preserve personal fields
and scheduling; tag and suspend explicitly retired notes; add calibrated form parsing with
a review queue; and add semantic morphology classes plus configurable color themes.

**v0.3 — normalized corpus and agent contracts.** Normalize USFX into a versioned JSONL
model with corpus namespaces, stable source passage IDs, content hashes, complete citations,
and immutable-source sidecar annotations. Add non-interactive JSON/JSONL CLI output, stable
exit/error codes, deterministic plan/apply behavior, and policy-gated agent automation.

**v0.4 — corpus-first generation.** Generate context, guided-analysis, phrase-translation,
and free-translation recipes without requiring an existing deck. Default context to one
sentence while retaining the complete source segment and citation. Use transparent,
deterministic ranking budgets instead of requiring review of every candidate. Add TEI XML
as an adapter to the normalized corpus model and English generated content.

**v0.5+ — grammar and integration expansion.** Add reviewed syntactic roles, separate
morphology and sentence-function color layers, curated grammar/mnemonic recipes, additional
lexical and paradigm exercises, optional dictionary links, enriched-corpus exports, and
optional direct Anki integration. File outputs remain the canonical auditable workflow.

**v1.0 — stable core contract.** Deck-first and corpus-first workflows, generated-note
identity, update semantics, profiles, recipes, normalized corpora, provenance, and file
formats become compatibility promises with documented migrations. v1.0 does not require
every possible card type, corpus adapter, output language, or integration.

## Risks And Trade-Offs

- Existing decks vary widely; assisted mapping must expose examples and uncertainty rather
  than imply universal automatic inference.
- Principal-part order is convention-dependent. The profile must name semantic roles, not
  preserve only positional indices.
- A stable ID created from mutable text would duplicate notes after corrections; identity
  must remain separate from content hashes.
- CSV import depends on matching note type and first field. Documentation and fixtures must
  demonstrate the required Anki import settings.
- Pre-1.0 schema freedom accelerates design but may require users to recreate profiles.
- Existing direct APKG mutation manually manages Anki internals and is not evidence that
  safe managed updates are complete.

## Open Inputs

- A sanitized representative deck or export is required to confirm field mappings,
  separators, principal-part conventions, and generated-note examples.
- The initial German wording and principal-part terminology require user review.
- Development may use provisional synthetic fixtures and terminology, but representative-
  deck and terminology validation must gate the assisted setup and recipe deliverables.
- Exact command names and profile serialization are implementation decisions, provided the
  contracts above remain stable within v0.1.0.

## Explicitly Out Of Scope For v0.1.0

- Direct updates to a live Anki collection.
- Automatic conflict detection or retirement application.
- Corpus-first card generation or new corpus adapters.
- Form-level morphological parsing cards.
- Syntax analysis or sentence-function coloring.
- User-configurable color themes beyond preserving semantic markup extensibility.
- LLM-required generation or network-required core workflows.
- English generated content or localized CLI controls.
- Backwards-compatible migration of pre-1.0 profiles.
- PyPI publishing, prebuilt binaries, a GUI, or an Anki add-on.
