# LatinitasCards v0.3.0

## Summary

Planned release. Adds a normalized corpus model with stable passage identity, USFX and
plain-text adapters, annotation sidecars bound to that identity, an agent-ready CLI
contract for the new commands, policy-gated sidecar writes, and PyPI publishing. The
existing Vulgate commands keep their behaviour while reading through the USFX adapter.
Deck, phrase, claim and managed workflows are unchanged; corpus tools are new and optional.

v0.3.0 changes no generated note CSV, note-type layout, template or CSS. Characterization
goldens committed before any refactor replace native Anki acceptance, and no task
reopens a v0.2.x native gate; a change to Anki-facing output is out of scope and is filed
against a later spec. Fixed Contracts is binding: agents do not amend this spec during
the implementation loop but file a blocked follow-up task for the maintainer.
This maintainer-authorized pre-loop preparation may clarify the contracts before the
loop starts; it does not grant implementation workers permission to amend them. Where
task notes disagree with this prepared spec, this spec takes precedence.
Schema additions specified here belong to the existing manifest/plan tasks, not a new
feature; task size guards do not override these safety and recovery contracts.

## Goals

- Represent biblical, classical, late-antique and medieval Latin sources in one corpus
  model with provenance and work-specific citations, via USFX and plain-text adapters.
- Keep sources immutable, annotations in sidecars, and passage IDs stable across fixes.
- Give agents deterministic, non-interactive, versioned commands with stable exit codes,
  and gate sidecar writes by policy; linguistic acceptance stays a reviewed decision.
- Publish versioned releases on PyPI so users can install the CLI without a Git checkout.

### Normalized JSONL Corpus Model

A normalized corpus is one JSONL file: a header line, one `corpus` record, `work` records,
then `passage` records in document order. `passage_id` joins `corpus_id` and the
source-native `native_ref`; another edition is another corpus, and no identities are
mapped across editions. v0.4.0 uses `passage_id` as the `source_identity` of corpus-first
notes, so its grammar is frozen here. `passage_hash` covers only canonical `text`, so a
correction keeps the ID and changes the hash. A derived `norm` (`latin-fold/1`) serves
matching only. `citation` is `{scheme, parts: [{unit, value}], display}` with string
values, so no scheme needs a biblical model. Optional `translations` are schema-validated
and read only by `cloze`; no v0.3.0 adapter populates them.

The plain-text adapter reads one passage per non-empty line. With `--citation-template`,
each line's component-encoded label is the `native_ref` and no manifest is used.
Otherwise refs `p000001`... come from a `latinitas-corpus-manifest`, a new format reusing
only the matching rules of
`manifest.reconcile_csv_manifest` (not its file format, scope or allocator) with
`passage_hash` as fingerprint. A unique exact-hash match is reused automatically; an
unchanged source (same ordered hash list as the snapshot) reuses every ref positionally,
duplicates included. Edits, insertions, new duplicates and removals are review items
resolved only by `--approve-reuse N=REF`, `--approve-allocation N` and `--approve-removal
REF`, `N` being the zero-based passage ordinal. A retired ref is never reassigned.

Sentences and tokens are derived segmentation, stored in the annotation sidecar and
produced by the fixed rules `latin-seg/1` and `latin-tok/1` without CLTK; a sentence never
spans passages.

Illustrative, not normative (each record is one line in the file; wrapped for display):

```json
{"adapter":"usfx/1","corpus_id":"vulgata-clementina","edition":"Biblia Sacra Vulgata
 Clementina","format":"latinitas-corpus","language":"la","license":"Public Domain",...,
 "record":"header","source":{"bytes":4652378,"file_name":"lat-clementine.usfx.xml",
 "sha256":"sha256:05bc..."},"text_canon":1,"version":1}
{"citation":{"display":"GEN 1:1","parts":[{"unit":"book","value":"GEN"},...],
 "scheme":"usfx-bcv"},"native_ref":"GEN.1.1","order":1,"passage_hash":"sha256:...",
 "passage_id":"vulgata-clementina:GEN.1.1","record":"passage",
 "text":"In principio creavit Deus cælum et terram.","work":"GEN",...}
```

Acceptance: `corpus validate --json` accepts committed golden corpora. It exits 3 for an
unreadable file, non-JSONL, a missing header, an unknown format or a higher version, and
exits 1, with distinct codes, for a malformed `corpus_id`, a duplicate `native_ref`,
non-NFC `text`, a hash mismatch, a non-string citation value and a float. Golden hashes
pin three passages; NFD input hashes equal to NFC. `norm` tests cover precomposed and
combining macrons and breves, `æ`/`œ`, `j`, and unchanged `v`. `usfx-bcv`, `ordinal` and
work/section/line template fixtures round-trip. The manifest reuses refs after an
unrelated insertion, reports edited, inserted, duplicate and removed passages as review
items that change nothing until approved, and exits 3 on `--approve-reuse` of a retired
ref. An unchanged source with repeated lines reruns with exit 0 and byte-identical files.
Inject interruptions before manifest replacement, between manifest and corpus replacement,
and after corpus replacement. Rerunning the same approved request recovers to the same
bytes as an uninterrupted run, including duplicate passages, removed refs and `next_ref`;
no approval is consumed twice and no ref is allocated twice. While recovery is pending,
a different source, descriptor, corpus ID or approval set exits 4 (`binding_drift`) without
changing either file. A held corpus or shared manifest lock exits 4 (`busy`), including
two output paths using the same manifest; aliasing either output to an input or lock is
rejected. Recovery also works on first creation when the previous corpus was absent.
Segmentation fixtures cover each tokenizer and segmenter rule, `continues`/`continued`,
`" : "` spacing and non-ASCII offsets. A drift test compares regenerated JSON Schemas
with `docs/schemas/`.

### USFX Normalization

`corpus normalize --adapter usfx` supports `usfx`, `book@id` as container or empty
milestone, `h`, `c@id|n`, `v@id|n` in milestone (`<v/>...<ve/>`) and container form, `ve`,
`p`, `q` and `wj`. `wj` and `<w>` attributes are recorded in `source_markup` spans, text
kept. Notes (`f`, `x`, `fe`) and headings (`s`) leave `text` for passage `notes` and
`headings`, with descendants flattened and not checked as unknown; a heading attaches to
the next passage. `h` becomes `work.title`; IDs stay strings (`3a`). Unknown elements fail
with a diagnostic listing names and counts, unless `--allow-unknown` keeps them in
`source_extra`. XML is untrusted: stdlib `xml.parsers.expat` parsing rejects a DOCTYPE,
entity declarations and external entities (exit 3, `unsafe_xml`) and limits input to 64
MiB and element depth to 64 (exit 3). No XML dependency is added.

`data/lat-clementine.usfx.xml` is repository-only, not in the wheel or sdist. The
committed `data/lat-clementine.descriptor.json` gives edition "Biblia Sacra Vulgata
Clementina", publisher "eBible.org", url "https://ebible.org/find/details.php?id=latVUC"
and license "Public Domain"; `docs/license-compatibility-audit.md` records the provenance.
Other inputs, including installed users' paths, use `--descriptor FILE` or null fields.

`preview --usfx`, `generate --usfx`, `cloze` (USFX, txt, CSV) and `validate --usfx` keep
their options and byte-identical stdout and files. After the goldens, the USFX code moves
from `cli.py` into the adapter module (red/green TDD). Legacy commands call its
`legacy_projection`, which reproduces `parse_usfx_to_df` exactly (lenient tags and
attributes, note and heading text inline, fragments joined with a space, duplicates kept,
empty verses dropped, integer references, book-ID sort) plus the XML hardening; rejecting
unsafe XML or inputs exceeding the size/depth limits is the only intended legacy change.
Strict structural validation is for `corpus normalize` only. `cloze --corpus-format`
gains `jsonl`, which `auto` now picks for `.jsonl`
(previously `txt`). Each JSONL passage is one context with `ref` = `citation.display`, and
`translations[].language` becomes `translation_<language>` for `--translation-lang` and
`--parallel-mode`.

Acceptance: synthetic fixtures cover milestone and container books and verses, `c@n`,
`p`, `q`, `wj`, `w` attributes, nested `f`, `x`, `fe`, `s`, a `3a` verse, a duplicate
verse (error), an unknown element (failure, then `--allow-unknown`), non-NFC input, and a
DTD, an entity declaration, depth over 64 and size over 64 MiB (exit 3). GEN 1:1-5 match
a committed golden. Ref fixtures cover literal dots, percent signs and non-ASCII
components: `%2E`, `%25` and UTF-8 `%C3%A9` survive corpus validation; bare `%`, lowercase
`%2e` and incomplete `%2` are rejected. A raw `%2E` component encodes as `%252E`, distinct
from a raw dot. One module-scoped test normalizes the full bundled file and asserts
source SHA-256 `05bcb3f669d9b36deab6cf26950b8a24c7609b292e5af1abfa51717677701950`, 73
works, 1,334 chapters, 35,809 passages, no duplicate IDs, a passage-ID set equal to an
independent regex scan, and a committed output digest; it records its duration against a
15 s CI budget, asserts under 60 s, and skips under `MUTANT_UNDER_TEST`. Source bytes
never change. Goldens and existing USFX tests pass after rewiring, except unsafe or
oversized/deep XML inputs (exit 3), and legacy commands demonstrably call
`legacy_projection`. A `cloze --corpus x.jsonl` golden covers `ref`, translation columns
and `auto` detection.
`[tool.mutmut].also_copy` lists `data/`, asserted by the mutation-config guard.

### Sidecar Annotation Model

Annotations are an append-only `latinitas-annotations` stream of proposals beside the
corpus. Each record has an `annotation_id`, a `layer` (`segmentation`, `morphology`,
`translation` or `correction`), an anchor, a `value`, optional `alternatives`, a
`producer` `{kind, name, version}`, an `input_hash` (the anchor's `passage_hash`), an
optional `confidence` (integer 0 to 1000, provenance only, never a review status),
`created` and `plan`. A `correction` proposes a corrected source reading for a passage
span; sources are never edited. Replacing a proposal is a `supersede` naming its
`annotation_id`; superseded or retracted records stay, flagged by later records. Writers
skip a record whose `annotation_id` is present. `syntax` arrives in v0.5.0.

`annotations segment` is the only built-in producer and the only writer outside
plan/apply; it appends only `rule` segmentation records, one per passage, with sentences
and tokens. Morphology and translation enter only as imported patches; morphology values
are schema-validated maps with a declared `tagset` string whose contents are not modelled.

Anchor states (Fixed Contracts) are reported by `annotations inspect` and `corpus
validate`; `corpus show` and every other consumer omit such annotations, and nothing is
re-anchored. Review reuses the v0.2.1 claim-decision contract through claim sidecar
version 2: `claims list|record|inspect` accept a corpus with `--annotations SIDECAR`,
keeping statuses, stale and unmatched reporting, reviewer and reason, batch JSON and no
approve-all. `corpus show` is a bounded read-only view, not an enriched export.

New writers take `<file>.lock` with `fcntl.flock(LOCK_EX | LOCK_NB)` (contention: `busy`,
exit 4), validate, and replace atomically through a same-directory temp file with `fsync`
and `os.replace`. Like `phrase_inputs.save_selections` (T-084 S-001), they reject outputs
aliasing sources, corpora, manifests, sidecars or locks directly, by symlink or by hard
link. `claims record` keeps its blocking lock.

Acceptance: `annotations segment` keeps `annotation_id`s across `--timestamp` values and
is byte-identical on reruns with one timestamp; reapplying a patch, or replanning and
applying an identical one, adds no record. Editing one word of a fixture passage makes
its annotations `stale` in `annotations inspect --check` (exit 1) and `corpus validate
--annotations` and hides them from `corpus show`, leaving other passages untouched.
Superseding a segmentation orphans dependent token annotations. A corpus annotation
accepted through `claims record` shows as accepted in `claims inspect` and `corpus show`
and turns stale with it. The characterization v1 claim sidecars load unchanged and their
CSV exports match the goldens; deck commands reject a v2 file (`unsupported_version`).
While the test holds the lock, `annotations apply` and `segment` exit 4 (`busy`) with no
byte change. Alias targets are rejected, and a failure injected before replace keeps the
previous sidecar. A `fixture-morph/1` patch imports with full provenance; no test
imports CLTK, Stanza or an LLM client.

### Agent-Ready CLI Contract

The contract covers the new `corpus`, `annotations` and `policy` groups. `claims` keeps
its v0.2.1 JSON shape, codes and exit behaviour (failures exit 1) for deck and corpus
inputs, except the explicit corpus-mode option rejection below (`--value`, `--evidence`
or `--selected-sense` exits 3; invalid batch items still exit 1). Click usage errors
retain exit 2. Its envelope retrofit is deferred with other legacy commands. Text is the
default; `--json` prints exactly one `latinitas-cli-result` document on stdout, with
warnings as `severity: "warning"` diagnostics. Identical existing output is a no-op (exit
0); plans and receipts with different bytes are refused (exit 3, `exists`). Only `corpus
normalize` (corpus and manifest, after reconciliation succeeds), `annotations segment` and
`annotations apply` (sidecar) advance files in place. Diagnostic codes are a closed,
documented enum. Envelope (`item` is a patch index, `ref` a fingerprint or ID; nullable):

```json
{"format":"latinitas-cli-result","version":1,"command":"annotations apply","ok":false,
 "exit_code":4,"diagnostics":[{"code":"binding_drift","severity":"error",
 "message":"sidecar differs from the plan base; re-plan","item":null,
 "path":"vulgata.annotations.jsonl","ref":"plan:sha256:3f2a..."}],"result":null}
```

Annotation changes flow through patch, plan, approve and apply. `annotations plan`
classifies each operation `auto`, `review`, `deny` or `invalid` with reasons, binds the
corpus header, sidecar, policy and patch digests, records the effective `receipt_actor`,
always writes `--output`, and exits 1 if any operation is `invalid`, else 0. `annotations
approve` follows `managed approve`'s rules (explicit operation IDs, review text, no
approve-all), also requires `--operation` and a declared `--actor`, writes the receipt to
`--output`, and exits 5 (`denied`) for a `deny` and 3 for an unknown or invalid operation.
`annotations apply` rechecks the corpus header, policy and patch digests and accepts the
sidecar if it matches the plan's base digest or every record appended since names this
`plan_id`; otherwise it exits 4 (`binding_drift`) writing nothing. A plan with an invalid
operation exits 3. Apply appends `auto` and receipted operations atomically, warns
`denied` for `deny` operations, and reports pending `review` operations and
`already_applied` runs, with exit 0. It never records a claim decision or touches managed
destination state, CSV exports or Anki files.
Before any append, apply also performs the locked safety revalidation in Fixed Contracts
**Apply-time safety**. Same-plan suffix acceptance is not permission to use obsolete
routing facts.

`latinitas-cards --version` prints `latinitas-cards <version>`. `corpus config` reports
tool version, supported format versions, resolved paths, input and policy digests, rule
versions and each value's origin (`default`, `file` or `flag`); there is no project file.
Prompts anywhere in the CLI are allowed only behind the shared `_is_interactive()` check
(stdin and stdout are TTYs); `setup` also skips them under `--non-interactive`, and new
contract commands never prompt. A needed but disallowed prompt exits 2 with
`prompt_required` naming the flags that supply the answer, or follows the documented
default (`cloze --parallel-mode prompt` ignores translations with a warning). Other
existing commands keep their exit semantics and output; their JSON retrofit is left to a
later release.

Acceptance: a parametrized CliRunner test triggers each exit code that
`docs/agent-cli-contract.md` lists per contract command; every `--json` run reaching the
callback emits one schema-valid document, and Click parse errors exit 2 without one. The
diagnostic registry equals the documented table and covers every code raised by the
`corpus`, `annotations` and `policy` modules. A static test asserts every `typer.prompt`,
`typer.confirm` and `input(` call in `src/` is guarded by `_is_interactive()`. With stdin
`DEVNULL` and a 20 s timeout, `setup` needing a field choice or confirmation exits 2
naming the flags, `setup --confirm` succeeds, and `cloze` with a parallel CSV warns and
ignores translations. `corpus normalize`, `annotations plan` and `annotations apply` give
byte-identical outputs in two subprocess runs with different working directory, `TZ`,
locale and `PYTHONHASHSEED`, free of absolute paths, hostnames and clock values. Apply
after a foreign sidecar or corpus change exits 4 with no byte change; `auto` operations
then the same plan with a receipt both apply; a rerun reports `already_applied`.
`--version` matches package metadata; `corpus config` shows all three origins.

### Policy-Gated Agent Automation

v0.3.0 gates sidecar writes, not linguistic acceptance. A `latinitas-policy` file
(`--policy`, rules in Fixed Contracts) is not part of the deck profile, never enters claim
fingerprints, and never invalidates review decisions or note and card identity. `auto`
applies only to `add` operations and only appends annotation records; `supersede` and
`retract` are at least `review`, and `auto` never writes a claim decision or bypasses
`claims record`. A threshold, `min_confidence` or calibration field makes the policy
invalid (exit 3); calibrated auto-acceptance is v0.5.0 scope.

Destructive operations (`supersede` or `retract` of an annotation with an accepted or
withheld decision or with dependents) and conflicting ones (two operations, in a patch or
against the sidecar, proposing different values for one anchor and layer from the same
producer) are never `auto`. Receipt actors are declared, not authenticated. Each applied
record names its producer, `input_hash` and plan.

Acceptance: a parametrized truth table over operation, layer, producer kind, destructive
and conflicting asserts route and reasons for each combination, including the default
policy, first-match ordering and `deny` precedence. `policy validate` and `annotations
plan` reject a threshold field and `auto` for `supersede` or `retract`. No route yields
an accepted claim. The same invalid patch is rejected with the same codes whether its
producer kind is `human` or `agent` and whether a `human:` or `agent:` actor approves. A
batch with one invalid operation leaves the sidecar byte-identical. An `agent:` receipt
is refused under the default policy (exit 5, `actor_refused`). `annotations inspect`
resolves each applied record to its passage, source digest, producer and plan.
After planning a retract with no decision, record an accepted decision, then separately
a withheld decision (including a stale binding): apply with the old receipt exits 4
(`binding_drift`), changes no sidecar bytes, and requires re-plan/re-approve. A
same-plan-tagged suffix introducing a dependent before a pending retract or a conflict
not represented in the patch likewise exits 4 on the next apply; a foreign append still
fails the existing base check.
Removing a decision, dependent or conflict must not downgrade an old plan to `auto`.
An unrelated decision change that leaves the pending operations' safety facts unchanged
does not invalidate the plan. An absent claims file means no decisions; an unreadable,
malformed or v1 file exits 3, not an empty decision set. Holding the claims lock makes
apply exit 4 (`busy`) without writes; a concurrent `claims record` cannot change the
decision snapshot between revalidation and sidecar replacement. An unchanged partial
apply followed by its receipt and an already-applied rerun still succeed.

## Fixed Contracts

**Terms.** A corpus is one edition of one or more works in one input file set
(`corpus_id`); a work is a citable text inside it (`GEN`); a passage is the smallest
source-native citable segment (verse, paragraph, line); sentences and tokens are derived
`segmentation` content, not identity; a corpus source file is immutable input bytes,
unlike deck "source records" (`sources.py`).

**Identity and hashing.**

- `corpus_id` matches `^[a-z0-9][a-z0-9-]{1,62}$`, set by `--corpus-id`, kept in the header.
- `native_ref` matches `^(?:[A-Za-z0-9._-]|%[0-9A-F]{2})+$`: `%` occurs only in
  uppercase two-hex-digit escapes. Encode source components once from their NFC UTF-8
  bytes, leaving only ASCII `[A-Za-z0-9_-]` literal, then join with literal `.` separators.
  USFX: `<book>.<chapter>.<verse>` (a source `.` becomes `%2E`, `%` becomes `%25`,
  `é` becomes `%C3%A9`; `3a` stays `3a`). Validators check the encoded spelling, never
  decode/re-encode IDs. Plain text: manifest refs, or the encoded line label under
  `--citation-template SCHEME:UNIT.UNIT...` (for example `wsl:work.section.line`), where
  each line is `LABEL<TAB>text`; split the raw label on `.`, require one non-empty
  component per unit, then encode each component as above. Citation values remain raw
  NFC strings. Without a `work` unit the single work is `--corpus-id`.
  Manifest refs use scheme `ordinal` with parts `[{unit: "passage", value: "p000001"}]`.
- `passage_id = corpus_id + ":" + native_ref`: case-sensitive, NFC, at most 256 bytes.
  A duplicate `native_ref` in one corpus is an error.
- Canonical `text`: source orthography, NFC, each Unicode whitespace run replaced by one
  U+0020, trimmed (`text_canon: 1`). `passage_hash = "sha256:" + hex(sha256(utf8(text)))`.
- Structured digests hash canonical JSON (`sort_keys=True, ensure_ascii=False,
  separators=(",", ":"), allow_nan=False`) with a `sha256:` prefix; hashed records hold no
  floats. Existing checkpoint, manifest and claim digests are untouched.
- `annotation_id` digests the record without `annotation_id`, `created` and `plan`;
  `segmentation_id` is the `annotation_id` of a passage's segmentation record;
  `operation_id` digests a canonical patch operation; `plan_id` digests the plan body.
- `producer.kind` is `rule`, `analyzer`, `agent`, `llm` or `human`; `producer.version` is a
  non-empty string; `annotations segment` uses `{rule, latin-seg, "1"}`. Policy `producer`
  globs match `name`.
- `latin-fold/1`: NFC, NFD, strip combining marks, casefold, then `æ` to `ae`, `œ` to `oe`,
  `j` to `i`; `v` stays. `norm` never feeds IDs or hashes.
- `latin-tok/1`: tokens are maximal runs of `[\w\u0300-\u036F]+` (Python `re`, Unicode)
  or a single `[^\w\s]` code point, with code-point offsets `[start, end)` into `text`.
  The executable Python pattern is `r"[\w\u0300-\u036F]+|[^\w\s]"`.
  Enclitics stay in their word token; an apostrophe is its own punctuation token
  (including U+0027 and U+2019). For example `d'arma` yields `d`, `'`, `arma`.
- `latin-seg/1`: a sentence ends after a `.`, `?` or `!` token plus any directly
  following `"`, `'`, `)`, `»` or `”`. `:` and `;` never end one; there is no
  abbreviation list. A passage end without a terminator sets `continues: true`, and the
  next passage's first sentence in the same `work` sets `continued: true`.
- Anchor `{passage_id, passage_hash, segmentation_id?, span?}`: hash mismatch is `stale`,
  superseded segmentation `orphaned`, missing passage `unmatched`.

**Versioned documents.** Every JSON document has top-level `format` and `version` keys,
and a JSONL stream's first line carries both plus `"record": "header"`. Files hold
canonical JSON (the digest rules), one record per line ending in `\n`. Versions are
strict integers (Pydantic strict mode rejects `1.0`); an unknown format or higher version
exits 3. Names, each prefixed `latinitas-`: `corpus`, `corpus-manifest`,
`corpus-descriptor`, `annotations`, `annotation-patch` (`add`, `supersede`, `retract`),
`annotation-plan`, `annotation-receipt` (`plan_id`, operation IDs, actor, review text),
`policy` and `cli-result`. JSON Schemas generated from the Pydantic models
are committed under `docs/schemas/` with a drift test.

**Corpus records.** Header: `corpus_id`, `language` (BCP 47, `--language`, default `la`),
`text_canon`, `norm_rules`, `adapter` (`usfx/1` or `text/1`), `source: {file_name,
sha256, bytes}` (basename only), and descriptor `edition`, `publisher`, `url`, `license`
(else null). `corpus`: `corpus_id` and descriptor `title`, `period`, `register` (free
strings). `work`: `work`, `title`, `order`. `passage`: `passage_id`, `work`, `native_ref`,
`order`, `citation`, `text`, `norm`, `passage_hash`, optional `translations: [{language,
text, provenance}]`, `notes`, `headings`, `source_markup`, `source_extra`.

**Claim sidecar version 2.** `{"version": 2, "decisions": [...]}` with no `format` key
(a v0.2.1 document family, exempt from the format rule). Each decision is the v1
`StoredDecision` plus `binding: {"kind": "corpus", "corpus_id", "passage_id",
"passage_hash", "annotation_id", "layer"}`. A corpus claim fingerprint is unprefixed hex
`sha256` of canonical JSON of `{annotation_id, layer, value, anchor, producer}`; claim
kinds are the annotation layers. `--value`, `--evidence` and `--selected-sense` exit 3 in
corpus mode. Deck fingerprints, the v1 schema and its serializer are unchanged; deck
sidecars stay v1, corpus sidecars are v2, and deck commands reject v2 with
`unsupported_version`.

**Files.** Default names; commands take paths explicitly. Corpus, plan and receipt:
`--output FILE`. Manifest: `<output-stem>.manifest.json` or `--manifest FILE`. Sidecar:
`<corpus-stem>.annotations.jsonl`. Corpus claim decisions: `<corpus>.claims.json` (the
v0.2.1 `sidecar_path` rule), version 2. Linux and macOS are supported; Windows is not.

**Runtime rules.**

- With no manifest, the first normalization of an ID-less source allocates `p000001`...
  in document order for every passage, duplicates included, and writes the manifest
  without approval flags or a scope. Later runs reconcile as described; unresolved
  review items exit 1 and write nothing. The manifest is replaced before the corpus.
  `--manifest` or approval flags with `--adapter usfx` or `--citation-template` exit 2.
- Manifest-backed normalization is a recoverable two-file commit, not a claim of atomic
  visibility across two paths. Hold both `<output>.lock` and `<manifest>.lock` from
  reading the old state through both replacements (all multi-file locks acquired in
  lexical resolved-path order, nonblocking; contention exits 4 `busy`). Never unlink
  lock files. Reject direct, symlink and hard-link aliases among outputs, inputs,
  descriptor and locks before writing; the intended replacement of each output itself
  is allowed. Validate reconciliation and stage/fsync both target files before replacing
  either; fsync each parent directory after its replacement.
- The manifest persists the ordered ref assignments, retired refs, allocator state and
  a required `materialization` object with `request_digest`, `corpus_digest` and
  `previous_corpus_digest` (null for first creation). The request digest covers raw source
  digest and basename, corpus ID, adapter/rule versions, language, descriptor content and
  canonicalized approval flags (reuse pairs sorted by ordinal/ref, allocation ordinals
  and removal refs sorted; contradictory/duplicate flags rejected before committing),
  never filesystem paths or timestamps. Corpus digests cover file bytes.
  This object is the last committed transition receipt, retained after success; no third
  journal file or new command is required. Do not advance/reconcile a manifest whose
  corpus does not yet match `corpus_digest`.
- If the corpus is absent or matches `previous_corpus_digest`, an identical request may
  rebuild the corpus using the manifest's committed assignments, verify `corpus_digest`,
  and replace only the corpus. Do not reapply approvals or advance `next_ref`. A different
  request, unexpected corpus bytes, or failure to reproduce the committed digest exits
  4 `binding_drift`, leaving both files unchanged. If the corpus already matches the
  target digest, an identical request is a byte-identical no-op (even with the original
  approval flags); a new request may reconcile normally. Before the manifest replacement
  a failure leaves both old files; after it a failed corpus replacement leaves the new
  manifest and old/absent corpus, reports failure, and instructs the caller to rerun the
  identical request (expected filesystem errors: exit 3 `unreadable`). Temporary files
  are cleaned on handled failures; orphan temps after process interruption are never
  interpreted as committed state. Read-only corpus consumers see the complete old or
  new corpus and do not need the manifest. Ref identity never rolls back or reallocates.
- For a new annotation record, `created` comes from the patch, `--timestamp` (RFC 3339
  UTC) or `SOURCE_DATE_EPOCH`; with none, its writer exits 2 (`timestamp_required`).
  A no-op rerun needs no timestamp; normalization and planning do not require one.
  `created` enters no ID digest; file and plan digests cover bytes.

**Commands.** Positional primary input, text by default, `--json` for the envelope.

- `latinitas-cards --version`; `corpus normalize SOURCE --adapter usfx|text --corpus-id
  ID --output FILE [--language TAG] [--descriptor FILE] [--manifest FILE]
  [--citation-template T] [--approve-reuse N=REF]... [--approve-allocation N]...
  [--approve-removal REF]... [--allow-unknown]`
- Read-only: `corpus validate CORPUS`, `corpus show CORPUS [--passage ID]... [--limit N]`
  (default 20, maximum 1000), each with `[--annotations SIDECAR] [--claims SIDECAR]`;
  `corpus config [--policy FILE] [--corpus FILE]`
- `annotations segment CORPUS --output SIDECAR [--timestamp T]`; `annotations inspect
  SIDECAR --corpus CORPUS [--claims SIDECAR] [--check]`
- `annotations plan PATCH --corpus CORPUS --sidecar SIDECAR [--policy FILE] --output
  PLAN`; `annotations approve PLAN --operation ID... --actor human:<id>|agent:<id>
  --review TEXT --output RECEIPT`
- `annotations apply PLAN --corpus CORPUS --sidecar SIDECAR [--policy FILE]
  [--receipt RECEIPT] [--timestamp T]`
- `claims list|record|inspect CORPUS --annotations SIDECAR ...`; `policy validate FILE`

**Exit codes** for contract commands; precedence when several apply is 3, 4, 5, then 1.
The per-command matrix lives in `docs/agent-cli-contract.md`.

| Code | Meaning | Example diagnostic codes |
| --- | --- | --- |
| 0 | Success, including no-op rerun, pending review, `already_applied` | warnings |
| 1 | Check or validation findings | `stale`, `orphaned`, `unmatched` |
| 2 | Usage, prompt or timestamp needed (Click errors: no envelope) | `prompt_required` |
| 3 | Input rejected: unreadable, invalid, unsafe, unsupported, output exists | `exists` |
| 4 | Stale or conflicting state: binding mismatch, busy writer | `binding_drift`, `busy` |
| 5 | Refused by policy or review gate | `denied`, `actor_refused` |
| 70 | Internal error, never used for expected failures | `internal` |

**Policy.** `latinitas-policy` version 1 holds `rules`, an ordered list of `{operation:
add|supersede|retract|*, layer: <layer>|*, producer_kind: <kind>|*, producer: <glob>,
action: auto|review|deny}`, and `receipt_actor: human|any` (default `human`, which
refuses `agent:` receipts). First match wins; the default action is `review`; with no
policy file `add` is `auto`. `auto` is valid only for `add`; a rule granting `auto` to
`supersede` or `retract` is invalid. Destructive and conflicting operations are never
`auto`: a matching `deny` still denies, otherwise they route to `review`. Unknown fields,
including any threshold or calibration field, make the policy invalid.

**Apply-time safety.** No claims digest is added to the plan. Plan and apply read corpus
decisions only from `<CORPUS>.claims.json`; accepted or withheld decisions matching
`binding.annotation_id` count for destructiveness even if stale. Absence means no
decisions; an unreadable/malformed file exits 3 (`unreadable`/`invalid_sidecar`) and v1
exits 3 (`unsupported_version`). Apply holds `<CORPUS>.lock`, the annotation sidecar lock
and the claims file's existing `.lock` (exclusive, nonblocking, same multi-lock ordering
as above) from reading current state through revalidation and replacement. Creating
these lock files is permitted even when the claims file is absent; neither the corpus,
claims file nor its decisions are written. The corpus lock serializes apply with
normalization; the sidecar lock serializes it with other annotation writers.
`claims record` retains its blocking lock on that same path.

For every not-yet-applied operation, recompute validity, route and safety facts against
the current corpus, current effective sidecar, entire embedded patch and current claim
decisions. Persist the plan-time `safety` facts per operation: `decision_status`
(`accepted`, `withheld` or null; null for add), `dependents` (sorted dependent annotation
IDs; empty for add), and `conflicts` (sorted conflicting annotation IDs). At both plan
and apply, include records proposed by other patch operations when computing dependents
and conflicts; deduplicate by annotation ID so an expected record later present in a
same-plan suffix does not change the facts. This also prevents an earlier append in one
batch from bypassing the safety check for a later operation. Compare these facts and
route with the plan, not just whether the result is still `review`. Any changed
fact/route or newly invalid pending operation exits 4 (`binding_drift`) for the whole
batch, before any append; old receipts cannot authorize the changed context. Re-plan
and, where needed, re-approve. Unrelated decisions
do not invalidate a plan. Already-applied records are not re-applied or re-routed, and an
operation's own already-present annotation is not a new conflict. Preserve deny
precedence and receipt-actor checks; do not silently downgrade a route, accept a new
conflict, or promote an old receipt. Same-plan partial retries and no-op reruns remain
supported when these pending-operation checks pass.

## Caution

- Hash and canonicalization drift (NFC, whitespace, JSON separators, algorithm) silently
  invalidates every anchor and decision; golden hashes pin each format version.
- Combining marks, `æ`/`œ`, `i`/`j`, `u`/`v` and spacing such as `" : "` affect tokens;
  folding belongs only to `norm`. Clementine versification differs from other Bibles,
  and no citation is mapped across corpora.
- Large corpora are streamed; `fcntl` locks are POSIX-only; corpus XML is untrusted;
  redistributed corpora need licence notices.
- Clock values, dict order, locale sorting and absolute paths break byte-identical reruns.
- A crash before replace leaves the previous sidecar intact; a plan against a foreign
  sidecar change is stale, not merged.

## Recommendation About LLM Support

v0.3.0 adds no LLM integration; `annotate --use-llm` is not wired into sidecars. LLM output
enters only as an imported patch with `producer.kind: llm` and a named model, under the
same provenance, policy and review contract as other producers. Core commands stay
offline and provider-independent.

## Explicitly Excluded

- TEI XML ingestion and corpus-first card generation (v0.4.0).
- Syntax annotation (v0.5.0), confidence calibration, or automatic linguistic acceptance.
- Enriched corpus export formats (v0.6.0) and project layout or bundles (v0.7.0).
- Cross-edition alignment, network download adapters and required hosted services.
- Direct Anki integration, Windows support, a TestPyPI stage, and Anki-facing changes.
- JSON retrofit of legacy commands, left to a later release.
