# LatinitasCards v0.6.0

## Summary

Planned release. Adds optional direct Anki integration and broader interoperability while
keeping file generation as the canonical auditable workflow and all network access explicit.
Carry v0.5.5's complete morphology baseline through every supported transport and template;
nouns, adjectives and related forms must not become second-class or verb-only on import.

## Planning Status And Dependencies

Planned and inactive, after v0.5.5. The morphology requirements reuse
[v0.5.5's coverage matrix](v0.5.5.md#complete-morphology-coverage), v0.5.1's nominal
roles and explicit upgrades, and v0.5.0's shared acceptance/managed-update contracts.
This revision does not change their approvals, activate a release or authorize Anki writes.
Technical contracts require design approval before dependent implementation; the acceptance
requirements below do not create implementation tasks or claim demonstrated transport support.

## Goals

- Apply the same reviewed plans to files or a running Anki instance.
- Preserve note identity, scheduling, user fields, and retirement policy across transports.
- Export enriched corpora and connect cards to optional external lexical resources.
- Add explicit source-download workflows without making core operation network-dependent.
- Preserve full noun/adjective/verb morphology coverage, alternatives and evidence across
  files, enriched corpus exports and optional direct Anki operations.

## Potential Features

### Optional Direct Anki Integration

Read and apply plans through a supported local Anki integration while reusing the established
create/update/unchanged/conflict/retire model. Direct apply requires explicit permission,
never bypasses preview/policy, preserves scheduling, updates only managed fields, and tags
and suspends retired notes rather than deleting them. File generation and auditable
plan/report handoff remain available when direct integration is unavailable or declined.
Lifecycle effects unsupported by file transport, including suspension/retirement, remain
blocked with explicit manual-resolution instructions; emitting a file does not apply them.

### Stable Note-Type And Template Management

Manage the small stable family of recall, parsing, grammar, and context/translation note
types. Preserve v0.1.0's coherent-learning-object notes with conditional sibling cards,
shared personal fields/tags, and independent card schedules. Reuse the established schema
and stable semantic card/template bindings; never repurpose slots or silently consolidate
legacy per-exercise notes. General automated provisioning belongs to this release, while
earlier releases retain their reference templates and explicit migration/capability gates.

### Morphology Parity Across Transports

Reuse the accepted v0.5.5 coverage inventory and recipe applicability, including noun
declensions, adjective agreement/comparison, pronouns/numerals and verbal/non-finite forms.
Do not introduce a second analyzer, weaken acceptance or reclassify a nominal exercise as
a verb principal-part card to fit a transport. Adding a transport must not change an
exercise's semantic identity, accepted alternatives, evidence binding or selected recipe.

Preview/plan, file emission, managed update and direct apply must agree on the semantic
exercise set for the same accepted input and selection. Preserve lexical versus contextual
gender, case/number/degree, class/paradigm metadata, source spans, acceptance provenance and
applicable withheld/unsupported reasons in their defined records. Card payloads retain
their managed fields and inspectable evidence; stage detail stays in the accompanying report,
not forced into visible Anki fields. No transport may silently drop a new morphology field,
collapse distinct analyses or claim human review for automatically accepted content.

Use explicit capability/version checks and migration preview for nominal and other expanded
templates. An old or customized destination that cannot represent an exercise must produce
an actionable conflict/unsupported outcome before mutation; never silently coerce it to an
older layout. Preserve existing verb ordinals, stable identities, personal fields/tags and
scheduling. An approved upgrade must not replace unrelated note types or reset sibling-card
schedules. File output remains available if direct integration is unavailable or declined.

Acceptance: run the same independently accepted noun/adjective/verb and related-form fixture
through file export/import, managed update and direct apply in a disposable Linux Anki
Desktop collection. Cover all v0.5.5 matrix families, common-gender versus agreement gender,
syncretism, comparison, plural-only nouns, participial agreement and defectiveness.
For each advertised transport/version, acceptance evidence must account for every distinct
morphology representation required by the approved inventory, including alternatives,
compound-form agreement, applicability and evidence bindings. Demonstrate preservation or
explicit incompatibility; one example per family does not establish full parity.
Compare semantic exercise sets and provenance against the accepted input, not merely the
two outputs against each other; rerunning unchanged input creates no duplicates or schedule
changes. Inspect German/English, light/dark and collapsed/expanded evidence states with
neutral fronts and accessible non-color cues. Reject incompatible/custom templates before
writing, and test explicit upgrade, partial apply failure, retry and policy-driven retirement
without deleting history. A changed paradigm/evidence policy invalidates dependent claims;
show the resulting explicit update/retirement plan rather than silently retaining stale
accepted labels. Direct writes require separate permission even in acceptance environments.
Declining direct access for a retirement must leave an inspectable pending/manual handoff,
not a report that the file export suspended the installed card.

### Enriched Corpus Export

Export normalized corpus plus selected sidecar annotations to documented JSONL and supported
enriched XML forms. Exports retain source identity, provenance, language tags, confidence,
and review state and can be regenerated without mutating canonical source files.
Document which versioned format carries each morphology field, alternative, construction
span and evidence record. A selected target format must carry the requested semantics
losslessly, including by documented accompanying records, or reject that export as unsupported
before creating a misleading artifact. Do not imply that existing USFX/TEI adapters can
round-trip new annotations without a defined mapping. Unknown/conflicting metadata must
not silently disappear or become accepted during conversion.

Acceptance: export and re-import independently specified noun, adjective, verb and ambiguous
occurrence fixtures through each advertised enriched format/version, accounting for the same
distinct inventory representations required for transport parity. Recover the defined semantic
records, identities, provenance and review state; check source files remain byte-identical.
Missing mappings, unknown schema versions and conflicting alternatives must produce explicit
diagnostics, not a successful but lossy round trip.

### Optional Dictionary Links

Allow recipes or themes to render configurable links for a lemma to external dictionary
resources. Links are conveniences rather than required lexical data. No specific dictionary
or target language is hard-coded into the core model.

### Explicit Source Downloads

Add opt-in download/import commands for supported public corpus sources. Downloads record
URL, retrieval metadata, checksums, and licensing/provenance information. Core deck and
corpus processing remains offline after inputs are available.

## Morphology Acceptance And Release Requirements

Parity and migration contracts require maintainer approval based on accepted v0.5.5
morphology contracts and v0.5.1 nominal upgrades before dependent implementation. Define
versioned format/field mappings, capability checks, semantic identity/provenance, template
upgrades and partial-failure/retry behavior. Distinguish file-emittable updates from
direct-only/manual lifecycle effects; unsupported mappings must be explicit, not lossy.
Shared template and identity changes must remain consistent across file and direct routes.

Independent integrated acceptance must use the implemented v0.5.5 capabilities and accepted
release evidence to compare matrix/recipe coverage across file, managed, direct and
advertised enriched-format routes. Include unknown versions, conflicting/lossy mappings,
unchanged source checksums, policy drift, safe retry/retirement and German/English native
states. Preserve identities, schedules and personal fields. Publish actual results and
unsupported versions; silently missing representations preclude a full-parity claim.

Capture supported Anki/integration versions, reference rights and access to a disposable
native environment before acceptance. Direct writes require separate permission. Missing
access leaves the direct route unverified; a file-only pass cannot stand in for it.
Whole-release readiness must include this evidence alongside integration/export/download
checks. A maintainer must accept readiness and separately authorize publication; no task
status or transport comparison grants either permission. Implementation decomposition and
activation remain separate work.

## Caution

- Direct Anki integration introduces version, availability, and partial-failure concerns.
- An applied operation must be recoverable or safely retryable.
- Note-type migrations can affect many unrelated notes if not namespaced and scoped.
- Download support must not imply permission to redistribute source texts.

## Recommendation About LLM Support

No change to the optional provider-independent policy. Direct Anki access does not grant an
LLM authority to write outside an approved plan or disclose deck content to a provider.

## Explicitly Excluded

- Making direct Anki integration mandatory.
- Silent background synchronization.
- Deleting user notes or review history.
- Bundling proprietary dictionaries or corpora.
- Network-required core workflows.
- Silent morphology loss, verb-only template shortcuts or transport-specific relaxation of
  the v0.5.5 coverage and acceptance baseline.
