## 2. Proposed public commands and profile

All commands are under `latinitas-cards`. Proposed group `pipeline` has these commands:

| Command | Contract |
| --- | --- |
| `run --profile FILE --output DIR` | Orchestrates ingest → analyze → propose → counter-check → decide → select → render → export. |
| `stage NAME --run DIR` | Exposes one stage with the same prerequisite checks; cannot bypass decision eligibility. |
| `validate`, `report` | Never call providers. |
| `preview --profile FILE --run DIR` | Read-only rendered preview of stored results and withheld reasons; no provider calls, export, identity allocation or approvals. |
| `export --run DIR [--after-receipt H]` | Only selects/renders stored eligible decisions; without predecessor requests the initial batch, with predecessor requests its successor. Repeating either request replays that batch (section 5). |
| `resume --run DIR` | Resumes deferred/failed work within renewed explicit limits, not unknown calls. |
| `reconcile-call` | Resolves unknown calls under section 6. |
| `adapt`, `migration-plan` | Provide the adapters and migration planning described below. |

Output files do not authorize Anki application.

Proposed `curated` group has `validate`, `preview`, `review`, `export`; review takes an explicit decision file, never approve-all by default. `pipeline adapt --kind human-claims|phrase-inputs|phrase-plan|corpus-facts` produces bound internal records. `pipeline migration-plan` reports an opt-in layout change and the required manual installation steps; it never replaces templates. CLI options override matching profile settings only when explicitly supplied. Every command prints the effective configuration and records it in the report.

New format `latinitas-pipeline-profile`, version integer 1, contains exactly these required keys:

| Key | Type / rule |
| --- | --- |
| `format`, `version` | Constants above; strict JSON, unknown keys forbidden. |
| `deck_profile` | `{path: string, sha256: H}`; existing validated profile, no credentials. |
| `inputs` | Nonempty array of `{kind: deck\|phrases\|corpus\|curated, path: string, sha256: H}`. |
| `language` | `de` or `en`; missing variant is not an instruction to translate. |
| `preset` | `grammar-study` or null; saved with language and resolved recipes. |
| `recipe_overrides` | `{include: [string], exclude: [string]}`; disjoint unique known identifiers. |
| `recipes` | Unique ordered recipe identifiers; default resolved list is translation only for supported forms/phrases/PPP. |
| `selection` | `{patterns: [string], entries: [string], variants_per_binding: positive integer, output_limit: positive integer\|null}`. Empty filters mean all available supported input, not an empty output. Default variants=1, output_limit=null. |
| `processing` | `{max_source_units: positive integer\|null, max_calls: positive integer, max_tokens: positive integer, timeout_seconds: positive integer, retries: nonnegative integer}`. Defaults below; null source limit means all selected units. |
| `providers` | `{proposal: Endpoint\|null, counter_check: Endpoint\|null}`; both null means LLM-off. |
| `policy` | `{id: string, version: string, sha256: H}`; only approved class/stratum policies can enable automatic acceptance. |
| `layout` | `{id: string, version: positive integer, template_sha256: H}`; existing layout or explicitly approved new installation. |

`Endpoint` is `{url: string, provider: string, model: string, locality: local|hosted, credential_ref: string|null}`. Credentials are resolved at runtime and never serialized into a profile/report. URLs cannot contain userinfo or credential query parameters. Record service/model revision from the endpoint; if it cannot be pinned, reusable model results require a recorded immutable deployment identifier or are non-reusable across runs. Same model for both calls is permitted, separate invocations are required. No silent fallback or inferred endpoint.

Recipe registry proposal: `form_translation`, `form_recognition`, `ppp_translation`, `ppp_recognition`, existing `phrase_translation` and `phrase_recognition`, plus opt-in `verb_production`, `noun_declension`, `adjective_declension`, `form_cloze`, `phrase_form_cloze`, `rule_application`, `mnemonic_recall`, `formation_rule_recall`, `component_explanation`. Curated default is rule_application; formation/component/mnemonic recipes are independently selectable. Production/cloze opt-ins do not enable each other. Registry entries define target feature requirements and supported paradigm/pattern versions; unknown recipes are errors, unsupported cells are reported, not fabricated.

`grammar-study` selects verb_production, noun_declension, adjective_declension, formation_rule_recall, component_explanation and mnemonic_recall (four exercise types, production spanning three recipes). Resolution order is defaults or preset → saved overrides → explicit CLI `--include-recipe`/`--exclude-recipe`; conflicting same-level include/exclude is an error. Saved recipes must equal the resolved list; mismatches are validation errors, not silent recomputation. `--save-profile FILE` persists preset, overrides, effective recipes and language without modifying the original implicitly. The preset does not add clozes, all combinations or approvals. Partial eligible output reports absent content/evidence/approvals per recipe. All four types require German/English prompts, reference answers, terminology, explanations, caveats and reports; English CLI controls stay unchanged.

Phrase upgrade proposal:

- `PhraseInput` retains the v1 top-level keys, sets version=2 and adds required `binding: Binding` and `registry_version: string`.
- `Form` adds `source_role: present_1s|present_infinitive|perfect_1s|supine|ppp|other` and `role_evidence: [Evidence]`. PPP requires confirmed mapping and nonempty role evidence.
- `SelectionRequest` retains selections/limits/version, sets version=2, adds `binding: Binding` and changes limits.max_exercises to positive integer|null. Null means no aggregate quota, processed in finite chunks.
- `RecipePlan` retains version/max_exercises/exercises, sets version=2, changes max_exercises to positive integer|null and adds binding/registry_version. It extends Exercise.recipe only to phrase_form_cloze; reference/target validators remain, with a required target and non-meaning distinction for cloze.

v1 Entry/Form/Features/Pattern validators remain authoritative; reuse existing verb feature support rather than reimplement it. New standalone/curated recipes consume shared assertion/task records, not legacy phrase exercises. Down-adaptation requires v1-representable values, explicit finite chunk limits and a separate acceptance binding; otherwise reject. Up-adaptation adds confirmed provenance, never guesses a PPP role.

## 3. Exact proposed record shapes

These are schema proposals, not permissive pseudo-fields. JSON objects have exactly the listed keys; all keys required unless marked `?`. Strings are nonempty unless noted; enum spellings are literal. `H` is a lowercase 64-hex SHA-256; `ID` is a nonempty stable key; timestamp is UTC RFC3339. Arrays are ordered and duplicate-free by their record identity. Null is allowed only where written. Integers exclude booleans. Hashing uses UTF-8 canonical JSON: sorted object keys, compact separators, preserved array order, no floats, no Unicode/macron folding. Hash fields exclude themselves. Hashes establish integrity, not trusted authorship.

Shared nested types:

- `Binding = {source_scope: ID, source_identity: ID, source_sha256: H, extraction_sha256: H, mapping_sha256: H, task_sha256: H, language: de|en, config_sha256: H}`. Source hash covers selected source evidence; extraction hash covers extractor/version/options/results, mapping hash confirmed field/PPP-role mapping. Task hash covers recipe/objective/target/context, not just answer text. Configuration hash covers effective linguistic configuration, not output batch size or theme.
- `Versions = {producer: string, analyzer: string, proposal_prompt: string|null, counter_prompt: string|null, checker: string, comparison: string, policy: string, policy_sha256: H, proposal_model: string|null, counter_model: string|null}`. Values identify immutable code/data/prompt revisions, not mutable aliases. Null prompts/models allowed only on a no-model path.
- `Evidence = {source: string, reference: string, version: string, text: string}` retaining the current Evidence semantics; array cannot be empty for an accepted claim.
- `Assertion = {id: ID, kind: label|segmentation|explanation|translation, value: string, selected_sense: string|null, alternatives: [string], evidence: [Evidence]}`. Translation requires a non-null sense; other kinds require null. Each rendered linguistic assertion, including front presuppositions, examples, caveats and explanation clauses, maps to an assertion ID. Missing mappings block the card; layout-only labels do not manufacture claims.
- `Check = {id: ID, assertion_ids: [ID], method: library|rule|blind_model|semantic_comparison|human, version: string, result: pass|fail|unresolved|not_applicable, evidence: [Evidence], alternatives: [string], objections: [string], input_sha256: H}`. assertion_ids is nonempty. Pass requires no unresolved objection; not_applicable cannot satisfy a required check.

For library/rule/human checks, input_sha256 hashes exactly `{binding: Binding, versions: Versions, method: string, checked_assertions: [Assertion], prerequisite_output_sha256s: [H], reference_constraints: [Evidence]}`. checked_assertions contains the full current records in assertion_ids order, not just IDs. Recompute and verify this commitment on load, reuse and export; changing a value, evidence, alternative or context cannot retain an old pass. The corresponding immutable stage artifact retains this envelope. A blind_model check instead commits to the actual proposal-free model task/request and its response digest; it cannot alone authorize proposed assertions. A subsequent semantic_comparison check uses the full assertion envelope plus required `proposal_output_sha256: H` and `counter_output_sha256: H`, binding both actual outputs after independent solving. Accepted model-assisted assertions require that comparison in addition to the blind check.

Top-level records all include `format`, `version: 1` and the following keys:

| Format | Required keys beyond format/version |
| --- | --- |
| `latinitas-stage` | `run_id: ID, stage_id: ID, stage: ingest\|analyze\|propose\|counter_check\|decide\|select\|render\|export, binding: Binding, versions: Versions, prerequisite_ids: [ID], state: pending\|running\|succeeded\|failed\|cancelled\|unknown\|deferred, input_sha256: H, output_sha256: H\|null, artifact: string\|null, call_ids: [ID], reason: string\|null, started_at: timestamp\|null, finished_at: timestamp\|null`. |
| `latinitas-acceptance` | `decision_id: H, binding: Binding, versions: Versions, assertions: [Assertion], checks: [Check], origin: human\|automatic\|none, state: accepted\|withheld\|failed\|stale, human: {reviewer: string, reason: string, reviewed_sha256: H}\|null, stage_ids: [ID], reason: string, created_at: timestamp`. |
| `latinitas-call` | `call_id: ID, stage_id: ID, endpoint_sha256: H, request_sha256: H, request_artifact: string, response_sha256: H\|null, response_artifact: string\|null, state: prepared\|sent\|succeeded\|failed\|cancelled\|unknown, attempts: nonnegative integer, reserved_tokens: nonnegative integer, used_tokens: nonnegative integer\|null, provider_request_id: string\|null, reason: string\|null`. |
| `latinitas-pipeline-report` | `run_id: ID, profile_sha256: H, effective_profile: profile object, source_units: {selected: nonnegative integer, attempted: nonnegative integer, deferred: nonnegative integer}, stage_counts: object mapping stage states to nonnegative integer, outcomes: [Outcome], calls: [ID], decision_ids: [H], receipt_ids: [H], permission_sha256: H\|null, complete: boolean`. |
| `latinitas-export-receipt` | `receipt_id: H, run_id: ID, previous_receipt_id: H\|null, selection_sha256: H, layout_sha256: H, files: [{path: string, sha256: H}], cards: [ExportCard], ineligible: [Handoff], batch_cursor: Cursor\|null, created_at: timestamp`. |

`Outcome = {source_identity: ID, candidate_id: ID|null, card_key: ID|null, outcome: not_generated|deferred|withheld|processing_failed|accepted_unselected|exported, reason: string, related_ids: [ID]}`. Candidate/card IDs stay null for unattempted source units; never estimate undiscovered candidate counts. Counts for stages, distinct claims, candidate exercises, cards and source units are reported separately, derived from those identities, never summed interchangeably. One failed claim may withhold several cards. Representative examples accompany reason-group counts in the readable report.

`CardRef = {note_id: ID, card_key: ID}` identifies one card instance; card_key remains the existing note-local recipe/role key, never a globally unique note identity. `ExportCard = {note_id: ID, card_key: ID, decision_ids: [H], assertion_ids: [ID], rendered_sha256: H, acceptance: human|automatic|mixed, owned_fields: [string], owned_tags: [string]}`. `Handoff = {note_id: ID, card_key: ID, previous_decision_ids: [H], reason: string, resolution: manual|managed_retained_fields|blocked, required_action: string}`. `Cursor = {selection_sha256: H, ordered_card_refs_sha256: H, emitted_cards: [CardRef]}`. All cross-note membership, deduplication and receipt reconciliation use CardRef; identical slot keys on different notes remain distinct. Receipt files exclude the receipt itself to avoid a circular digest.

Decision and stage invariants:

- Accepted requires complete assertion coverage, all required checks passing, current bindings/versions and no open material objection.
- Automatic requires human=null and a policy approved for every assertion class/stratum.
- New human review requires human non-null and reviewed_sha256=hash(binding, assertions). Its reason/reviewer attest that content rather than the decision digest, avoiding recursion. An adapted legacy review uses the verified projection below; the computed envelope digest records an encoding transformation, not a new review by the historical reviewer.
- Origin none cannot be accepted. Mixed cards refer to multiple decisions; a single decision has one origin.
- Failed provider/parse work has state failed, not linguistic rejection. A stale success cannot authorize export.
- Unsupported claims cannot be accepted by agreement or human override without supported replacement evidence.
- Output hashes/artifact paths are non-null only for succeeded stages; a succeeded stage has finished_at. Corrupt/missing artifacts invalidate reuse.

Legacy human projection: a referenced ingest stage stores exactly `{format: "latinitas-human-projection", version: 1, adapter_version: string, source_sidecar_sha256: H, original_claims: [object], original_decisions: [object], corpus_bindings: [object], mapping: [{original_claim_fingerprint: H, assertion_ids: [ID]}], binding: Binding, reviewed_sha256: H}`. The object arrays retain full legacy objects accepted by their original versioned readers, including base fingerprints, authored overrides and corpus bindings; not arbitrary reinterpreted JSON. Reconstruct the actually reviewed claim after v1 overrides, verify its original fingerprint/current acceptance with the legacy reader and exact current corpus binding where applicable, then verify a lossless content projection to each mapped assertion. Preserve separate phrase combination and aggregate-answer approvals, requiring both for affected phrase assertions. No new clause, sense, context, source or alternative inherits authority merely by sharing an ID. Added/unrepresentable content yields unrepresentable_claim or requires fresh review; conflicting proofs fail closed. The stage artifact retains original reviewer/reason and immutable proof; human.reviewed_sha256 equals the verified target envelope digest, not a claim that the reviewer reviewed its new serialization. Projection and human Check artifacts must both be available and valid on reuse/export. M1 requires positive deck/corpus/aggregate-phrase cases and rejection of an added unreviewed clause.

Model protocol: both endpoints return exactly `{format: "latinitas-model-answer", version: 1, task_sha256: H, assertions: [Assertion], alternatives: [string], objections: [string]}`. Proposal and blind inputs have exactly `{format: "latinitas-model-task", version: 1, task_sha256: H, binding: Binding, objective: string, target: object, source_evidence: [Evidence], reference_constraints: [Evidence]}`; target keys/types are the recipe's required feature tuple from the versioned registry. The proposal answer is not an input to the blind task. Model output cannot supply an authoritative decision or policy. Request digests bind the exact endpoint input including immutable prompt version.

## 4. Evidence, comparison and reuse

Analyze source forms/meanings against confirmed mapping and applicable library/rule evidence first. PPP requires an explicit confirmed PPP role; a supine or unspecified fourth principal part does not establish it. No analyzer can repair missing source identity. An eligible no-model path uses sufficient rule/library checks or current explicit human decisions. An unsupported automatic stratum remains withheld even if model checks agree.

For model-assisted acceptance, proposal and blind counter-check use separate requests. The counter-check receives only the source evidence, task, approved reference constraints and required answer schema, never proposal answer/rationale/confidence or a cache derived from them. Persist the actual redacted request body locally for inspection, hash it, and retain a data-scope manifest; a hash alone is not evidence of blindness. Redaction removes credentials, not task/evidence fields. Structured findings, alternatives and objections suffice; do not request private reasoning traces. Compare after both requests succeed; matching output with an open objection is withheld. Same-provider/model correlation remains an evaluation limitation.

| Assertion class | Required checks / comparison contract |
| --- | --- |
| Morphological label / production target | Bound lemma/form/sense and complete requested features; supported paradigm/cell, agreement/government where applicable. Compare canonical feature tuples and cited forms, not capitalization of labels. Contrast amās/amant; puellam/puellārum; bonam/bona. Underspecified tense/mood/voice is not silently filled. |
| Segmentation | Cited segmentation convention, reconstructed surface form, component roles and applicable sound/stem changes. `puell- + -ārum` and `puellā- + -rum` may be legitimate alternatives under separately supported conventions; string inequality is not a failure. No universal concatenation assumption. |
| Translation | Confirmed sense, contextual government/valency, number/person/voice and relevant ambiguity. Compare supported meaning propositions with allowed alternatives, not exact German/English strings. Do not call both readings equivalent merely because their glosses overlap. |
| Explanation | Decompose every factual clause into supported propositions linked to covered assertions; check applicability/exceptions and contradiction against source/reference. A correct label never approves a causal sentence. |
| Controlled phrase | Each constituent plus construction, required features, agreement/government, selected senses and contextual meaning. Preserve defensible readings or withhold a distinction the prompt cannot support. No original-corpus role discovery. |
| Curated rule / rendered card / mnemonic | Mandatory human approvals in section 8; automatic checks only flag problems, never substitute for those approvals. |

Semantic comparison returns equivalent, compatible_alternatives, contradiction or unresolved with cited propositions and open objections. Equivalent/compatible alternatives can pass only if the prompt/reference exposes all relevant supported readings and every assertion passes. The comparison policy is versioned by class; no majority vote or self-confidence threshold. T-185 must establish independently judged reference availability and reliability before T-186 approves automatic strata.

Reuse key is hash(stage name, input digest, binding, versions, prerequisite output digests). Store successful stages immutably. Changed source content, extraction, mapping, task, language, linguistic config, analyzer, prompt, model deployment, checker, comparison or policy invalidates dependent stages and decisions; unaffected dependency branches remain reusable. Withdrawal of a policy invalidates its decisions regardless of stored success. Language changes invalidate translated checks, not an unrelated original-language curated approval. Theme/batch/output-path changes only reselect/rerender; rendered approval may still need renewal. Export revalidates eligibility against current policy/bindings even when a cursor and prior decision are present. Historical human decisions retain their human origin and history; stale binding marks them unusable, never converts them to automatic.

## 5. Deterministic enumeration, limits and continuation

Enumerate a finite registry, not arbitrary cross-products. In source identity order, choose selected supported pattern IDs in lexical order and the explicit compatible entry/sense/form bindings declared by those patterns. For each role tuple, sort form keys lexically; emit at most variants_per_binding surface alternatives, keeping the first supported distinct alternatives under the pattern's versioned ranking. Record suppressed variant keys/reasons. Missing constraints or unsupported patterns yield not_generated, not random samples. Verb mini-clauses require government/valency/agreement and finite forms, extending the existing phrase engine. Standalone targets enumerate only supported selected cells in registry order, never all hypothetical paradigms.

Recipes follow the explicit resolved list. Deduplicate identical CardRef pairs, never raw note-local slot keys across notes. Suppress redundant variants only within the same source scope/object, recipe, target, tested distinction and equivalent accepted assertion set; retain the lexically smallest candidate key and record its suppressed siblings. Never collapse different learning objectives, languages, source identities or legitimate distinctions solely because visible strings match. Accepted-card order is `(source_scope, source_identity, object_key, recipe, target, distinction, candidate_key)` with null targets ordered first.

Limit precedence: validate configuration → enumerate selected source work → apply processing ceilings before requests → decide all completed work → duplicate/redundancy suppression → explicit output limit/batch. Profile and explicit CLI values resolve per key; provider hard limits and permission ceilings cap the result by minimum. No CLI option can widen an existing hosted permission. The report records each effective value and its source. Default output_limit=null exports **all eligible cards**, including >20. Legacy v1 phrase limits remain legacy semantics; the new orchestrator uses bounded chunks and reports unattempted remainder, not hidden output truncation.

Proposed finite defaults: 60 seconds per request, one retry (two total attempts), 200 total provider attempts and 200000 total input+reserved-output tokens per run; maximum output reservation 2048 tokens per attempt, one call in flight. Both proposal and counter-check attempts count. Tokens are checked conservatively before sending; adapters without a reliable upper bound reject the request rather than exceed the cap. Retries reserve fresh budget. max_source_units defaults null. These are operational safety proposals, not measured linguistic thresholds or a promise that all inputs finish. Exhaustion produces deferred source work/stages, not rejected claims or a smaller implicit card quota. Explicit output_limit must be positive; null alone is unlimited.

Batch continuation snapshots accepted ordered CardRefs and records emitted pairs in the receipt cursor. `export --run DIR` requests the initial batch; `--after-receipt H` requests the successor of that exact current-snapshot receipt. Request identity is hash(run_id, selection snapshot digest, predecessor receipt ID or null, effective output limit, layout digest). Repeating the same request returns its prior receipt and identical operation-owned files, including after a lost command response; advancing requires naming the newly returned receipt. Reject stale/foreign predecessors rather than advancing an offset. Successor selection excludes previously emitted pairs only after validating the snapshot, current eligibility and output hashes; it reuses valid completed checks without model calls solely for batching. A changed selection/eligibility requires a new snapshot and explicit reconciliation with previous CardRefs. Concurrent writers fail with run_busy. Under the run lock, stage output files and receipt before atomically publishing the request-to-receipt/cursor pointer; recovery validates staged hashes and completes or rolls back publication before another export. Never overwrite a different batch's files. This is pipeline-local recovery, not portable project bundles/generation locks, and does not allocate new semantic identities.

## 6. Provider permission and recovery

Before network use, show effective proposal/check URLs, provider/model revisions, execution location, selected files/fields, text spans and languages, token/call/time limits, retention behavior and expected outbound data. Hosted runs require `--allow-hosted PERMISSION.json`; this is a local explicit permission record bound to endpoint/config/input/data-scope hashes, expiry and ceilings, not a cryptographic identity claim. Widening scope or changing endpoint requires fresh permission. LLM-off commands make zero provider calls. A loopback URL in an orb is local to that orb, not the user's computer; local-only also requires no hosted extraction or upstream proxy processing. Unknown locality blocks local-only claims. No credentials, personal-note fields or unrelated deck material enter requests; proposal and blind check each receive the minimal task-bound evidence. Text cannot grant tool/file/destination authority. No tools are exposed to the model.

Permission has exactly `{format: "latinitas-hosted-permission", version: 1, permission_id: H, run_id: ID, endpoint_sha256s: [H], config_sha256: H, input_sha256s: [H], data_scope: [{source_identity: ID, fields: [string], spans: [{start: nonnegative integer, end: positive integer}], language: de|en}], max_calls: positive integer, max_tokens: positive integer, timeout_seconds: positive integer, expires_at: timestamp, confirmed_by: string, confirmed_at: timestamp}`. Spans are half-open Unicode codepoint ranges in the bound extracted text; end>start. permission_id hashes the other keys. Actual requests must be a subset of approved fields/spans/endpoints/inputs and within remaining ceilings and expiry; an empty scope never means blanket access. A resumed hosted run requires unexpired permission for new calls. Local retention is permission-scoped run artifacts, owner-readable only, not a claim about provider-side retention; disclose that provider policy before confirmation.

Permission authorizes exactly its persisted run_id. Merely supplying the same permission path for another run is not fresh authorization; reject it and require a newly disclosed/confirmed record for the new run. Resume, cancellation recovery, unknown-call retries and permission renewal for the same run retain one durable consumed/reserved ledger; renewal does not reset spending, and explicit higher total ceilings require new confirmation. Pipeline-hosted proposal/check processing and any hosted lecture-note extraction use this per-run rule; the latter's explicit per-run requirement also comes directly from the spec. The run ID is allocated before confirmation without making provider calls. Copying or renaming a run does not create fresh budget under an old permission.

Persist prepared call journal and token reservation before sending, then sent before dispatch. Write response and digest before marking succeeded. Retry only a known failed transient request (timeout after dispatch is unknown, not safe-to-retry), with one-second bounded backoff and remaining budget. Reject malformed output with processing_failed; no unbounded repair prompts. Cancellation stops new calls, records in-flight state as unknown unless endpoint confirms cancellation before execution, and preserves completed artifacts. Export never treats an interrupted check as success.

`pipeline reconcile-call --run DIR --call-id ID --response FILE` verifies provider request identity, original endpoint/request digest and response schema, retaining the supplied response as evidence. If retrieval is unavailable, `--abandon` records an unresolved attempt and reserved budget; it does not accept it or silently rerun it. Explicit `--retry-unknown` after abandonment warns of possible duplicate processing/billing and requires fresh remaining budget/hosted scope permission. An unknown call remains unknown until this action; resume does not resubmit it. Count abandoned/unknown reservations against ceilings until authoritative token usage is known. No idempotency support is assumed. Missing endpoint, exhausted budget, failure and cancellation appear as distinct report reasons without fallback.

## 7. Anki ownership, layout and ineligibility

Preserve LatinitasID derivation and stable card semantic keys; do not include wording, policy, acceptance, color or mnemonic text in identity. A curated item uses author-controlled item key as object_key in a persisted source scope; recipe/target/distinction identifies its semantic card. Existing notes keep template ordinals. New roles require an explicit append-only slot registry/migration proposal; never reuse an old slot for another objective.

Proposed opt-in layout `acceptance-1` adds managed fields `Acceptance Data` (versioned per-card decision references/status), `Evidence Summary` (escaped per-card concise basis/checks/limitations) and `Acceptance Receipt` (run_id and card_key lookup reference, not the final receipt digest, avoiding a CSV/receipt hash cycle). Personal Notes and all other user-owned fields remain untouched. Acceptance Data carries no confidence percentage. Existing content/provenance field ownership remains authoritative. Default export keeps old layouts until an explicitly confirmed installation supports these fields/templates; CSV headers do not install them. New layout rendering puts status/evidence on the answer only, using `Warum diese Antwort?` in German and `Why this answer?` in English, keyboard-operable collapsed evidence, light/dark styling and text labels alongside colors. Detailed traces remain in the local report.

Pipeline owns only exact tags in namespaces `latinitas::acceptance::` and `latinitas::basis::` that its prior receipt lists. Origin summary is human only if every eligible sibling is human accepted, automatic only if every sibling is automatic, mixed if origins differ (including a mixed card); incomplete if any retained sibling is now ineligible/unresolved. Basis tags `source`, `rule`, `library`, `model`, `curated` mean at least one supported sibling uses that basis, not all siblings. Per-card truth stays in Acceptance Data/answer. Preserve inherited/source/user tags and case; namespace collision with an unowned existing tag requires explicit adoption or a blocked conflict, never deletion. Never write probability/confidence tags.

New-note CSV export and existing-note application are separate contracts. A prior export receipt proves neither absence of a destination note nor its current tags. For every proposed existing-note update that writes Tags, including routine still-eligible content updates, require either (a) a fresh destination snapshot, ownership/adoption reconciliation of the full tag set and exact supported managed-footprint approval, or (b) an explicit manual handoff inspecting and preserving actual destination tags and resolving namespace collisions before import. Without either route, block that update's application and do not label its files safe for direct reimport. Ordinary CSV reimport can remove destination-only tags when a managed field changes; namespace ownership and source-tag preservation do not prevent that loss. This prerequisite applies to the new pipeline, not a claim that legacy commands gained destination observation. Export never applies the files itself.

Compare every prior receipt's installed identities to current eligibility on regeneration, including changed checker/policy withdrawal. New CSV omits ineligible assertions, but the handoff must list previously exported note/card identities, reason, previous decision and required manual action. A handoff says installation is presumed from export unless a separately observed import confirms it; exporting is not proof of installation. Manual path: in a disposable/backup collection, locate identity, review affected card, remove/update stale assertion/status or suspend it manually as appropriate, record resolution and verify unrelated fields/history/scheduling preserved. This proposal does not perform suspension. A supported managed_retained_fields path requires registered layout, fresh observed snapshot, exact full-column plan approval and post-import observation/reconciliation; unsupported clearing/retirement/template changes stay blocked. Retain receipts and previous decisions; do not delete history or claim a missing CSV row retired a card.

For partial sibling invalidation, ordinary regenerated CSV withholds the affected whole note row until resolution; it must not blank stale sibling payloads or reassert an old acceptance badge. A supported destination-approved retained-field plan is a separate operation and preserves unselected sibling values, exposing any unresolved stale assertion in its handoff. Unrelated notes remain exportable.

## 8. Curated payload and approval proposal

`latinitas-curated` v1 has exactly `format`, `version`, `source_scope: ID`, `items: [Item]`. `Item = {key: ID, rule: {text: string, language: de|en, applicability: string, caveats: [string], evidence: [Evidence]}, mnemonics: [Mnemonic], examples: [{latin: string, explanation: string, evidence: [Evidence]}], tags: [string], provenance: {document: string, section: string, reference: string, wording: quoted|agent_proposed|author_composed}}`. `Mnemonic = {key: ID, language: de|en, text: string, rule_key: ID, provenance: provenance object}`. Unique item keys within source scope; unique mnemonic language/key pairs; mnemonic rule_key equals item key. Empty mnemonics/examples permitted, but rule evidence is required. Content is escaped before rendering; mnemonic HTML is not executable.

Separate `latinitas-curated-approval` v1 records exactly `format`, `version`, `approval_id: H`, `supersedes: [H]`, `source_scope: ID`, `item_key: ID`, `subject: rule|mnemonic|rendered_card`, `subject_key: ID`, `language: de|en`, `fingerprint: H`, `decision: approved|rejected`, `reviewer: string`, `reason: string`, `reviewed_at: timestamp`. approval_id hashes the remaining record. The unique unsuperseded matching decision applies; conflicting decisions without explicit supersession block export, never use timestamp order to override a rejection. Rule fingerprint covers key, rule text/language/applicability/caveats/evidence and provenance. Mnemonic fingerprint covers key, language, wording, rule fingerprint and association/provenance. Rendered-card fingerprint covers semantic key, language, prompt, answer, visible explanation/caveats/provenance, rule fingerprint, used mnemonic fingerprints, template digest and presentation config. Approvals attest exact content; they are not general authority or provider permission.

Approval requirements:

- Every card needs approved rule and rendered-card fingerprints.
- Every mnemonic shown on either side additionally needs approval of that language-specific mnemonic and its association with the rule. Rule-only cards need no mnemonic approval.
- A missing requested mnemonic variant yields withheld missing_language_variant for mnemonic-required cards; rule-only eligible recipes remain available. Do not translate German wordplay automatically or insert a placeholder mnemonic.

Approval invalidation:

- Changed rule/caveats/evidence invalidates dependent rule/mnemonic/rendered approvals.
- Mnemonic-only edits invalidate only that variant and cards displaying it.
- A theme/template/rendered-language change invalidates rendered approval, not the underlying linguistic rule acceptance.
- Translation into another language requires new rule/wording evidence and approval; no implicit approval transfer.

Illustrative structurally valid intake (not independently verified Latin content and not approved):

```json
{"format":"latinitas-curated","version":1,"source_scope":"course-demo","items":[{"key":"imperfect-a","rule":{"text":"Imperfekt Aktiv der regelmäßigen a-Konjugation: Präsensstamm, Imperfektzeichen und Personalendung.","language":"de","applicability":"Regelmäßige a-Konjugation, Indikativ Aktiv; Endungsanpassungen sind gesondert zu prüfen.","caveats":["Keine Aussage über unregelmäßige Verben."],"evidence":[{"source":"reference","reference":"demo:imperfect","version":"draft-1","text":"Illustrative reference; human source verification pending."}]},"mnemonics":[],"examples":[],"tags":["course"],"provenance":{"document":"demo","section":"imperfect","reference":"demo:1","wording":"agent_proposed"}}]}
```

Mnemonic-bearing example is the same item with mnemonics replaced by:

```json
[{"key":"ba-demo","language":"de","text":"Mit ba war es damals da.","rule_key":"imperfect-a","provenance":{"document":"demo","section":"imperfect","reference":"demo:2","wording":"agent_proposed"}}]
```

This is an agent-proposed memory aid, not quoted course authority or an approved rule. For language=en and recipe=mnemonic_recall, this payload has no English mnemonic: structurally valid intake, withheld card (`missing_language_variant`), no model translation and no export. The same rule-only German rule_application can proceed once its rule/rendered approvals exist. Invalid variants: missing mnemonics key (use []), mnemonic rule_key="other", empty rule evidence, duplicate item key, version=true or extra `approved:true` all fail validation. An approval whose digest matches mnemonic text but not its rule association is invalid/stale.
