### Finite support and comparison rules

Engineering support means representability, not an evaluated automatic-policy cell. The initial support registry uses the existing validated noun/adjective/verb feature vocabulary in `phrase_inputs.py`, source forms with confirmed senses/mapping, and exactly the four controlled families `preposition-noun`, `noun-genitive`, `verb-noun`, `adjective-noun`. It adds the contract's explicit PPP role and target-bearing cloze records. Standalone production may select supplied cells or derive bounded target forms from verified source forms/principal parts under enumerated applicable rule/library evidence, recording the derivation and checks. A missing/unconfirmed source form or inapplicable paradigm cannot be invented; the requested target surface need not already appear in the deck. The spec's contrasting verb/noun/adjective production and PPP examples remain required acceptance scenarios. Full morphology-matrix completion and original-corpus syntax discovery remain v0.5.5 work, not an excuse to omit the v0.5.0 examples.

Every registry revision must enumerate recipe IDs, family/role requirements, supported feature tuples or finite source-cell selection rule, evidence applicability and unsupported reasons. T-187 owns the strict reader/registry binding; T-188 owns library/rule applicability; T-191 owns recipe/target enumeration. Freeze the actual registry with the implemented candidate before T-200 designs supported evaluation strata. No implementation owner may extend an automatic policy by adding a registry entry.

Use canonical feature tuples for morphology, cited convention plus reconstruction/component checks for segmentation, supported meaning propositions/alternatives for translation, and clause-level entailment for explanations, exactly as contract §4 specifies. No universal segmentation convention or exact-string translation grading is selected. A missing applicable convention, unresolved reading or unsupported entailment is withheld; a comparator's agreement does not resolve it. Any empirical comparison revision requires policy versioning and renewed affected evidence.

### Policy denial is observable

Before any enabled policy exists, a candidate using the defined `v050-disabled` revision `1` policy with every check passing remains `origin=automatic`, `state=withheld`, reason `policy_not_enabled`; it may be inspected but cannot yield an ordinary learning CSV or an applicable destination plan. Contract §4 defines that bootstrap policy, canonical digest, built-in registry and exact policy/authorization commitments. Only a reviewed application update can change authority; no run file, profile, environment variable, self-authored approval or public registration command can add an enabled policy. Unknown policy tuples are configuration errors before calls. A stored `accepted` record, resumed run, stage command or stale batch cannot bypass the current registry. A withdrawn policy yields `policy_withdrawn` and an identity-specific ineligibility handoff for prior exports. Offline copies learn withdrawals only after the application update; no remote revocation guarantee is claimed.

Automatic positive engineering vectors run only with isolated synthetic application-registry fixtures. No enabled fixture is shipped, no public bypass switch is added and no fixture counts toward evaluation. Research artifacts record candidate assertions, checks and would-accept classifications, not accepted cards or import-ready learning files. Properly bound human-reviewed cards and separately approved curated cards still follow their established export paths.
