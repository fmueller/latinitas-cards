# v0.5.0 development workflows

This is a development walkthrough, not a release announcement. The installed
automatic policy is **`v050-disabled`, revision `1`, empty scope**. The profile's
policy digest must match that installed record; changing JSON cannot enable it.
Offline engineering completion does not accept the original automatic release
scope. Do not replace that scope with human-only fixtures to call the release ready.

T-200 must first obtain approval of its concrete bounded prerequisite plan before
reference acquisition, development feasibility, judge/study work or real inference.
Independent reference qualification, permitted custody, an approved evaluation and
separate exact-revision policy enablement remain distinct gates. Research outputs
are non-learning artifacts, not ordinary CSV acceptance. T-201 owns native and
integrated acceptance; publication is a separate blocked maintainer gate. Nothing
here authorizes hosted/private processing, production enablement or publication.

## Disposable offline examples

Use a development checkout, Python 3.13/3.14 and `mise run setup`. The runner uses
the checkout's integration fixture builders and locked dev dependencies; it is not
an installed-package tutorial or an extraction from real lecture notes. It creates
original synthetic data and synthetic review identities, never real approval.
The output directory must not exist. Keep it outside source inputs and Anki data.

```sh
mkdir -p .amp/in/orb-backup
uv run python docs/examples/v050_disposable.py .amp/in/orb-backup/v050-example
```

Expected: `PASS`, zero network dispatch, two languages, six full-card human-path
engineering controls per language, one curated application card per language,
receipt replay without another CSV, and one exact manual-handoff identity after
deliberate fixture replacement. The final synthetic record replacement is a fault
injection, **not** a supported way to edit immutable acceptance records. The initial
CSV then represents an earlier snapshot, not currently eligible material. Never
import this material into a study collection. `source.json` records checkout HEAD;
`schemas/` captures the runtime schemas. Native evidence is not produced.

The following commands use its disposable German inputs. Replace `de` with `en`
for English; the source meanings and output language both change, not just labels.

```sh
demo=.amp/in/orb-backup/v050-example/de
uv run latinitas-cards pipeline validate --profile "$demo/pipeline.json" --json
uv run latinitas-cards pipeline report --run "$demo/workflow/run" --json
uv run latinitas-cards pipeline resume --run "$demo/workflow/run" --offline --json
uv run latinitas-cards pipeline preview --run "$demo/run" --json
uv run latinitas-cards pipeline handoff --run "$demo/run" --json
```

`report` inspects an existing execution snapshot without provider calls; there is
no `pipeline inspect` command. `preview` reconstructs current cards, and `handoff`
compares installed-material obligations recorded by earlier exports. Reports do
not attest that a CSV was imported. Retain the whole run, stages, approvals,
receipts and ancestor CSV files, not only `report.json`.

## Library-only stages, optional review and resources

To prepare a new run and inspect its stages before any further work:

```sh
uv run latinitas-cards pipeline run --profile "$demo/pipeline.json" \
  --objectives "$demo/objectives.json" --output "$demo/prepared" --offline --prepare-only --json
uv run latinitas-cards pipeline stage analyze --run "$demo/prepared/run" --offline --json
uv run latinitas-cards pipeline stage select --run "$demo/prepared/run" --offline --json
uv run latinitas-cards pipeline resume --run "$demo/prepared/run" --offline --json
```

The finite stages are `ingest`, `analyze`, `propose`, `counter_check`, `decide`,
`select`, `render`, `export`. A stage success is not semantic approval. With no
providers, library/source/rule coverage is lower than a separately qualified
workflow might achieve; there is no fabricated model verdict. Supply existing
Latin Stanza resources explicitly with `run --library-resources DIRECTORY`.
`LocalStanza` disables downloads and does not supply a complete ambiguity set or
lexical sense/valency authority. Missing packages/resources are processing failures,
not evidence that a Latin reading is false. Installing optional `annotate` resources
is separate from installing the package and does not authorize model downloads.
The example runner deliberately tests a nonexistent resource directory.

Optional human review is independent authority, not a mandatory replacement for
automatic acceptance. It must cover the complete current card assertion set,
including source binding, target, translations, explanation, caveats and rendered
sides. The library API's `AcceptanceReader.decide(origin="human", ...)` requires
bound checks, persisted stages and an explicit `Human` record. There is no public
`pipeline approve-all` or interactive full-card reviewer command. The synthetic
runner demonstrates record plumbing only; do not copy its reviewer as authority.
Legacy `claims record` approvals do not automatically approve an entire new card.
See [bounded grammar cards](grammar-pipeline.md) for target and recipe contracts.

## Authorized provider stages and real token-accounting refusal

Providers are explicit paired `proposal`/`counter_check` endpoints in profile v1.
There is no implicit endpoint, model, fallback or network permission. `--offline`
forbids dispatch; `--local-only` restricts declared locality. Restrictions persist
on resume; use a new run to relax them. An orb is not the user's local machine.

The [provider boundary](provider-boundary.md) defines full endpoint paths, runtime
credential references, task/wire-request disclosure and permission records.
Configuration and possession of input files are **not hosted permission**. Before
any authorized hosted stage, inspect the complete disclosed task, source fields,
Unicode spans, input/request hashes, endpoints/models, retention terms and effective
call/token/time caps. Permission must bind run/config/endpoint/expiry and the exact
disclosed scope. Do not place credentials in JSON or URLs. These are command forms
for a separately authorized run, not permission to execute them now:

```sh
uv run latinitas-cards pipeline run --profile authorized-profile.json \
  --objectives objectives.json --output authorized-run --prepare-only --json
uv run latinitas-cards pipeline stage analyze --run authorized-run/run --json
# Inspect analysis before proposing; each stage requires its predecessor.
uv run latinitas-cards pipeline stage propose --run authorized-run/run \
  --allow-hosted exact-permission.json --json
# Continue only after successful proposal, not after a token-bound refusal:
uv run latinitas-cards pipeline stage counter_check --run authorized-run/run \
  --allow-hosted exact-permission.json --json
uv run latinitas-cards pipeline resume --run authorized-run/run \
  --allow-hosted exact-permission.json --json
```

Today no production endpoint is token-qualified. An unqualified configured endpoint
must yield **`missing_token_bound`**, no calls, incomplete report and deferred work,
not a linguistic rejection. Endpoint labels or a byte/4 estimate cannot qualify it.
The trusted adapter must prove an upper bound including prompts/protocol overhead;
the ledger charges input plus reserved output for both roles and retries. Unknown
calls stay charged and are not blindly retried. `reconcile-call --help` documents
captured-request retrieval or abandonment; abandonment does not cancel remote
billing. Duplicate retry requires both `--retry-unknown` and
`--confirm-duplicate-billing` and current permission/budget. Model agreement is not
reference truth, acceptance authority or a token-usage attestation.

Run only the controlled public-HTTP engineering tests below to exercise dispatch,
blind counter-check, interruption/resume, permission binding and refusal. They use
synthetic token bounds in an isolated process and loopback servers, not a model,
hosted service or approved production policy:

```sh
uv run pytest -v tests/integration/grammar_pipeline_test.py -k \
  'orchestrated_http_success_lost_response_resume_and_offline or orchestrated_permission_exact_requests_and_renewal or pipeline_report_provider_prerequisite_is_not_linguistic_rejection or orchestrated_unqualified_provider_labels_do_not_supply_token_bounds'
```

## Selection, output and recoverable batches

Default recipes are translation-first. `grammar-study` explicitly selects production
and curated recall/explanation recipes; neither preset enables clozes or authority.
Saved overrides precede CLI overrides; include/exclude conflicts reject. A profile
saved with `--save-profile NEW_FILE` binds inputs by hash and makes paths absolute.
Keep immutable input identities and explicit objective keys across wording changes.

`processing.max_source_units` bounds selected objective work, including automatically
enumerated source forms; it is not a lexical-entry count. `max_calls`, `max_tokens`,
timeout and retries bound processing separately. `selection.variants_per_binding`
bounds alternatives within one controlled pattern binding; it is not all combinations.
Default `selection.output_limit: null` imposes **no implicit output quota** (not 20).
Suppression and acceptance happen before a positive output limit. Reports separate
`suppressed`, `accepted_unselected` and `deferred_source_work`; deferred work is not
a count of undiscovered candidates or a linguistic rejection.

For a currently eligible run with more than one accepted selected card:

```sh
uv run latinitas-cards pipeline export --run eligible-run --output batch-1.csv --output-limit 2 --json
# Copy the returned receipt_id exactly, not a numeric offset:
uv run latinitas-cards pipeline export --run eligible-run --output batch-2.csv \
  --output-limit 2 --after-receipt RECEIPT_ID --json
# After explicitly reconfirming changed input hashes/selection:
uv run latinitas-cards pipeline export --run eligible-run --profile renewed-profile.json \
  --output next.csv --reconcile-receipt RECEIPT_ID --json
```

Replay reuses the original receipt/files, not the newly supplied filename. Retain
ancestor outputs for integrity checks. Reconciliation is not retirement or import
approval. A recovery-required transaction may already have published its CSV;
retry the unchanged request to recover receipts, never blindly import a second file.
For executable batch/limit controls, including more than 20 eligible cards:

```sh
uv run pytest -v tests/integration/grammar_pipeline_test.py -k \
  'full_output_and_receipt_bound_batches or processing_limit_precedes_output_limit_and_resumes or batch_invalidation_reconciles_only_changed_source'
```

## Curated intake, exact approval and ownership

Use [curated intake](curated-intake.md) for the strict candidate, permission,
approval-history and recipe-plan shapes. The permitted original synthetic lesson
in `tests/fixtures/curated-extraction/` is runnable offline:

```sh
uv run latinitas-cards curated validate tests/fixtures/curated-extraction/candidates.json \
  --permissions tests/fixtures/curated-extraction/permissions.json
uv run latinitas-cards curated preview tests/fixtures/curated-extraction/candidates.json \
  --permissions tests/fixtures/curated-extraction/permissions.json
```

Extraction permission records attest original source bytes and **all** prior
manual/local/hosted processing. They neither authenticate rights nor authorize a
new call. Preserve source wording and German wordplay. Agent proposals need
`agent_proposed` provenance, not quotation or course authority. A missing mnemonic
remains missing; an English rule does not approve a German or English aid.

Preview with `--plan PLAN` exposes exact `card_key`, rendered HTML and requirement
fingerprints. A real reviewer supplies explicit rule, displayed mnemonic and
rendered-card decisions, language, reason, timestamp and superseded heads; use
`make_approval` to seal those supplied decisions, not to decide. Submit them with
`curated review INPUT --permissions PERMISSIONS --plan PLAN --decisions DECISIONS --approvals OLD_HISTORY --output NEW_HISTORY`.
Omit `--approvals` only on first review; retain every history. Then
`curated export INPUT --permissions PERMISSIONS --plan PLAN --approvals NEW_HISTORY --output NEW_CSV --run RECEIPT_STORE`.
Repeat the exact preview language/profile/recipe/theme options on review and export;
without `--plan`, review cannot record rendered-card decisions.
There is no approve-all default. Rule-only cards need no invented mnemonic.
Theme/template/language changes renew affected rendered approval. Rule edits
invalidate dependent aids; a mnemonic-only edit leaves unchanged rule-only
approval valid but can still block a whole installed note row for safe handoff.

## Initial import, updates, upgrades and rollback

Initial CSV import is manual. Install the exact opt-in note type, map `LatinitasID`
to the first field, match by note type, enable HTML/comma, map managed fields and
the complete Tags column, and leave `Personal Notes` **unmapped**. Preview first;
CSV headers never install templates. Keep note/card keys and template ordinals,
user fields, user/source tags and schedules. `acceptance-1` adds answer-only evidence
and note-level summary tags; mixed siblings have per-card origins, not a universal
note-level verdict. Reserved `latinitas::acceptance::*`/`latinitas::basis::*` tag
collisions reject, including case variants. Receipts own generated tags only,
never arbitrary user/source tags. Tags are filtering metadata, not authority.

```sh
uv run latinitas-cards pipeline migration-plan --acceptance --family grammar --json
uv run latinitas-cards pipeline migration-plan --acceptance --family curated --json
# Only AFTER installing the exact family layout in a disposable destination,
# and choosing its exact id/version/template digest in the profile:
uv run latinitas-cards pipeline confirm-layout --profile installed-profile.json \
  --family grammar --installed --json
```

Confirmation records an operator attestation beside the profile. It does not read
Anki, install anything or certify native preservation (`applied: false`,
`native_verified: false`). Wrong family/digest fails. Copy existing profiles before
an explicit format upgrade; do not reinterpret legacy phrase-input v1 as v2 or
silently replace templates. For existing collections, back up a closed collection,
inspect the destination and review any structural/template migration separately.
Restore a full closed backup for rollback, then reacquire destination evidence and
reconcile old journals/receipts. Reverting a profile or approval file alone cannot
undo an import or erase a retained rejection/withdrawal.

Grammar and curated exports currently use **manual-only** initial import and
installed-ineligibility handoff, not a `managed` grammar/curated adapter. Supported
managed principal-part/phrase layouts use fresh closed capture, explicit adoption,
subset approval, `plan → approve → emit → observe → reconcile`; consult
[managed capture](managed-capture-and-adoption.md) and
[phrase workflows](reviewed-phrase-inputs.md). Their content-only retained-field
transport preserves actual unapproved slots; it does not create/retire cards or
authorize a new layout. Do not feed new grammar/curated layouts through it.

Withdrawal, source/policy invalidation or unavailable coverage reports exact prior
note/card/decision identities through `pipeline handoff` or curated receipts.
**Omission is not retirement.** The user must inspect installed material, choose an
explicit supported manual action and verify it against fresh destination evidence.
Neither handoff command marks that native resolution done. T-195's manual path and
T-201's native history/scheduling evidence remain separate, unproven here.
