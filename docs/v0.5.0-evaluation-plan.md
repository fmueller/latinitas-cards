### Custody capability and missing boundary

The approved boundary requires implementation and ordinary review roles to be unable to retrieve protected answers or source maps through files, thread/artifact reads or file-transfer APIs. Current capabilities do not demonstrate that boundary:

- `scripts/capture-evaluation.py` exclusively reserves a 0700 directory and 0600 files, retains raw bytes before validation and refuses overwrite. These are same-owner file controls, not separate credentials or protection from the owning runtime. The [v1 harness](evaluation-harness-v1.md#invocation-and-custody) explicitly supplies no model transport and is not a tamper-proof store. Structural validity cannot certify rights, linguistic entailment or isolation.
- `read_thread` can read owner-accessible threads; artifact reads follow artifact access, including owner access to thread-only artifacts. `download_thread_file` reads files in another owned thread's repository, and `thread_file_url` exposes executor files through temporary owner-readable URLs. Private thread visibility retains owner access. No per-role answer/source-map deny grant is exposed by these interfaces. No historical answer stores were opened to test this.
- [Custom agents and plugin hooks](https://ampcode.com/docs/customize/plugins) support tool allowlists and rejecting `tool.call` events. [Managed settings](https://ampcode.com/docs/cli/settings#enterprise-managed-settings) can disable tools, including server-side tools in orbs. These are potential components, not an installed custody boundary here: no separately administered evaluator identity, protected store, immutable tool policy or complete retrieval-path denial has been configured and tested. A locally editable hook, prompt or tool exclusion alone does not establish storage/API authorization.
- A separate orb isolates its filesystem but does not, by itself, revoke the same owner's thread, artifact or transfer authority. No new thread, account, plugin, ACL or credential was created or changed in this inspection.

**No viable restricted surface has been demonstrated for the required denial test.** No sentinel denial is claimed. Creating protected answers first and testing afterward would violate the gate. The missing capability is an independently administered, non-bypassable execution/storage boundary denying implementation/review roles every protected retrieval route, while allowing only bounded task inputs and independently audited safe-report egress. Custodian and safe-report auditor access also need explicit grants and logs.

The maintainer/coordinator could select and provision:

1. An external custodian-controlled evaluator with separate credentials and storage, no implementation/review mount or administrative access, a task-only product interface, and audited answer-free report transfer.
2. A separately administered Amp identity/workspace with no developer sharing, credential inheritance or owner bridge. Cross-identity thread/artifact/file denial must be demonstrated; a second thread under the current owner is not this alternative.
3. An administrator-supported locked execution/tool surface with independently controlled storage and server-side denial across all retrieval APIs. Confirm that shell/network, tool discovery/calls, delegation, settings changes and transfer helpers cannot bypass the boundary; do not infer this from a tool being absent from one prompt.

These are proposals, not available or approved deployments. Before choosing protected material, test the selected surface with disposable sentinels from actual implementation and ordinary-review identities through direct files, thread reads, artifact reads and file-transfer/temporary-file APIs. Preserve denial receipts, the allowed custodian read and safe-report handoff, actual principals and grants. Stop on any reachable protected path; never repair exposure by renaming material or asking agents to ignore it. No exhaustive new custody infrastructure is implemented by this documentation cycle.
