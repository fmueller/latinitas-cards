# M1 receipt: Pydantic AI migration feasibility (T-249)

Decision: **defer**. Do not adopt `pydantic-ai-slim[openai]` 2.76.0 for the hosted
provider path. Defer still permits A1, and optional R1, on the current transport
(post-trial plan); R1 still needs its own prospective hosted authorization. M2 is
not executable: no adopt receipt exists.

This receipt records one disposable prototype on synthetic data against loopback
receivers. It made no hosted call and used no private data or saved responses.
The product dependencies, `uv.lock`, the provider dispatcher, approval policies
and report/store contracts are unchanged. The prototype and its outputs stay
outside Git.

## Why defer

The safety contract can be kept only by wrapping the library in the existing
controls. In the gated prototype the existing `HTTPTransport` sends every byte and
the existing `_answer` reader decides success. The gate emulates the permission,
reservation and accounting that `ProviderRun` would keep. Pydantic AI would
contribute only the body construction in the OpenAI-compatible part of `_request`
(about 40 lines) and a second parse of output that has already passed the strict
reader. `_request` itself must stay for `latinitas-json/1`, Ollama and stage
identity. The glue the library needs is larger than the code it would replace:
about 80 prototype lines for the capture pass, the gate transport, the profile
override and explicit settings. It also adds 21 packages to the base install. No
supported configuration that reduces hosted plumbing was found.

Adoption would also change the wire for MiniMax: two system messages instead of
one, PromptedOutput template text, and a differently serialized schema. That needs
a new prompt version, fresh exact permission and T201 requalification. This is a
contract change requiring a maintainer decision, which by itself bars adopt. It
brings no evidence of better Latin correctness. The T248 deadline causes remain
unknown, and this library is not a remedy for them.

## Prototype controls

- One prototype script, corrected exactly once. The diagnosed failure: the first
  run exercised the strict reader's nested-value checks with a free-text
  objective, which skips those checks by design, and one nested replacement never
  matched the canonical key order. The correction reused the
  `tests/integration/providers_test.py` `NESTED` inputs with the structured
  recognition objective and routed each scenario's task and permission to the
  gate. It dropped the top-level control-character case, which the reader checks
  only inside structured values. It also added, beyond the diagnosis, the
  top-level extra-key and moved-field cases. The corrected script then ran
  unchanged on 3.13 and 3.14, and the behavior signatures were identical.
- The prototype ran under `unshare -rn` with only loopback up. A connect to
  `1.1.1.1:443` failed with `ENETUNREACH`. The environment was rebuilt with
  `env -i` (PATH, a scratch HOME and a tiktoken cache directory only), so no hosted
  API keys or proxy variables were inherited. The separate TLS probe was launched
  the same way from the shell but recorded no route check of its own. A synthetic
  `sk-synthetic-…` credential went only to loopback receivers. The SDK client held
  only a placeholder API key; the credential reached only `HTTPTransport`.
- A `sys.addaudithook` in the parent recorded non-loopback
  `socket.connect`/`getaddrinfo` events. It does not see spawned HTTP workers or
  sockets opened in C extensions. Those are bounded only by the network namespace,
  which blocks IP egress but not filesystem AF_UNIX sockets.
- Configuration A measured library defaults: `OpenAIProvider(base_url=…)`,
  `PromptedOutput(ModelAnswer)`, `max_tokens=2048` (sent as `max_completion_tokens`),
  `openai_reasoning_effort="low"`,
  and a 3-second timeout so the probe stays bounded.
- Configuration B, the gated design, uses
  `AsyncOpenAI(max_retries=0, http_client=httpx2.AsyncClient(transport=Gate, trust_env=False))`,
  `OpenAIChatModel(..., profile=OpenAIModelProfile(supports_json_object_output=False))`,
  `Agent(retries=0)`, `PromptedOutput(ModelAnswer)`, and the same cap and effort. The
  gate captures the exact body, refuses undisclosed bytes or a second send, and
  delegates the body to `HTTPTransport` with a 2-second deadline, then runs
  `providers._answer` before returning anything to the SDK.
- Reuse: the input is the existing `ModelTask` and the output types are the existing
  `ModelAnswer` (via `PromptedOutput`/`NativeOutput`). No parallel schema was
  introduced. Each call built a fresh `Agent` without message history.
- Roles: only the proposal role (`proposal/2`) was exercised. Both roles send
  `canonical(task)` as the user message, which stayed byte-identical, so the
  counter-check stays answer-free as a property of the unchanged `ModelTask`. The
  `blind/2` counter-check bytes were not built and are unknown.

## Send count and raw validation

Each cell gives receiver sends, then the outcome. A and B are identical on 3.13
and 3.14.

| Scenario | A: library defaults | B: gated |
| --- | --- | --- |
| Valid answer | 1, accepted | 1, accepted; equal to the strict-reader answer |
| HTTP 500 | **3**, failed (SDK retries) | 1, refused |
| Non-JSON text | **2**, failed (output retry) | 1, malformed |
| Duplicate key in answer | 1, **accepted** | 1, malformed |
| Duplicate key in envelope | 1, **accepted** | 1, unknown (screening cannot parse) |
| NaN in answer | **2**, failed | 1, malformed |
| Infinity in envelope | 1, **accepted** | 1, unknown |
| Extra top-level key / moved field | **2** each, failed | 1 each, malformed |
| Nested syntax, duplicate, NaN, control, shape, extra key, 3000-deep | 1 each, **all accepted** | 1 each, malformed |
| Valid nested values | 1, accepted | 1, accepted |
| Refusal | 1, failed | 1, malformed |
| Tool call | **2**, failed | 1, malformed |
| `finish_reason=length` with parseable text | 1, **accepted** | 1, malformed |
| 307 redirect | 1, not followed | 1, not followed (status recorded) |
| Body over 1 MiB | 1, **accepted** | 1, unknown (withheld) |
| Credential reflected | 1, **accepted** | 1, unknown (withheld) |
| Response after 4 s | **3**, 10.4–10.5 s total | 1, unknown at 2.01 s (worker killed) |

"Accepted" under A means the library returned an output object. The SDK default
(`max_retries=2`) and the output-retry default (1) were observed directly. Pydantic
AI's own validation cannot replace the strict reader: it accepted duplicates,
nonfinite envelope numbers, malformed nested values, cut-off output, oversize
bodies and reflected credentials. B kept one send per logical call while combining
disabled SDK and output retries with the gate. Three things were not exercised
separately: the gate's second-send refusal, retries disabled without the gate, and
a `ModelSettings['max_retries']` override. So independence from SDK settings rests
on the gate's design, not on an observed refusal. Durable reservations must stay in
`ProviderRun`, because SDK counters are not the ledger. For every disclosed case the
emulated journal recorded `reserved` before the send and `accounted:*` then
`timing_diagnostic` after it; the send itself is not a journal entry. That order
mirrors T248, but the journal was not the real ledger. Undisclosed bytes were
refused before reservation.

## Disclosure, permission and metadata

- Two capture passes produced byte-identical bodies, and so did 3.13 and 3.14. A
  capture pass whose transport raises before any socket can therefore produce the
  bytes to disclose. The gate sends only bytes whose raw SHA256 is in the permission;
  it checks before dispatch. In the test, a permission for the current `_request`
  bytes refused the pydantic-ai bytes with zero receiver sends. The test built the
  permitted set directly from the raw capture hash, not through
  `ProviderRun.disclosure()`.
- Today's `disclosure()` publishes `digest(decode_json(body))`, which equals the raw
  SHA256 only because `_request` emits canonical bytes. For the captured
  pydantic-ai body the two hashes differ. A migration must disclose and permit the
  raw captured bytes, or send `canonical(decode_json(sdk_body))`. In either case
  the gate must hash exactly the bytes it hands to `HTTPTransport`, and comparing a
  canonical digest while sending different raw bytes is not consent.
- The SDK adds `User-Agent: pydantic-ai/2.76.0` and nine `X-Stainless-*` headers
  (lang, package-version, os, arch, runtime, runtime-version, async, retry-count,
  read-timeout). httpx2 adds `Accept: application/json`, `Connection: keep-alive`
  and `Accept-Encoding: gzip, deflate` (3.13) or `gzip, deflate, zstd` (3.14). The
  gate records every header name and the SDK metadata values, and forwards only the
  body. The receiver saw exactly the names `accept-encoding`, `authorization`,
  `content-length`, `content-type` and `host`. That is today's `http.client` header
  set, so the data boundary does not widen. The header values come from
  `http.client` and `_http_worker` source and were not recorded.
- An environment `HTTP_PROXY` redirected the default configuration to the proxy
  trap (one proxied request, zero direct). The gated configuration sent zero
  proxied requests and one direct send. That is because httpx2 ignores environment
  proxies when a custom transport is given, and `http.client` reads none. It does
  not depend on `trust_env=False`. `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` and `.netrc`
  are excluded on the gate path by construction; they were not exercised.

## Message, parameter and schema differences

MiniMax-M3.1-Flash (bare, chat completions):

- Without a profile override (observed in configuration A), the OpenAI profile
  reports `supports_json_object_output=True` and PromptedOutput sends
  `response_format: {"type": "json_object"}`. The bundled `minimax` profile is
  not selected through `OpenAIProvider`. Bare MiniMax requires the explicit
  override, and with it B sent no `response_format`.
- `max_completion_tokens: 2048` and `reasoning_effort: "low"` were preserved (A and B).
- The user message is byte-identical to today's (`canonical(task)`).
- The system prompt differs. Today: one system message with the instruction, the
  prompt version, and `canonical(ModelAnswer.model_json_schema())`. Pydantic AI:
  the instructions as the first system message, then a second system message from
  `DEFAULT_PROMPTED_OUTPUT_TEMPLATE` ("Always respond with a JSON object that's
  compatible with this schema: … Don't include any text or Markdown fencing before
  or after."). That schema is serialized with `json.dumps` defaults (`", "`/`": "`
  separators, unsorted keys), with every property and `$defs` title removed and the
  top-level `"title": "ModelAnswer"` kept. Otherwise it is semantically the same.
- Both bodies are compact UTF-8, but top-level key order differs
  (`model, stream, messages, …` against canonical sorted keys), so the bytes differ.
  The bodies are also not JSON-equal, because the messages differ.
- The probe's instruction text repeated the `proposal/2` token. That harness defect
  stayed uncorrected under the one-correction cap and does not change the
  differences above.
- Unexercised: `PromptedOutput(template=False)` with the full current system string
  as instructions might reach one system message. Byte equality would still fail
  on key order, and MiniMax behavior with either layout is unknown without hosted
  calls.

Supported OpenAI native output (`gpt-4o-mini`, `NativeOutput(..., strict=True)`):

- One system message (no template), with
  `response_format.json_schema.{name: latinitas_model_answer, strict: true}` as
  today.
- Schema projection differs from `_strict_schema`. Pydantic AI keeps `const`,
  `pattern`, `minLength` and `minItems` and strips `title`. Today's projection maps
  `const` → `enum` and drops `minLength`, `pattern` and `minItems`. Whether OpenAI
  strict mode accepts the retained keywords was not exercised.
- Pydantic AI sends `max_completion_tokens` by default; today's `openai-json-schema`
  sends `max_tokens`.
- ToolOutput and tool acceptance were not used. They remain a separate, unapproved
  contract change.

## Deadline, bounds, TLS and offline paths

- In B, the deadline is demonstrated: the slow case ended as unknown at 2.01 s with
  the spawned worker terminated. That and the response bounds, redirect refusal and
  credential screening hold only because `HTTPTransport` performs the send. The
  SDK's timeout is 600 s with a 5 s connect timeout by default. Even with
  configuration A's 3-second timeout, a slow response took three sends. The openai
  SDK's own default client follows redirects. A did not follow the 307 only because
  Pydantic AI supplies a plain httpx2 client.
- TLS, Linux, no CA environment variables: `ssl.create_default_context()` has
  `verify_flags` 557088 (`VERIFY_X509_STRICT`, `VERIFY_X509_PARTIAL_CHAIN`,
  `VERIFY_X509_TRUSTED_FIRST`). The httpx2/httpcore2 default context has 32768
  (`TRUSTED_FIRST` only). It is looser on RFC 5280 strictness and stricter on
  partial chains. Both rejected the synthetic CA. On 3.13 both loaded 150 roots. On
  the uv-managed 3.14.7 neither loaded any file-based root, so that rejection shows
  only that both refused.
- With `SSL_CERT_FILE` or `SSL_CERT_DIR` set, httpcore2 builds
  `ssl.create_default_context(cafile=…)` or `(capath=…)`. The verify flags then
  match stdlib, but the anchor sets differ: httpcore2 loads only the given
  location, while the stdlib default also keeps the other compiled-in location
  (`SSL_CERT_DIR` on 3.13: 150 stdlib roots against 0 for httpcore2). Both accepted
  the loopback server signed by the synthetic CA. Otherwise httpcore2 uses
  `truststore` (the OS store) on macOS and Windows, a Linux CA-file fallback list,
  and ignores `SSL_CERT_*` under `trust_env=False`. None of those paths was
  exercised.
- So any socket opened by SDK or httpx2 code is a trust-policy change (verify flags,
  anchors, OS store) that needs documented maintainer approval. The gate design
  avoids it only because the sole SDK client uses the gate transport and the side
  paths below stay excluded.
- Startup: importing the library and the providers module took 1.0–1.5 s. No
  Python-level external network events were observed in the parent during
  startup, schema generation or agent runs.
- `tiktoken.get_encoding("o200k_base")` attempted DNS for
  `openaipublic.blob.core.windows.net` and failed offline. It downloads through
  `requests`, which has its own proxy, `.netrc` and CA-bundle handling outside the
  gate. In the tag, tiktoken is imported only by the embeddings and realtime
  modules, not the chat-model path, and the agent runs never triggered it. Nothing
  in `pydantic_ai` references `genai_prices.update_prices`.
- `genai_prices.calc_price` priced MiniMax-M3.1-Flash from bundled data
  (0.00075 USD per 1000+1000 tokens) with no network. Its `update_prices` builds its
  own httpx2 client and was not exercised. Those prices are not the
  `hosted_accounting` pricing and must not feed the ledger.
- The OpenTelemetry tracer provider was the no-op `ProxyTracerProvider`.
  `logfire-api` is a no-op shim while `logfire` is not installed. No telemetry
  export was observed.
- Strict offline validation (`ModelAnswer.read_json`, `_answer`) made no network
  calls with the library loaded.
- Unknowns:
  - The product's offline CLI validation and export with the library installed.
  - Lazy paths: count-tokens APIs, streaming, the Responses API and its websocket
    transport, gateway providers, and price auto-update.
  - The gate's second-send refusal, retries disabled without the gate,
    `ModelSettings['max_retries']`, 429/408/`Retry-After` and connection-error
    retries.
  - Cancellation and SDK `request_timeout` during an in-flight gated send.
  - HTTPS sends through either path (every prototype send was plain HTTP to
    loopback); a TLS positive control against a system CA; the `X509_STRICT`
    difference; truststore on macOS and Windows.
  - HTTPS/ALL/NO proxy variables and `.netrc` (not exercised); AF_UNIX reachability.
  - Telemetry export with an OpenTelemetry SDK or full `logfire` installed.
  - The `blind/2` counter-check bytes; the real `ProviderRun` ledger with the gate.
  - MiniMax and OpenAI acceptance of the changed messages and schema.
  - Non-Linux resolution and markers, and Python versions other than 3.13.5 and
    3.14.7.

## Prospective design if reopened

The smallest boundary is a request builder only. Pydantic AI would build the body
in a capture pass. `ProviderRun.request` would then disclose, permit and reserve
those raw bytes, and the dispatch callable would run the agent through a gate that
sends exactly those bytes with `HTTPTransport`. Everything else stays: Endpoint
validation, the bare-MiniMax qualification checks, `Limits`, the ledger, campaign
reservations, the T248 timing marks after durable accounting, the strict reader and
`compare_answers`. That design removes no plumbing. It also needs these invariants:

- The gate receives `ProviderRun`'s endpoint, body, timeout and cancel event. SDK
  `timeout` and `request_timeout` stay unset. The dispatch callable returns the gate's
  `TransportReply` or `TransportFailure`, never the SDK result, and `ProviderRun`'s
  `_answer` stays authoritative. Otherwise an SDK-side cancel could leave the worker
  sending while the call is recorded as interrupted.
- The SDK holds only a placeholder API key; the credential stays in `HTTPTransport`.
- The dispatch path must not use tiktoken, `genai_prices.update_prices`,
  `count_tokens` or `UsageLimits(count_tokens_before_request=True)`. A test must fail
  on any socket not opened by `HTTPTransport`.
- Qualification: every migrated body has a new `request_sha256` and stage
  identity. It needs a new prompt version, fresh exact permission and T201
  requalification of endpoint, model, settings and accounting. R1 measures the
  current transport only.
- Old stores: historical requests and responses stay readable through the same
  strict reader, and succeeded stages are reused only for identical bodies. New
  bodies are stale against old evidence and never inherit its approval.
- Rollback: remove the dependency and builder and restore `_request`. Evidence is
  kept, but answers produced through the migrated path cannot be qualified under
  the old path.

## Reopen conditions

Reopen only with a concrete hosted-plumbing reduction target that the gate does
not cancel out. Any reopening also needs maintainer approval for the message
change and its requalification, a fresh exact-version M1 receipt and its
independent review. M2 still needs every precondition in the post-trial plan
(accepted F1/F2/A1, R1 completed or explicitly declined, independent acceptance of
the exact migration contract and maintainer approval of any changed contract).
Until then, M1 closes as defer. It authorizes no dependency change, hosted call,
tool use, repair or policy enablement.
